\subsection{Case Study 1: Evaluating CVE-2024-21626}

CVE-2024-21626 is a critical vulnerability in runc, the low-level container runtime used by Docker and other container engines. It allows a malicious container to escape its isolation and execute arbitrary commands on the host system. This poses a significant risk to enterprises relying on containerization, as attackers could gain unauthorized access to sensitive data and system resources. 

The root cause of this vulnerability lies in how runc handles cgroups for containers, which are used to manage system resources like CPU and memory. During container creation, runc opens a file descriptor to the host's \texttt{/sys/fs/cgroup} directory to configure resource limits. This descriptor remains open throughout the container’s lifecycle and is exposed inside the container via \texttt{/proc/self/fd/}, which lists all open file descriptors of the running process. The vulnerability arises when an attacker sets the working directory in the Dockerfile to point to one of these exposed descriptors, such as \texttt{/proc/self/fd/N}, where \texttt{N} refers to the specific file descriptor inherited from runc that points to the host’s cgroup hierarchy. This causes the container’s current working directory to resolve to a privileged host path. As a result, all subsequent relative file operations in the container are interpreted from the host’s cgroup filesystem rather than the container’s own root, allowing unintended access or modification of host resources.

This behavior is enabled by Linux's treatment of \texttt{/proc/self/fd/N} as dynamic symlinks to open file descriptors. When dereferenced, these symlinks resolve to the original host-side path, regardless of container filesystem restrictions. Because runc and Docker do not restrict access to inherited file descriptors or sanitize the working directory path during initialization, attackers can exploit this oversight to escape isolation. By simply changing the container’s working directory to a leaked file descriptor, a malicious container can directly interact with host-managed control groups.

To test the exploitability of CVE-2024-21626, we designed a \houdini trick that executes the following steps:
\begin{enumerate}
    \item Launch a container with various runc versions.
    \item Set the working directory to \texttt{/proc/self/fd/<fd>}, pointing to a controlled file descriptor.
    \item Attempt to break out of the container by leveraging the misconfigured working directory.
    \item Validate whether commands can be executed on the host system.
\end{enumerate}

The CVE for this vulnerability initially indicated that the affected runc versions were $\geq 1.0.0\text{-}rc93$, $\leq 1.1.11$. This suggests the vulnerability was introduced in runc version rc93 and fixed in version 1.1.12. However, empirical tests conducted by \houdini revealed a significant discrepancy with this assumption. Houdini's testing showed that earlier runc versions, such as \texttt{1.0.0-rc1}, \texttt{1.0.0-rc2}, \texttt{1.0.0-rc3}, and \texttt{1.0.0-rc4}, also exhibited the same vulnerability. This discovery expands the scope of the CVE, revealing that the issue existed well before version \texttt{rc93}.

This discrepancy highlights a recurring issue in vulnerability disclosure processes: CVEs often rely on assumptions from static code analysis or limited testing. Without rigorous empirical validation across historical versions, critical edge cases can be missed. In the case of CVE-2024-21626, this oversight could have allowed vulnerable deployments relying on older runc versions to remain unpatched under the false belief that they were unaffected.

These findings highlight two key aspects of \houdini’s role in uncovering the true scope of the vulnerability. Firstly, it challenges misleading security assumptions. Secondly, it identifies gaps between intended and actual enforcement.

The security assumption outlined in the CVE is that the vulnerability exists only in runc versions >= 1.0.0-rc93, <= 1.1.11, suggesting that earlier versions are safe. This creates a false sense of security, leading users and system administrators to believe there is no urgency to patch or retire older versions. Rather than accepting the CVE’s claims, \houdini takes a more rigorous approach by testing the actual behavior of the continaer to determine whether the vulnerability is present in those earlier versions. In doing so, \houdini follows a fundamental security principle: security must be validated through testing, not simply assumed or trusted. 

While security policies and CVEs often describe what should be true, such as which versions are affected or which behaviors are restricted, what actually happens at runtime can tell a different story. Houdini helps expose these gaps between what is stated in documentation and how the system behaves in practice by testing the system in real-world scenarios. For example, while the CVE marked runc version 1.0.0-rc93 as the point where the vulnerability was introduced, Houdini’s testing revealed that the issue existed in earlier versions as well, showing that isolation was already broken. This mismatch between what is expected and what is actually happening can lead to serious problems. Organizations may rely on official documentation and assume their systems are safe, overlooking vulnerabilities that fall outside the scope of the CVE. As a result, they might miss critical risks, leaving systems unpatched and vulnerable to exploitation. By testing how the container behaves under specific configurations, Houdini provides a more accurate picture of the system’s security, which helps to uncover vulnerabilities that might otherwise be overlooked.

\subsection{Case Study 2 - Evaluating Host Process Manipulation}

In this evaluation, we examine whether a Docker container running as a non-privileged user with \texttt{UID=1000} can interact with and manipulate host processes that are also owned by \texttt{UID=1000}. Under normal circumstances, the PID namespace provides process isolation by restricting a container's visibility and access to processes outside its own namespace. However, when the container is launched with the \texttt{--pid=host} flag, it shares the host’s PID namespace, allowing it to enumerate and potentially interact with all host processes. This configuration effectively bypasses one of the core isolation mechanisms provided by containers. To assess the security implications of this namespace sharing, we investigate whether process-level interactions, such as sending signals or attaching debuggers are permitted between the container and host processes when UID ownership is aligned.

To evaluate whether a non-root container can interact with and manipulate host processes, the container was started with a combination of various security configurations:

\begin{itemize}
    \item \texttt{--pid=host}
    \item \texttt{CAP\_KILL}
    \item \texttt{CAP\_SYS\_PTRACE}
    \item \texttt{Privileged Docker container}
\end{itemize}

The evaluation began by assessing whether a container launched with \texttt{--pid=host} could list host processes using \texttt{ps aux}. As expected, the container displayed all processes running on the host, confirming that sharing the host PID namespace fully exposes the host's process table to the container.

Following this, we tested whether a container process could send a \texttt{SIGCONT} signal to a host process owned by UID 1000. The container was launched with \texttt{--pid=host}, allowing it to see and interact with host processes. Despite not being granted \texttt{CAP\_KILL}, the signal was successfully delivered. This is because both processes shared the same UID and PID namespace, and under standard Unix permission checks, a process can send signals to another process it "owns" by UID without requiring special capabilities. In this configuration, \texttt{CAP\_KILL} is not required for signaling host processes that have the same UID as the container process (e.g., UID 1000), as long as both share the same PID namespace (e.g., with \texttt{--pid=host}) and reside in the same user namespace (e.g., with \texttt{--userns=host}). However, if the target host process is owned by a different UID (another non-root user), \texttt{CAP\_KILL} is required for the signal to be delivered. That capability must also be effective in the user namespace of the target process. Importantly, signaling host processes owned by UID 0 (root) remains restricted even with \texttt{CAP\_KILL}, unless the container process itself is also running as root.

As shown in Table ~\ref{tab:pid-namespace-security}, combining \texttt{--pid=host} with \texttt{CAP\_SYS\_PTRACE} enables nearly the same level of interaction with host processes as granting full \texttt{--privileged} mode. Specifically, it allows a containerized process to list host processes, send signals, and attach a debugger to them, all key capabilities typically associated with privileged containers. However, unlike \texttt{--privileged}, this more targeted configuration limits access to only what's required, reducing the attack surface and following the principle of least privilege. These results demonstrate that it is unnecessary to over-privilege containers when finer-grained controls like capabilities and namespace sharing can achieve the same functional outcomes with significantly better security posture.

When the container is confined by AppArmor’s \texttt{docker-default} profile, its ability to interact with host processes becomes significantly restricted. Specifically, \texttt{docker-default} explicitly denies critical system calls such as \texttt{signal} and \texttt{ptrace}, which are required for sending signals and attaching debuggers to other processes. As a result, even if the container shares the PID namespace with the host and possesses the necessary capabilities, these operations will still fail due to mandatory access control restrictions imposed by AppArmor. However, including the \texttt{--privileged} flag when starting the container overrides AppArmor confinement by disabling the \texttt{docker-default} profile entirely. This lifts all AppArmor-imposed restrictions, allowing the container full access to the previously restricted system calls. As a result, operations that were previously blocked—such as sending signals or attaching debuggers to host processes are now permitted, even if AppArmor would normally deny them.

It is also important to note that granting capabilities such as \texttt{CAP\_KILL} and \texttt{CAP\_SYS\_PTRACE} alone is not sufficient for interacting with host processes unless the container shares the host’s PID namespace. Without the \texttt{--pid=host} flag, the container operates in its own isolated PID namespace, meaning it cannot see or reference host PIDs at all. As a result, any attempt to send signals or attach to host processes will fail—not because of insufficient capabilities, but because the target PIDs are simply invisible or meaningless within the container’s isolated view.

This case study highlights a core strength of \houdini, which is its ability to systematically explore and identify the least privilege for a given operation. By allowing users to declaratively modify container configurations, \houdini makes it easy to test a wide range of privilege combinations in a repeatable and automated way. Instead of relying on trial-and-error or defaulting to the overly permissive \texttt{--privileged} mode, users can incrementally grant permissions and observe the effect of each change. This enables security practitioners, developers, and researchers to precisely determine the minimum set of permissions required for a given trick to succeed. As a result, \houdini not only serves as a testing framework for container escapes and misconfigurations, but also as a practical tool for privilege minimization and hardening container deployments.

This case study highlights a scenario where the security policies administrators intend to enforce may not be upheld at runtime. For example, an administrator may configure a container with \texttt{--pid=host} to allow it to observe host processes—for instance, for monitoring or debugging—under the assumption that harmful interactions such as sending signals, attaching debuggers, or reading memory will still be blocked. However, if the container shares the same user namespace as the host (or UID mappings align), and the container process runs as the same UID as the host processes it targets, it may be able to perform these operations even without elevated capabilities like \texttt{CAP\_KILL} or \texttt{CAP\_SYS\_PTRACE}. This includes successfully sending signals or attaching via \texttt{ptrace} to same-UID host processes. \houdini empirically validates such configurations by testing for these interactions. If the container is able to perform unauthorized actions despite expectations to the contrary, it reveals a gap between intended security policies and actual enforcement.

\subsection{Case Study 3 - Evaluating Docker Privileged Port Forwarding Restrictions}

This case study highlights how discrepancies between Docker versions in handling privileged port binding can create gaps between administrators' intended confinement policies and actual enforcement. A change in Docker's handling of binding to privileged ports, such as the removal of the NET\_BIND\_SERVICE requirement starting from Docker 20.03, may allow containers to bypass restrictions even when policies are set to prevent it. 

For example, administrators might configure a container to be restricted from binding to privileged ports, but if Docker is running a version where the NET\_BIND\_SERVICE capability is no longer required for root containers (like in Docker 20.03 and beyond), the container could still bind to these ports despite the policy specifying otherwise. This creates a mismatch between the intended policy (restricting privileged port binding) and the actual enforcement (where containers can still bind to those ports in certain Docker versions).

Houdini helps identify these gaps by systematically testing container configurations across different Docker versions. By simulating different Docker versions and security policies, Houdini verifies whether containers are correctly enforcing the intended restrictions on privileged port binding. For instance, Houdini could test whether containers configured to prevent binding to privileged ports are still able to bind to those ports in Docker versions 20.03 or later, where the security model has changed. If a container running with Docker 20.03 or newer can bind to privileged ports despite the configuration specifying otherwise, Houdini will detect this discrepancy and highlight the gap between the intended policy and actual enforcement.

This set of experiments evaluates how Docker’s privilege model for binding to privileged ports (i.e., ports below 1024) has evolved across versions. Traditionally, binding to privileged ports required root access or the NET\_BIND\_SERVICE capability. However, newer versions of Docker introduced support for binding to these ports even in rootless containers, provided the necessary capability is explicitly granted.

By testing various combinations of user privileges (root vs. rootless) and capability settings across multiple Docker versions, this case study reveals which configurations are sufficient and which are excessive for achieving the goal of binding to a low-numbered port. It demonstrates that in modern Docker versions (23.0.0+), it is no longer necessary to run as root or grant all privileges to perform this operation. Instead, a least-privileged approach using a rootless container with NET\_BIND\_SERVICE is sufficient.

This case study shows that \houdini can empower Docker users to avoid unnecessary elevation of privileges, particularly avoiding full root access or the use of the --privileged flag, both of which expose containers to a broader attack surface. Houdini enables this kind of analysis by systematically testing Docker configurations and identifying the minimum set of privileges required for a given operation, helping developers and administrators adopt safer, more secure defaults.

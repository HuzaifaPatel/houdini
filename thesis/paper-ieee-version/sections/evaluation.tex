\section{Evaluation}
\label{sec:evaluation}

To assess the effectiveness of container confinement mechanisms, we conducted a series of controlled experiments to evaluate whether common security policies successfully prevent resource starvation, unauthorized access attempts, and container escapes. Our evaluation focuses on testing various isolation features, including namespaces, cgroups, seccomp, and Linux capabilities, under different configurations and attack scenarios. These are done in the form of three case studies.

\subsection{Case Study 1 - Evaluating Host Process Manipulation via PID Namespace Escape}

In this evaluation, we investigate whether a Docker container running with \texttt{--pid=host} can interact with and manipulate host processes. The PID namespace is responsible for process isolation, ensuring that containerized processes remain separate from host processes. However, when \texttt{--pid=host} is enabled, the container shares the host's PID namespace, making all host processes visible inside the container. We assess the security implications of this setting by evaluating the following:

\begin{itemize}
    \item Whether a container with \texttt{--pid=host} can list host processes.
    \item Whether the container can send signals \texttt{SIGKILL}, \texttt{SIG\-TERM} to host processes.
    \item Whether enabling \texttt{CAP\-\_SYS\_ADMIN} allows process tracing of host processes.
    \item Whether a container can read host process memory via \texttt{/proc/\$PID/mem}.
    \item Whether a container with \texttt{--pid=host} can manipulate processes running inside another container that also has \texttt{--pid=host}.
\end{itemize}

The container was started with various security configurations:

\begin{itemize}
    \item Default Docker container configuration (separate PID namespace)
    \item Docker container with \texttt{--pid=host}
    \item Docker container with \texttt{--pid=host} and additional capabilities \texttt{CAP\_KILL}, \texttt{CAP\_SYS\_PTRACE}
    \item Privileged Docker container with \texttt{--pid=host}
\end{itemize}

For each security configuration, different methods were tested to determine whether a process inside the container could interact and/or manipulate host processes.

The evaluation began by assessing whether a default container (see \Cref{lst:configuration-file}) can list host processes. This test checks whether the container is isolated in terms of its process namespace. In Docker, unless explicitly configured, containers run with their own private PID namespace. As such, they are unable to see or interact with processes running on the host system. To validate this, a trick was implemented that attempts to list all system processes using the command \texttt{ps aux}. When executed inside the default configured container, the output only included processes running within that container itself.

This behavior confirms that, as expected, the default Docker configuration does not include \texttt{--pid=host}, which would otherwise share the host's PID namespace with the container. Because of this separation, the container is unable to observe or affect processes running outside its isolated environment. The result of the trick was classified as a failure, which indicates that no process escape or visibility was achieved, which is the correct and secure behavior in this case.

This initial test serves as a baseline for container isolation and validates that Docker’s default settings do enforce process namespace isolation properly (for this testing environemnt). Subsequent tests explored how altering these settings (e.g., enabling \texttt{--pid=host}) affects this behavior.

For every subsequent test, we evaluated the impact of enabling host-level process namespace sharing by configuring the container with \texttt{--pid=host}. This setting allows the container to share the host's PID namespace, effectively removing the isolation between the container's and the host's process views. To test this, a trick was executed inside the container that simply invoked the \texttt{ps aux} command.

Unlike the default configuration, where only the container’s own processes were visible, the output in this case included the full set of host processes. The result of the trick was classified as a pass, indicating that the container successfully observed host-level processes. 

Following this, we tested whether a container could send termination signals, specifically SIGKILL to host processes by enabling \texttt{CAP\_KILL}. This configuration successfully allowed the container to send termination signals to host processes. By targeting a known host PID, the container was able to forcibly terminate the process using \texttt{SIGKILL}.

Next, we investigated whether a container could attach a debugger to host processes using the command \texttt{strace -p <PID>}, which attaches to a running process and traces the system calls it makes. This test was designed to evaluate whether a container could observe the runtime behavior of host processes.

Under default Docker settings, this operation failed as expected. Containers are denied the ability to trace processes outside of their own PID namespace, and more importantly, they do not have the \texttt{CAP\_SYS\_PTRACE} capability by default. This Linux capability is required to use debugging or tracing tools like ptrace, gdb, and strace on other processes. As such, attempting to attach strace to a host process resulted in a "permission denied" error.

To further examine the security boundary, we granted the container \texttt{CAP\_SYS\_PTRACE}. However, this alone was not sufficient because the container was still running in its own isolated PID namespace, it could not see or reference host PIDs. Once the container was configured with both \texttt{CAP\_SYS\_PTRACE} and \texttt{--pid=host}, the strace command succeeded in attaching to a host process. This allowed the container to begin tracing the system calls of the host process in real time, including file accesses, socket operations, and memory interactions.

We then examined whether the container could read host process memory by attempting to access \texttt{/proc/<host\_pid>/mem}. With Docker’s default restrictions, the operation was denied, but when running the container with \texttt{--privileged}, the operation was successful.

This case study highlights a core strength of \houdini, which is its ability to systematically explore and identify the principle of least privilege for a given operation. By allowing users to declaratively modify container configurations, \houdini makes it easy to test a wide range of privilege combinations in a repeatable and automated way. Instead of relying on trial-and-error or defaulting to the overly permissive --privileged mode, users can incrementally grant permissions and observe the effect of each change. This enables security practitioners, developers, and researchers to precisely determine the minimum set of permissions required for a given trick to succeed. As a result, \houdini not only serves as a testing framework for container escapes and misconfigurations, but also as a practical tool for privilege minimization and hardening container deployments.

This case study also highlights a scenario where the security policies administrators intend to implement are not properly enforced when the container is running. For example, an administrator may want to use the host's process namespace for tracing host processes but restrict the container from manipulating those processes. To achieve this, the administrator configures the container with \texttt{--pid=host}. \houdini validates this configuration by performing controlled tests to ensure the container can only trace processes and cannot send signals, attach debuggers, or read process memory. If \houdini detects that the container can perform any of these unauthorized actions, it reveals a gap between the intended policy and its actual enforcement. Houdini’s tests provide actionable insights that help administrators adjust configurations to enforce proper isolation while allowing the container to trace processes.

\begin{listing}[h]
  \caption{Trick Implementation for Case Study I}
\label{lst:pythonfile}
  \begin{minted}[frame=lines,framesep=2mm, fontsize=\scriptsize, breaklines=true]{yaml}
    #!/bin/bash

    TARGET_CMD="python3 /houdini/server.py"
    PID=""

    find_target_process() {
        echo "[1] Searching for process: $TARGET_CMD"
        PID=$(ps aux | grep '[p]ython3 /houdini/server.py' | awk '{print $2}' | head -n 1)
        if [[ -n "$PID" ]]; then
            echo "Found: PID=$PID"
            return 0
        else
            echo "Target process not found."
            return 1
        fi
    }

    send_signal() {
        echo "[2] Sending SIGCONT to PID $PID"
        if kill -CONT "$PID" 2>/dev/null; then
            echo "Signal sent successfully"
        else
            echo "Failed to send signal"
        fi
    }

    attach_debugger() {
        echo "[3] Attaching debugger with ptrace to PID $PID"
        if strace -p "$PID" -e trace=none -o /dev/null -t -qq &>/dev/null & sleep 1; then
            echo "Able to attach (via strace)"
            pkill -P $$ strace 2>/dev/null
        else
            echo "Failed to attach debugger"
        fi
    }

    read_memory() {
        echo "[4] Trying to read memory from /proc/$PID/mem"
        if dd if="/proc/$PID/mem" bs=1 count=4 skip=0 2>/dev/null | hexdump; then
            echo "Read memory succeeded"
        else
            echo "Failed to read memory"
        fi
    }

    main() {
        find_target_process || exit 1
        echo
        send_signal
        echo
        attach_debugger
        echo
        read_memory
    }

    main
  \end{minted}
\end{listing}

\subsection{Case Study 2 - Evaluating Docker Privileged Port Forwarding Restrictions}

In this case study, we evaluate Docker’s network isolation mechanisms to determine how well they enforce privileged port binding restrictions. Starting with Docker version 20.03, a significant change was introduced to Docker. They redefined unprivileged ports to start at 0 instead of 1024, effectively removing the need for root to bind to privileged ports. Table ~\ref{tab:port-binding-pre-20.03} presents the results.

This case study highlights how discrepancies between Docker versions in handling privileged port binding can create gaps between administrators' intended confinement policies and actual enforcement. A change in Docker's handling of binding to privileged ports, such as the removal of the NET\_BIND\_SERVICE requirement starting from Docker 20.03, may allow containers to bypass restrictions even when policies are set to prevent it. 

For example, administrators might configure a container to be restricted from binding to privileged ports, but if Docker is running a version where the NET\_BIND\_SERVICE capability is no longer required for root containers (like in Docker 20.03 and beyond), the container could still bind to these ports despite the policy specifying otherwise. This creates a mismatch between the intended policy (restricting privileged port binding) and the actual enforcement (where containers can still bind to those ports in certain Docker versions).

Houdini helps identify these gaps by systematically testing container configurations across different Docker versions. By simulating different Docker versions and security policies, Houdini verifies whether containers are correctly enforcing the intended restrictions on privileged port binding. For instance, Houdini could test whether containers configured to prevent binding to privileged ports are still able to bind to those ports in Docker versions 20.03 or later, where the security model has changed. If a container running with Docker 20.03 or newer can bind to privileged ports despite the configuration specifying otherwise, Houdini will detect this discrepancy and highlight the gap between the intended policy and actual enforcement.














\subsection{Case Study 3: Evaluating CVE-2024-21616}

CVE-2024-21616 is a critical vulnerability affecting Docker and runc that allows malicious containers to escape their isolation and execute arbitrary commands on the host system. This poses a significant risk to enterprises relying on containerization, as attackers could gain unauthorized access to sensitive data and system resources. 

The root cause of this vulnerability is the improper handling of a container’s working directory when set to a special file descriptor path such as \texttt{/proc/self/fd/<fd>}, where \texttt{<fd>} typically points to \texttt{/sys/fs/cgroup}. If exploited, this flaw allows a containerized process to break out of its confined environment, effectively compromising the host machine. The vulnerability affects runc versions from \texttt{v1.0.0-rc93} to \texttt{1.1.11}.

To test the exploitability of CVE-2024-21616, we designed a Houdini trick that executes the following steps:
\begin{enumerate}
    \item Launch a container with a vulnerable version of runc.
    \item Set the working directory to \texttt{/proc/self/fd/<fd>}, pointing to a controlled file descriptor.
    \item Attempt to break out of the container by leveraging the misconfigured working directory.
    \item Validate whether commands can be executed on the host system.
\end{enumerate}

As this vulnerability is due to the runtime itself and not related to the configuration of a particular container, We conducted tests across only various runc versions. This is shown in Table ~\ref{tab:cve201616}.

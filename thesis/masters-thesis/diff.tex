\begin{doublespace}
Containers have become a foundational technology in cloud computing due to their speed, lightweight nature, and ease of deployment. However, ensuring that containers are truly secure and properly isolated remains a significant challenge. Most existing tools focus on scanning images for known vulnerabilities or validating configurations against security best practices. While these approaches are valuable, they do not confirm whether core confinement mechanisms, such as namespaces, cgroups, seccomp, or AppArmor are actually enforced during runtime. As a result, containers may appear secure on paper, yet still expose unexpected security gaps due to misconfigurations, version-specific behaviors, silent enforcement failures, overly permissive defaults, or incomplete security policies.

To address this gap, this thesis presents Houdini, a modular framework for empirically testing container confinement. Houdini executes scripted tests, called tricks, inside an isolated virtual machine to observe whether security features like namespaces, cgroups, seccomp, and AppArmor are correctly enforced at runtime. By simulating real-world attack scenarios, Houdini reveals when isolation mechanisms silently fail, helping users validate security empirically.

Through a series of case studies, Houdini reveals misconfigurations, enforcement failures, and security inconsistencies in container behavior across different combinations of Docker, runc, and Linux kernel versions. These case studies demonstrate how seemingly secure containers can violate isolation guarantees due to subtle interactions between runtime settings and system versions. By making container confinement observable and testable, Houdini provides a practical, empirical foundation for building and validating more secure container systems.

\chapter{Introduction}

Containers have become a cornerstone of modern cloud infrastructure, revolutionizing how applications are developed, deployed, and scaled, particularly within microservices architectures and DevOps workflows. Unlike hypervisor-based virtual machines (VMs), which each require a whole operating system and rely on a hypervisor for hardware virtualization, containers are lightweight, share the host system's kernel, and incur minimal overhead. This efficiency makes them exceptionally well-suited for continuous integration and rapid scaling, allowing organizations to optimize resource utilization and reduce costs while ensuring quick, consistent deployments. Furthermore, containers enable seamless portability by packaging all userspace dependencies into a unified image, thereby avoiding the common problem of environment-specific discrepancies. Yet, despite containers' numerous benefits, they also introduce new security challenges, especially where container confinement is concerned.

Linux kernel features such as cgroups and namespaces are designed to isolate container resources, processes, and networks. However, these mechanisms are not foolproof. Kernel vulnerabilities such as buffer overflows and privilege escalation bugs can allow malicious processes to bypass isolation boundaries entirely. At the same time, misconfigurations like granting unnecessary capabilities, mounting sensitive host directories, or enabling privileged mode can weaken a container's confinement from the start. These issues open the door to container escapes, where attackers break out of their isolated environment and interact directly with the host system. Once this boundary is breached, they may interfere with other containers, access sensitive data, or compromise the entire infrastructure.

\section{Problem}

Containers are now a core part of how software is deployed. They’re used everywhere from large cloud systems to small edge devices because they help keep applications isolated, make it easier to manage dependencies, and allow services to scale efficiently. Their lightweight design and smooth integration with DevOps tools have made them the go-to choice across the industry. However, as containers are increasingly used to run critical or sensitive services, such as authentication systems, microservices, or data pipelines, ensuring their security becomes essential \cite{sultan2019container}. True isolation between containers, and between a container and the host system, doesn’t happen automatically. It relies on a range of security features built into the Linux kernel and container runtime. These include namespaces, cgroups, seccomp filters, AppArmor or SELinux policies, Linux capabilities, and filesystem restrictions. All of these work together to form the boundary that keeps containers safely confined.

The challenge, however, is that container confinement is not a monolithic entity. A container’s actual security posture depends on a complex and evolving set of mechanisms provided by the kernel and container runtime. Kernel features may be enabled or disabled, runtime behaviors can shift across Docker or runc versions, and default security profiles often change silently between distributions (See Section \ref{sec:evaluating-ptrace-enforcement-across-linux-distributions}). The sheer number of tunable settings, which we refer to as security knobs, creates a combinatorial explosion of possible configurations. These knobs include namespace settings, Linux capabilities, seccomp profiles, AppArmor or SELinux policies, cgroup limits, and more. Importantly, the goal is not to reduce the number of knobs, as they provide valuable flexibility and control. Instead, the real challenge lies in understanding what each knob does in practice and whether the intended confinement is being enforced as expected. Even experienced developers can overlook subtle misconfigurations, resulting in containers that appear secure but are missing critical enforcement. To make matters worse, tools like Docker rarely surface these issues through warnings or validation, allowing insecure setups to persist unnoticed.

These challenges highlight a broader problem: it is often difficult to tell whether container security settings are working as intended. Administrators may believe containers are isolated based on documentation or default behaviors, but in practice, policies can be silently overridden, misapplied, or broken by version changes. Sometimes, no explicit policy is set, and the system falls back on insecure defaults. In other cases, configurations conflict with one another, leading to unintentional privilege leaks. Even when no changes are made to container settings, updates to the kernel, Docker, or runc can subtly shift how security features behave. This creates a gap between how containers are supposed to be confined and how they behave in the real world. What’s needed is a way to test container security empirically and repeatedly, across versions and configurations, to uncover these unexpected behaviors before attackers do.

Despite the growing adoption of containers, there exists no systematic and empirical method to evaluate whether a container is confined. Existing tools primarily fall into two categories: static scanners that inspect images for known vulnerabilities, and policy generators that attempt to produce security profiles from application behavior. These tools are helpful but insufficient for our goal. They do not test the actual runtime behavior of a container in the context of its complete configuration and environment. There is a critical gap: developers have no means to verify whether their containers behave securely under realistic execution conditions and across the full range of kernel and runtime versions that may exist in production.

This lack of runtime validation creates a serious blind spot in container security. A container may pass static security checks, such as configuration audits or image scans, and still be vulnerable at runtime. This is because many security failures do not arise from obviously incorrect settings, but from subtle interactions between components, missing kernel support, or changes across versions of Docker, runc, or the Linux kernel. For instance, a seccomp profile designed to block dangerous system calls might silently fail if the underlying runtime or kernel does not support the necessary filtering features. Similarly, a container that is assigned limited Linux capabilities may still escape confinement due to a change in how the runtime applies namespace isolation or grants privileges internally. The container runs, the settings look correct, but the intended isolation is not enforced.

\section{Thesis Outline}

This thesis is made up of eight chapters and an appendix. Chapter 1 introduces the main problem: making sure containers are truly secure and properly confined. It explains why this is difficult in practice and motivates the need for a testing framework like Houdini. The chapter also highlights the key contributions of this work.

Chapter 2 gives background information to help readers understand how container security works. It covers the basics of Docker and containers, explains the difference between virtualization and containerization, and introduces key Linux features like namespaces, cgroups, capabilities, seccomp, AppArmor, SELinux, and Yama. These are all essential tools used to isolate containers from each other and the host system.

Chapter 3 describes how Houdini was designed. It explains the system’s architecture and the main goals behind it, such as making tests reproducible, easy to scale, isolated from the host, flexible across different setups, and easy to debug. The chapter also gives examples of how Houdini can be used in practice.

Chapter 4 goes into the details of how Houdini was built. It describes how Buildroot is used to create a minimal virtual machine, how tests (called “tricks”) are defined using YAML-like files, and how the system uses Python and Flask to manage and run these tests. It also explains how Houdini handles version pinning to make sure tests are consistent over time.

Chapter 5 shows how well Houdini works through a series of experiments. It proves that the system gives consistent results over time and across different machines, that it keeps the host safe by using virtual machines, and that it can support many different versions of Docker, runc, and the Linux kernel. It also includes performance tests to show that Houdini can handle many test cases efficiently.

Chapter 6 presents real-world case studies to show how Houdini can find problems in container security. These include testing a known vulnerability (CVE-2024-21626), checking if containers can interact with host processes, looking at privileged port restrictions, and testing how ptrace enforcement works across different Linux distributions.

Chapter 7 reviews related work in the field of container and system security. It discusses other tools and research on topics like sandboxing, system call filtering, eBPF tracing, security frameworks like AppArmor and seccomp, and tools for scanning or testing containers. This chapter shows how Houdini fills a gap that existing tools do not address.

Chapter 8 wraps up the thesis with a summary of what was learned and suggestions for future work. This includes expanding Houdini to support more container runtimes, integrating it into CI/CD pipelines, and building a larger set of test tricks.

The appendix includes some preliminary performance benchmarking results. These tests measure aspects such as the time required to make the root filesystem, booting the VM, building Docker images, and executing specific commands. They give a basic view of how Houdini performs in practice.

\section{Containers and Docker}

The emergence of containers as a lightweight alternative to VMs has significantly influenced modern computing, particularly in the domain of application deployment and cloud-native architectures. Virtualization enables multiple operating system (OS) instances to run in isolation on a single physical host. In contrast, containerization achieves isolation at the process level using features built into the Linux kernel, such as namespaces and cgroups. Containers do not require a full guest OS. Instead, they share the host OS kernel and only encapsulate the application and its dependencies. As a result, containers are significantly more lightweight and have faster startup times than VMs \cite{sharma2016containers}.

Docker is a widely adopted platform that automates the deployment, management, and orchestration of containerized applications. It provides an abstraction layer over Linux kernel features, which simplifies container creation and lifecycle management through a high-level interface \cite{ostrowski2024containerd}. A Docker container runs from a Docker image, which packages the application code, runtime, libraries, and configuration files into a single, portable unit. Docker images are built from Dockerfiles, which are declarative text files that specify the instructions for constructing the image.

Docker follows a client-server architecture in which the Docker client communicates with the Docker daemon, also known as the Docker Engine, which is responsible for building, running, and managing containers. This interaction occurs via a RESTful API, typically over a Unix domain socket on Linux systems (e.g., \texttt{/var/run/docker.sock}), or over a TCP socket when configured for remote access \cite{mrdevsecops_dockerarchitecture}. When a user issues a command such as \texttt{docker run}, the client sends an API request to the daemon, which then interacts with the kernel to allocate namespaces, configure control groups (cgroups), establish virtual networking, and launch containers. This separation of concerns allows for remote container management and seamless integration with external tools such as Docker Compose and Kubernetes.

As illustrated in Figure~\ref{fig:docker-architecture}, the Docker architecture is composed of multiple layers. At the top, the Docker client acts as the interface through which users interact with the system. The Docker daemon operates beneath the client, serving as the control plane that handles requests and manages the lifecycle of containers. It relies on container runtimes such as \texttt{runc} to instantiate and manage containers from Docker images. These containers share the host operating system kernel but operate in isolated environments, with each container encapsulating its application and dependencies. At the lowest level, the host OS interfaces with the underlying infrastructure, which may consist of physical hardware or a virtualized host. This layered design enables Docker to provide efficient, portable, and consistent containerized environments across diverse platforms.

The Docker daemon interacts with the underlying kernel to implement container isolation using Linux namespaces, such as those for process identifiers (PID), networking, and file systems. It also uses cgroups to enforce resource limits, such as CPU and memory usage. Docker images are distributed through registries, such as Docker Hub, which allow users to pull pre-built images and push their own for reuse or distribution.

Docker typically operates on top of a host OS and does not require a separate hypervisor. However, when Docker is run on non-Linux systems such as Windows or macOS, a lightweight VM is used to host the Linux-based Docker daemon. This setup is sometimes mistaken for traditional virtualization, but Docker itself does not emulate hardware and should not be classified as a hypervisor \cite{tuanh_docker_linux_virtualization}.

\section{Virtualization}

The existence of cloud computing can be attributed to virtualization, a technology that enables multiple operating systems (OSs) to run concurrently in an isolated environment on the same hardware. How does virtualization achieve this? It utilizes a machine's hardware to support the software that creates and manages VMs. A VM is a virtual environment that provides the functionality of a physical computer by using its virtual central processing unit (VCPU), memory, network interface, and storage. The software that creates and manages a VM is formally called a hypervisor or virtual machine monitor (VMM). The virtualization marketplace is comprised of four notable hypervisors, which are: (1) VMWare, (2) Xen, (3) Kernel-based Virtual Machine (KVM), and (4) Hyper-V. The operating system running a hypervisor is called the host OS, while the VM that uses the hypervisor is called the guest OS. To maintain consistency within this proposal, we will use the word "hypervisor" when referring to virtualization software. Hypervisors can be divided into two types, depending on where they are located on the machine: type 1 and type 2 ~\cite{patel2025hypervisor}.

Type 1 hypervisors run directly on physical hardware to create, control, and manage VMs, and do not require support from the host OS. Type 1 hypervisors are also called native or bare-metal hypervisors. The first hypervisors, which IBM developed in the 1960s, were type 1 hypervisors ~\cite{meier2008ibm}. Examples of type 1 hypervisors include, but are not limited to Xen, KVM, VMware ESX, and Microsoft Hyper-V ~\cite{bauman2015survey}~\cite{patel2025hypervisor}.

Type 2 hypervisors (also called hosted hypervisors) are installed on the OS (Windows, Linux, macOS), similar to how computer programs are installed onto an OS. In other words, a type 2 hypervisor runs as a process on the host OS. Type 2 hypervisors abstract guest OSs from the host OS by introducing a third software layer above the hardware. Examples of type 2 hypervisors include but are not limited to VMware Workstation, VirtualBox, and QEMU ~\cite{bauman2015survey}~\cite{patel2025hypervisor}.

Although the definitions of type 1 and type 2 hypervisors are widely accepted, there are gray areas where the distinction between the two remains unclear. For instance, according to its creator, RedHat, KVM is implemented and deployed using two Linux kernel modules that effectively convert the host Linux OS into a type-1 hypervisor ~\cite{graziano2011performance}. At the same time, KVM can be categorized as a type 2 hypervisor because KVM VMs are standard Linux processes that are competing with other Linux processes for CPU time given by the Linux kernel's native CPU scheduler ~\cite{kvmcpuschedule}.

\section{Process Isolation}

\subsection{Control Groups}
Cgroup is a Linux kernel feature that allows system administrators to allocate and manage system resources (such as CPU, memory, disk I/O, and network bandwidth) for processes or groups of processes. When you create a cgroup, you are essentially grouping processes and imposing resource constraints on them. This is crucial for resource management and isolation in multi-user or containerized environments. For instance, cgroups allow setting a limit on the amount of memory a set of processes can use, preventing any single process from consuming excessive resources and affecting other processes or the system as a whole. Additionally, cgroups allow for the prioritization of resources, ensuring that critical processes receive more CPU or memory than less important ones. They also offer monitoring capabilities to track how much of each resource a process or cgroup is consuming. This feature is extensively used in containerization technologies like Docker, where containers are assigned their resource limits via cgroups to ensure fairness and prevent resource hogging \cite{brown2014cgroups}.

\subsection{Namespaces}
Namespaces are another crucial Linux kernel feature that provides process isolation. A namespace isolates certain aspects of a system for a process or group of processes, ensuring that they have their independent environment. There are several types of namespaces, including PID, network, mount, user, and UTS namespaces. For example, a PID namespace allows processes within it to have their process IDs, meaning that processes in different PID namespaces can have the same process ID without interfering with each other. Similarly, network namespaces allow processes to have their network stack, which includes IP addresses, routing tables, and network interfaces. This isolation is necessary for containers, as it ensures that processes running in one container cannot see or interact with processes in another, even though they may be running on the same physical host. Namespaces, combined with cgroups, provide the foundation for building lightweight, secure containers in Linux systems.

In containerized environments, namespaces are what give each container the illusion of being a completely separate system. When a container is started, it is placed into multiple new namespaces, such as its own PID namespace (so it sees only its own processes), its own network namespace (so it has isolated network interfaces and routing tables), and its own mount namespace (so it sees its own filesystem layout). This separation is critical for security and isolation, as it prevents containers from accessing or interfering with other containers or the host. By combining several types of namespaces, Linux containers can achieve strong isolation while still sharing the same underlying kernel, making them far more efficient than full virtual machines.

\section{Linux Capabilties}
Linux capabilities are a fine-grained security mechanism that splits the traditional superuser (root) privileges into smaller, more manageable components. Instead of giving a process full root access, Linux capabilities allow for the assignment of specific privileges to processes, such as the ability to bind to a network port or change the system time, without granting complete administrative control. This is particularly useful for increasing system security, as it limits the potential damage caused by vulnerabilities in applications. For example, a web server might require the ability to bind to port 80 but should not need full root privileges. By assigning only the necessary capabilities to a process, the security surface area is reduced, making it harder for an attacker to exploit. This approach is commonly used in containerized environments, where processes are run with just the capabilities they need to function. Table ~\ref{table:linux-capabilities} provides a list of all the Linux capabilities in recent kernels.

Several Linux capabilities are significant for container security and confinement. For example, \textit{CAP_KILL} grants a process the ability to send signals to other processes, including SIGKILL, regardless of user ID. Without proper restrictions, this capability can allow a container to interfere with other processes on the host or within different containers. \textit{CAP_NET_BIND_SERVICE} allows binding to privileged ports (i.e., TCP/UDP ports below 1024), which are normally reserved for root. Dropping this capability is a standard security practice to prevent containers from impersonating system services such as SSH or HTTP. Another critical capability is \textit{CAP_SYS_PTRACE}, which enables a process to observe or manipulate the memory and execution of another process via the ptrace system call.

\section{Linux Mandatory Access Control}

\subsection{Secure Computing Mode}
Secure Computing Mode (Seccomp) is a security feature in the Linux kernel that allows administrators to filter and restrict the system calls that processes can make. It provides a mechanism to limit the actions that a process can perform, which is particularly useful in reducing the attack surface of applications, especially in containerized environments. With seccomp, you can create an allow-list or deny-list of system calls, effectively controlling which parts of the OS a process can access. For instance, you could block potentially dangerous system calls like execve, which is used to execute programs, or restrict the ability to open files by denying access to specific file descriptors. This reduces the risk of an attacker exploiting a process to gain control over the system. Seccomp is often used in combination with other security mechanisms like AppArmor and SELinux to provide an additional layer of protection.

\subsection{AppArmor}
AppArmor is a Linux security module that provides Mandatory Access Control (MAC) by enforcing security policies on individual programs. It restricts the actions that applications can perform by defining profiles that specify which files, directories, and capabilities the program can access. AppArmor operates by using a set of predefined or custom profiles, which are attached to programs, to limit their access to system resources. For example, an AppArmor profile for a web server might restrict the server's access to specific directories and prevent it from executing arbitrary binaries or making network connections to external IP addresses. AppArmor is easier to configure and manage than some other security modules, and it provides a level of protection by ensuring that even if an application is compromised, the attacker has limited access to the system \cite{archwiki_apparmor}.

\subsection{SELinux}
SELinux (Security-Enhanced Linux) is a security feature built into the Linux kernel that provides fine-grained control over what users, processes, and programs can access on a system. Unlike traditional Linux security, which relies on Discretionary Access Control (DAC), where the owner of a file sets its permissions, SELinux uses Mandatory Access Control (MAC). This means access decisions are enforced based on a global security policy defined by the system administrator, not by the discretion of individual users. Even if a user or process has root privileges, SELinux can restrict actions that aren't explicitly permitted by its policy \cite{redhat2007selinuxguide}.

At the core of SELinux is a labeling system. Every file, process, and resource on the system is assigned a security context (or label), which usually includes a type like httpd_t for web server processes or bin_t for system binaries. SELinux policies define which types can interact. For example, whether a process running with the httpd_t label can read a file labeled httpd_sys_content_t. When a process attempts to access a file or resource, the SELinux policy engine checks the labels and consults the loaded policy to determine whether to allow or deny the action. If the action is not permitted, it is blocked and logged \cite{redhat2007selinuxguide}.

SELinux operates in three modes: Enforcing, where policies are actively enforced and violations are blocked; Permissive, where violations are only logged (useful for debugging); and Disabled, where SELinux is turned off entirely. This flexibility makes it easier to adopt SELinux gradually or troubleshoot access issues without entirely disabling it \cite{redhat2007selinuxguide}.

In addition to these comprehensive LSMs, Linux also provides more specialized modules, such as Yama, which focus on narrower aspects of process confinement.
}



\DIFaddend \section{YAMA}


Yama is \DIFdelbegin \DIFdel{a Linux Security Module (LSM ) }\DIFdelend \DIFaddbegin \DIFadd{another LSM }\DIFaddend that adds additional restrictions to the ptrace system call, which is commonly used for debugging and process tracing. While ptrace is a powerful tool for legitimate uses like debuggers and profilers, it can also be abused by malicious processes to interfere with or spy on other running processes. Yama was introduced to mitigate these risks by controlling and limiting which processes can use ptrace on others, providing a simple but effective hardening mechanism against certain types of attacks.

The core of Yama’s functionality revolves around the /proc/sys/kernel/yama/ptrace\_scope setting, which controls how restrictive the kernel is regarding ptrace access. The available levels range from 0 to 3, each enforcing progressively stricter controls. With ptrace\_scope=0, the system behaves traditionally, allowing any process to ptrace another process owned by the same user if the target is marked as dumpable. At 1, only parent processes can trace their children, limiting the risk of arbitrary tracing. Level 2 requires a process to have CAP\_SYS\_PTRACE capabilities (effectively root-level permissions) to trace any process, and level 3 completely turns off ptrace system-wide, locking down the system from process tracing even by privileged users.

Yama is especially valuable in multi-user systems or environments where processes run under the same user account but should remain isolated from one another, such as in containerized or sandboxed environments. While it is a relatively lightweight security module compared to more comprehensive systems like SELinux or AppArmor, it adds a meaningful layer of defense against local privilege escalation attacks. However, it’s important to balance its restrictions with the need for debugging and profiling tools that rely on ptrace. In production environments focused on security, higher ptrace\_scope values (such as 2 or 3) may be appropriate, while development systems typically keep it at 0 or 1 to allow standard debugging workflows.

Yama does not enforce its `ptrace\_scope` restrictions when attempting to trace host processes from within a container because Yama’s enforcement is limited to the current process visibility defined by PID namespaces. In most container environments, the containerized process runs in an isolated PID namespace and cannot see or interact with host processes unless explicitly configured using options like `--pid=host`. Even when a container is started with `--pid=host`, allowing it to see host processes, Yama primarily governs interactions within the same namespace context and is not designed to enforce security policies across different namespaces.

Additionally, for Yama to restrict tracing of host processes, the containerized process would not only need visibility of host PIDs but also require sufficient privileges, such as `CAP\_SYS\_PTRACE`, in the host’s user namespace. In practice, other security mechanisms like AppArmor, SELinux, and seccomp often prevent such privilege escalation before Yama’s policies even apply. As a result, Yama’s effectiveness is primarily confined to preventing ptrace interactions between processes that are already within the same visibility scope, rather than serving as a cross-namespace isolation mechanism. This makes Yama a valuable tool for hardening processes within the same environment, but not a comprehensive defense against container-to-host process tracing attempts.


The behavior of Yama is controlled by the \texttt{/proc/sys/kernel/yama/ptrace\_scope} setting, which determines the level of restriction imposed on \texttt{ptrace} operations. The possible values are summarized below:

When Yama’s ptrace\_scope is set to 2, processes cannot freely attach to other unrelated processes, even if they have administrative capabilities or are running as root. In this mode, the ability to trace or debug a process must be explicitly granted by the target process itself or configured through system-level controls.

This permission can be granted using the prctl() system call with the PR\_SET\_PTRACER option, allowing a specific process to act as a tracer. Alternatively, the system administrator can modify the global ptrace policy by lowering the ptrace\_scope value in /proc/sys/kernel/yama/ptrace\_scope. Without such explicit authorization, ptrace attempts will consistently fail, regardless of user privileges or capabilities. This design enforces stronger security boundaries by preventing unauthorized inspection or manipulation of processes, even by privileged users, unless the target process explicitly consents to being traced.

\chapter{Design}

The design of Houdini is guided by a set of core principles aimed at enabling reliable, large-scale testing of container security confinement. At its core, Houdini seeks to ensure \textbf{reproducibility}, so that each test yields the same result when run under identical conditions, and behaves consistently across time and environments. Alongside reproducibility, Houdini is also built for \textbf{scalability}. Despite Houdini running one test at a time, the framework can queue large batches of tests automatically, without requiring users to script each case manually. This makes it easy to scale experiments across hundreds or thousands of container configurations with minimal effort. It also enforces strong \textbf{host isolation} by executing potentially dangerous container workloads inside tightly controlled VMs. The framework supports \textbf{flexibility across configurations}, which allows users to test a wide range of Docker flags, Linux capabilities, AppArmor profiles, seccomp profiles, runtime versions, and Docker versions. Finally, Houdini prioritizes \textbf{debuggability} by logging all configuration inputs and test results in a structured format, which enables users to trace and interpret trick outcomes. The rest of this chapter describes how each of these design goals is achieved in Houdini.



\section{System Architecture}
Houdini is a security benchmarking framework that is designed to enable secure and reproducible testing of container confinement across diverse configurations. Its architecture is divided into two components: (1) the physical host-side and (2) the guest-side. Each of these components has a specific and isolated role.

On the physical host side, users interact with Houdini through a lightweight Python-based command-line interface (CLI). The CLI is responsible solely for parsing user input, such as selecting a trick, running a VM, or building the Buildroot-based filesystem. It does not manage execution logic itself. For example, if a user provides input to run a trick, the CLI delegates control to a programmatic API, which is responsible for managing the execution flow.

In Houdini, a single security test case is referred to as a \textit{trick}, which encapsulates a specific container security scenario. Each trick consists of three files: a configuration file, a Dockerfile, and an executable script (see~\ref{sec:yaml-trick}). The configuration file defines how the container should be launched, including its security parameters. The Dockerfile specifies how to build the container image, installing dependencies, and copying the script. The trick script (which can be written in any buildroot-supported language) contains the logic for performing the security test (trick). Some examples of a trick are attempting to read a protected file or escalate privileges. The trick is typically expected to emit a clear "pass" or "fail" message based on whether the action succeeds.

A Flask server provides the API communication. Each trick is executed in a newly booted VM, built from a minimal, stateless image generated by Buildroot. This clean-slate approach ensures that every test runs in a predictable and reproducible environment, free from side effects caused by previous tests, host-level conditions, or VM states. No persistent data is shared between executions, and the guest environment is intentionally stripped down. No background daemons, user services, or external dependencies exist inside the VM unless explicitly configured by the user.

The overall execution flow proceeds as follows: the user on the physical host sends a test request to the Flask server via an HTTP request. Inside the guest system, a listener process continuously waits for such requests. When a test arrives, the listener prepares the environment by building a Docker image using the specified Dockerfile and launches a container with the defined user-defined Docker configuration. These include, but are not limited to, Linux capabilities, namespace settings, seccomp profiles, AppArmor rules, volume mounts, and user privileges. The container is then launched with this configuration. Once the container is running, the trick script is automatically executed. During the tricks execution, any stdout is sent back to the physical host. This may include the results of the trick (whether it passed or failed), or more information at the tester's discretion. On the host, the result is logged in a \texttt{.log} file.

\DIFaddend \section{Reproducibility}

A central design goal of Houdini is to ensure that container security tests are reproducible, meaning that the same test, when run under the same conditions, will produce identical results regardless of when or where it is executed. Houdini achieves reproducibility through a combination of strict version control and isolation from external influences.

Each test in Houdini runs inside a new VM that is freshly booted from a Buildroot-based image. This means that every test starts in a clean environment, with no leftover data or settings from previous runs. As soon as a test finishes, the VM is thrown away, so nothing carries over into the next test. This helps make sure that results are consistent and not affected by what happened before.

The Buildroot image is very minimal; it only includes what's absolutely needed to run the test. By keeping things simple and stripped down, Houdini ensures that the only things running in the VM are the ones the user specifically added for the test. This clean and predictable setup makes it much easier to get the same results every time a test is run. Even if a trick is repeated many times or on different machines, the outcome stays consistent because the environment is always the same.

To avoid changes caused by updates or host system drift, Houdini uses a version pinning mechanism. Version pinning refers to the practice of explicitly specifying and using fixed versions of software components rather than relying on the latest or system-default versions. This ensures that tests always use the same binaries, regardless of when or where they are run, and prevents unexpected changes in behavior due to automatic updates or upstream changes. In the context of container security testing, version pinning is essential because even minor updates to Docker, runtimes, or the kernel can introduce subtle behavioral differences.

Each test in Houdini explicitly declares the versions of Docker, runc, and the Linux kernel to be used in a configuration file (~\ref{fig:version-pinning-configuration-implementation}). These components are downloaded from official release sources, precompiled, and stored in a local directory. This guarantees that the same binaries are reused across repeated runs. For example, if a trick is intended to evaluate a vulnerability in runc 1.0.0-rc2 but verify its resolution in 1.1.12, Houdini retrieves the exact binaries for each version and uses them directly, without relying on system package managers. Similarly, multiple Docker versions such as 20.10.3, 23.0.1, or 27.0.3 can be tested against the same logic to study behavioral drift. Behavioral drift refers to how the behavior of container runtimes and their enforcement of security mechanisms changes subtly across versions, even when the same configuration is applied.


\section{Scalability}

Houdini is built to support large-scale container security evaluations without requiring extensive manual effort or scripting. While each test is executed serially to maintain isolation, the overall framework is designed to scale efficiently across hundreds or thousands of test configurations. \DIFaddbegin \DIFadd{In this context, scalability refers to the ability to define and execute a larger number of diverse tricks, rather than running a larger number of containers in parallel.
}\DIFaddend 

At the core of Houdini's scalability is its matrix-based testing model. Instead of manually defining each test case, users specify sets of options, such as Docker flags, Linux capabilities, namespace settings, or user identities that they want to explore. Houdini then automatically generates the Cartesian product of these options, producing a comprehensive list of test cases. This allows for systematic evaluation of all meaningful combinations without the need for custom scripts or duplicated logic.

To efficiently manage large volumes of tests, Houdini avoids rebuilding the entire environment for every test case. Instead, it reuses a lightweight VM image generated by Buildroot, which serves as a clean, consistent base system. On top of this base, Houdini applies only the test-specific components, such as Docker binaries and runc binaries, Docker files, trick scripts, and configuration files, using an overlay filesystem. This layered approach allows each test to run in isolation without duplicating the entire filesystem. As a result, test execution is significantly faster and consumes fewer system resources, enabling Houdini to scale gracefully to hundreds or even thousands of tests. 

When you change the Docker version in the configuration file, Houdini updates the overlay filesystem by placing the new Docker binary and related files into it. During the Buildroot process, this overlay is then copied into the final root filesystem image. This means the new Docker version will be available inside the VM without having to rebuild everything from scratch. Only the updated overlay contents are refreshed, making the process much faster and more efficient. The entire root filesystem does not need to be rebuilt.


\section{Host Isolation}

Houdini is explicitly designed to safely execute potentially dangerous or privilege-escalating container workloads without risking the security or stability of the host system. This is achieved through strict isolation enforced by running all tests inside a QEMU-based VM. This approach ensures strong separation between the test environment and the host, providing both safety and reproducibility.

Each trick is executed within its own QEMU VM, which serves as a hardware-level isolation boundary. Unlike approaches that rely solely on Linux container isolation, this VM-level sandbox guarantees that even if a container successfully escapes its sandbox, it remains confined to the guest environment. No test payload can reach or affect the host OS, making Houdini suitable for executing untrusted or potentially malicious code safely.

Houdini further avoids any direct linkage between the host and the guest environment because no host directories are mounted into the guest, and no namespaces are shared between the host and the VM. Containers are launched entirely within the guest's user, mount, PID, and network namespaces. As a result, containers inside the VM have no visibility into host processes, filesystems, or resources. Flags such as \texttt{--pid=host} only apply within the VM context and never expose the physical host-level information.

Houdini's reliance on QEMU offers several key advantages over alternative virtualization platforms such as VMware or VirtualBox. First, QEMU supports both full system emulation and hardware-assisted virtualization through KVM, allowing it to run unmodified Linux kernels and minimalist userland environments generated by Buildroot. It can boot directly from a raw kernel image (e.g., \texttt{bzImage}) without requiring a bootloader or full OS, enabling precise control over the testing environment.

Second, QEMU supports complete command-line configuration, including CPU model, memory size, disk images, network interfaces, and serial ports. This makes it ideal for automated and reproducible test workflows. In contrast, VMware and VirtualBox rely on graphical interfaces and more static configurations, which hinder automation and scripting.

Third, QEMU is architecture-agnostic. It supports x86, ARM, MIPS, RISC-V, and other architectures, allowing for cross-platform testing. While Houdini currently focuses on x86\_64, the use of QEMU ensures that it can easily be extended to other architectures in the future. VMware and VirtualBox are limited to x86-based virtualization and do not support complete system emulation for different CPU architectures.

\section{Flexibility Across Configurations}

One of the ways Houdini stays flexible is by letting you easily change the versions of Docker, the container runtime (like runc or crun), and the Linux kernel using a single configuration file (see~\ref{fig:version-pinning-configuration-implementation}). Instead of hardcoding these versions into the system, Houdini treats them as settings you can adjust anytime. This means you can run the same container test across different versions just by changing a few values. For example, you could try Docker 19.03 with runc 1.0 and Linux 5.10, then switch to Docker 27.0 with runc 1.1.10 and Linux 6.5 without rewriting the test. This makes it easy to compare how behavior or security enforcement changes over time, and helps you catch issues caused by version differences.

Another important source of flexibility in Houdini is the use of a modular trick configuration file, which allows users to define the parameters, constraints, and behavior of each container-based test in a clean and extensible format (see~\ref{fig:configuration-implementation}). Each trick is composed of a lightweight configuration file that is written in a YAML-like structure that specifies runtime settings such as container flags (e.g., --cap-drop, --privileged, --pid=host), AppArmor or seccomp profiles, environment variables, mount points, user settings, and resource limits. By abstracting these details from the underlying execution logic, Houdini enables the same trick to be reused across different test scenarios simply by adjusting configuration values.

\section{Debuggability}

Each test execution generates a structured log file that includes the container's standard output and a timestamped record of the Docker configuration parameters used. These logs are stored in a standardized format and organized by test ID, where the format of the ID is \texttt{TRICK_NAME_DOCKER_VERSION_KERNEL_VERSION}, making it straightforward to trace the origin of any result.

To ensure debuggability, Houdini encourages each trick implementer to document the outcome of their test explicitly. While Houdini automates the environment setup and orchestrates trick execution, the framework delegates the responsibility of interpreting and reporting the results of each trick to the implementer. This is to be done within the trick script itself, which may include logic to determine whether a confinement boundary was bypassed, a capability was misused, or a system call succeeded unexpectedly.

Implementers are expected to encode result-handling logic directly into the trick, for example, by printing structured output such as \texttt{SUCCESS}, \texttt{FAILURE}, or specific diagnostic information that summarizes what occurred. This approach ensures that each trick captures the semantic meaning of its test: whether it was trying to escape a namespace, probe a kernel feature, or test permission enforcement. In more complex cases, the implementer may provide logs, exit codes, or structured JSON output to communicate results back to the host.

The design to delegate result interpretation to the trick author supports greater flexibility across test types and avoids making assumptions about what success or failure means in a given security context. It also allows Houdini to remain agnostic to the internal logic of the trick while still collecting meaningful and comparable results across many configurations. 

\section{Example Applications of Houdini}
A system like Houdini can be used in the following ways: 

\noindent\textbf{Identify gaps between intended confinement policies and actual enforcement:}
There is often a discrepancy between the security policies that administrators intend to enforce and what is actually upheld at runtime. These discrepancies generally fall into two categories: implicit policy problems and conflicting policy configurations.

An implicit policy problem happens when an administrator doesn't explicitly set a security rule, and the system's default behavior is used instead. These defaults might lead to behavior the administrator did not expect. For example, Docker containers are, by default, connected to a shared internal bridge network. While this topology typically prevents internet access, it still allows containers to communicate with each other. An administrator might see that outbound traffic from a container is blocked and mistakenly believe the container is fully isolated from different networks. However, internal communication between containers will still be allowed unless it's explicitly disabled. Thus, this default behavior can create a false sense of security and introduce unexpected risks.

A conflicting policy configuration, on the other hand, occurs when a security policy is correctly specified but is later invalidated by other conflicting configurations. For example, an administrator might launch a container with \texttt{--network=none}, expecting it to be fully isolated from all network communication. However, if the container is also inadvertently given elevated privileges such as \texttt{--cap-add=NET\_ADMIN} or \texttt{--privileged}, it can reconfigure its own network interfaces and regain connectivity. With the \texttt{NET\_ADMIN} capability, processes inside the container gain access to low-level networking operations, such as creating virtual interfaces, assigning IP addresses, or modifying routing tables. A process could use commands like \texttt{ip link set eth0 up} and \texttt{dhclient eth0} to bring up a previously disabled interface and request an IP address from the host's network. In the case of a \texttt{--privileged} container, even more capabilities are granted, allowing near-complete access to the host's kernel features, including the creation of new network namespaces or interfaces, effectively bypassing the isolation intended by \texttt{--network=none}.

\noindent\textbf{Challenge misleading security assumptions with empirical testing:}
Container security is often discussed in terms of theoretical guarantees, with many security best practices based on assumptions rather than direct testing. For instance, documentation may state that a container running in unprivileged mode cannot escalate to root, but Houdini actively tests whether that is actually the case under different container configurations. By running real-world security validation instead of relying solely on security claims, Houdini helps challenge misleading assumptions and exposes where security mechanisms fail in practice. This is particularly important as container escapes and privilege escalation exploits continue to emerge, demonstrating that security controls do not always work as expected. By grounding security claims in measurable results rather than theory, Houdini helps researchers and practitioners develop more robust container security strategies.

\noindent\textbf{Detect security drift over time:} One of the challenges in maintaining secure containerized environments is configuration drift. Security settings applied during container initialization may be inadvertently changed through image updates, runtime automation, or infrastructure changes. Houdini can be set up to periodically re-evaluate security policies, making it possible to detect when the system diverges from its initially intended security posture. This allows for the timely remediation of regressions that could otherwise go unnoticed. Configuration drift does not only arise from explicit policy changes, but also from underlying updates to system components such as the Linux kernel, Docker, or runc. Even when container configurations and security policies remain unchanged, an upgrade to the kernel or container runtime can subtly alter the enforcement of isolation primitives, security defaults, or available capabilities. For example, a new kernel version may modify the behavior of namespaces, cgroups, or seccomp filters; a Docker update may introduce new features or alter default permissions. See \ref{sec:evaluating-ptrace-enforcement-across-linux-distributions} for an example of this.

\section{Building a VM via Buildroot}


Buildroot is an open-source tool that automates the process of building custom Linux systems, primarily for embedded or minimal environments. It simplifies the creation of a complete Linux distribution by compiling the Linux kernel, root filesystem, bootloader (if needed), and a wide range of userland tools from source. Users define their system configuration through a menu-driven interface or configuration files, specifying which components to include, which versions to use, and how the resulting image should be structured. Because it builds everything from scratch using version-pinned sources, Buildroot is ideal for producing highly reproducible and minimal Linux environments. In the context of Houdini, Buildroot enables precise control over the guest VM, ensuring that all kernel features and userland components required for container security testing are present, consistent, and isolated from host system variability.

The Buildroot construction pipeline (see~\ref{fig:buildroot_construction}) is a sequential process that transforms high-level system specifications into a bootable Linux image. It begins with a configuration phase, where users define the system's architecture, target packages, kernel version, and root filesystem type using a `.defconfig` file or the menuconfig interface. Once configured, Buildroot fetches all required source code, including the Linux kernel, toolchains, and any selected userland packages, and applies patches if specified. These sources are then compiled from scratch using a cross-compilation toolchain that Buildroot generates specifically for the target architecture. As part of this process, the root filesystem is assembled by installing all compiled binaries and scripts into a staged directory. 


To enable container runtime support in a virtualized environment, Houdini must activate several groups of kernel features beyond just namespaces and cgroups. One such group includes networking and virtualization options, which are essential for simulating realistic container deployments. Enabling kernel options like \textit{CONFIG\_VETH}, \textit{CONFIG\_BRIDGE}, \textit{CONFIG\_MACVLAN}, and \textit{CONFIG\_VXLAN} allows containers within the guest VM to create and use virtual Ethernet devices, participate in bridged networks, and simulate more complex network topologies. These features are critical when testing container isolation at the network layer or evaluating capabilities such as port forwarding, network namespaces, or virtual NICs. Similarly, \textit{CONFIG\_NETFILTER}, \textit{CONFIG\_NF\_NAT}, and related options enable firewall rules, NAT, and packet filtering within containers, capabilities that many real-world container setups rely on and which are required to run Docker's iptables-based networking stack.

In addition to networking, Houdini must support advanced filesystem operations that are frequently used by container runtimes. Docker relies heavily on layered filesystems to manage images and containers. To this end, enabling \textit{CONFIG\_OVERLAY\_FS} allows the use of OverlayFS, the default storage driver for Docker. \textit{CONFIG\_BTRFS\_FS} is included to support setups using Btrfs as an alternative union filesystem with snapshotting features. Additionally, \textit{CONFIG\_EXT2\_FS} ensures basic compatibility for traditional disk images used in Houdini's root filesystem. Without these filesystems enabled, many containers would fail to start due to missing storage backend support.

Another critical group of options revolves around virtual I/O and hypervisor support, which is essential in QEMU-based virtual machines. Enabling \textit{CONFIG\_VIRTIO\_NET}, \textit{CONFIG\_VIRTIO\_BLK}, and \textit{CONFIG\_VIRTIO\_PCI} allows the guest VM to communicate efficiently with the host through QEMU's paravirtualized drivers. These options improve I/O performance, reduce emulation overhead, and ensure compatibility with typical QEMU virtual hardware. Without these, the guest VM may fail to boot correctly or experience degraded performance, especially during heavy I/O operations such as pulling container images or writing logs.

Finally, several security and cryptographic features are enabled to mirror real-world deployments and ensure complete runtime functionality. These include \textit{CONFIG\_SECCOMP} and \textit{CONFIG\_SECCOMP\_FILTER} for syscall filtering, \textit{CONFIG\_SECURITY\_APPARMOR} for enforcing AppArmor profiles, and cryptographic primitives like \textit{CONFIG\_CRYPTO\_GCM}, \textit{CONFIG\_CRYPTO\_SEQIV}, and \textit{CONFIG\_CRYPTO\_GHASH}. Docker and runc depend on these options to enforce container restrictions and protect against kernel-level attacks. Without them, security policies such as seccomp profiles or AppArmor confinement would silently fail, leading to inaccurate or incomplete test results.

By carefully assembling this kernel configuration, Houdini ensures that every kernel compiled through Buildroot is not only compatible with Docker and `runc`, but also remains minimal, reproducible, and isolated from host system dependencies. This tailored defconfig plays a critical role in enabling full container runtime functionality inside the guest while preserving the deterministic nature of the testbed.

A key feature of Houdini's Buildroot-based design is its use of the overlay filesystem mechanism. Buildroot allows users to inject arbitrary files into the target root filesystem through an overlay directory. Houdini takes advantage of this by maintaining a structured overlay that contains all required runtime components, custom configuration files, and initialization scripts. For example, the overlay includes statically compiled versions of Docker Engine, `runc` for each version being tested. These binaries are placed in appropriate locations such as `/usr/bin`, ensuring they are accessible at runtime within the VM without requiring package installation or network access within the guest. While Buildroot includes official packages for Docker and `runc`, Houdini deliberately avoids using them. This decision stems from the fact that many older versions of Docker and `runc` (which are critical for longitudinal security analysis) are no longer supported or even buildable within the current Buildroot ecosystem. Buildroot frequently removes or breaks compatibility with older software versions due to upstream changes, deprecated dependencies, or toolchain incompatibilities. As a result, attempting to evaluate historical versions of container runtimes using Buildroot's native package management would lead to build failures. By embedding all required components directly into the root filesystem at build time, Houdini avoids reliance on dynamic installation, networking, or user intervention. The overlay mechanism not only simplifies the build process but also strengthens reproducibility and isolation, which are key pillars of Houdini's design.

In addition to binaries, the overlay contains service definitions and startup scripts that initialize the environment when the VM boots. One critical element is the embedded Python Flask server, which runs automatically inside the guest and listens for incoming test instructions from the host. This server enables Houdini to remotely execute "tricks" from the physical host to the VM. Configuration files, test logic, and Docker files are also placed into the overlay, ensuring they are bundled directly into the root filesystem without external dependencies.

The final output of the Buildroot construction pipeline consists of a complete, bootable Linux system tailored for container security testing. Specifically, Buildroot produces two critical artifacts: a compressed Linux kernel image (`bzImage`) and a root filesystem image (e.g., `rootfs.ext2`). The `bzImage` contains the monolithic kernel with all necessary container-related features enabled, including namespaces, cgroups, AppArmor, and virtual I/O drivers. The `rootfs.ext2` image is a minimal Linux environment populated with userland tools such as BusyBox, Python 3, the embedded Flask API server, and pre-injected container runtimes like Docker and `runc`, along with all relevant test scripts and configuration files. These outputs are stored under the `output/images/` directory within the Buildroot tree and are used directly by Houdini to boot a virtual machine via QEMU. Together, they form a fully isolated and reproducible guest environment, allowing for deterministic execution of container-based tricks and security tests, independent of the host system's configuration.

\section{YAML-Like Trick Definition}
\label{sec:yaml-trick}

Houdini supports two modes for defining and executing tricks. The first is a YAML-like approach where a single trick is fully specified through a standalone configuration file (see~\ref{fig:version-pinning-configuration-implementation}). This method is ideal for running individual tests with carefully controlled settings, making it well-suited for targeted investigations of container confinement. The second mode is a Python-based approach that allows users to define parameter sets as lists, which Houdini expands into a Cartesian product to form a complete test matrix. For example, Docker configuration parameters can be defined in Python, and Houdini will automatically generate all combinations to be tested.

The YAML-like Trick definition is one of two ways to define a trick in Houdini. In this section, we will go through the implementation of it and provide examples of its use.

Each trick in Houdini is composed of three modular components that work together to define and execute a container-based security test: a configuration file, a trick script, and a Dockerfile. The configuration file (see~\ref{sec:configuration}) is a YAML-like document that specifies the Docker parameters for launching the container, including security-related settings such as Linux capabilities, namespace modes, AppArmor profiles, user privileges, and resource limits. These parameters are parsed by Houdini and translated directly into Docker's Python SDK, ensuring that containers are created with precise and repeatable configurations.

The second component is the trick file (see~\ref{sec:trick_file}), which contains the logic of the test and is executed inside the container. It is typically written in Python or Bash. This script attempts a specific action, such as reading a sensitive file, sending a signal to a process, or escalating privileges, and reports the outcome by printing a success or failure message, or however your implementation wishes to output it. The semantics of what constitutes a pass or fail are entirely defined by the script, giving users complete control over the evaluation criteria.

The final component is the Dockerfile, which builds the container image and defines the runtime environment. It includes instructions for copying the trick file into the container by using the \textit{COPY} instruction/directive. We also use the Dockerfile to install any necessary dependencies, and specify the base image to use.

Next, we will explain each of these files in more detail.

\subsection{Configuration File}
\label{sec:configuration}

Each Houdini trick begins with a configuration file, written in YAML-like format, that defines the runtime parameters used to launch the container. This file acts as the Docker command for how the container is constructed and executed. It specifies a range of Docker options including Linux capabilities (via \texttt{cap\_add} and \texttt{cap\_drop}), namespace settings (such as \texttt{pid\_mode} and \texttt{userns\_mode}), resource limits (e.g., \texttt{cpu\_shares}, \texttt{mem\_limit}), volume mounts, user identity, and security options such as AppArmor profiles or seccomp settings. See~\ref{fig:configuration-file} for an example.

The configuration is declarative and follows a structured YAML-like schema that maps directly to Docker's Python SDK API. For example, if a user wants to disable privilege escalation, enable a read-only filesystem, or run the container as a non-root user with dropped capabilities, these settings can be encoded clearly in the configuration file by giving it a simple \textit/t{True} or \textit{False} value. This abstraction allows users to focus on the security scenario being tested without needing to handcraft long and error-prone Docker command-line arguments.

When Houdini executes a test, the CLI parses the YAML-like configuration and validates it before test execution begins. It checks for required fields, ensures that runtime versions and trick paths are valid, and performs consistency checks to catch errors like incompatible or conflicting flags. Once validated, the configuration is sent to the trick listener and translated into a Docker run command within the guest environment. 

The configuration file is parsed using the parse\_trick\_and\_run() function (see~\ref{fig:configuration-implementation}). This function serves as the entry point for executing a trick. This function begins by extracting the container name from the provided arguments and then checks if a container with the same name already exists on the system. If so, it terminates and removes the existing container to ensure a clean test environment and guarantee reproducibility.

\subsection{Trick File}
\label{sec:trick_file}

The trick script is the core component that defines the actual test logic to be executed inside the container. This script is typically written in a high-level language such as Python or Bash and is copied into the container during the build process specified by the Dockerfile. But, first, it is copied into the VM using a custom overlay filesystem script. Once the container is launched with the desired configuration, the trick script runs automatically and attempts a specific action, such as reading a sensitive file, accessing a kernel interface, or interacting with another process. Its purpose is the discretion of the implementer of the trick file.

Houdini does not impose restrictions on the scripting language used, though Python and Bash are most commonly employed due to their simplicity and compatibility with minimal container environments. The scripting interface is straightforward: the script performs a predefined action and prints a result indicating whether the trick passed or failed. These results are captured via standard output by the trick listener running inside the guest VM. The listener uses these outputs, along with exit codes, to classify the outcome of the test.

The evaluation criteria are entirely defined within the trick script, giving users complete control over what constitutes success or failure. This flexibility allows Houdini to support a wide range of test types, from low-level privilege checks to higher-level behavioral verifications. Scripts can also emit additional diagnostic messages to aid in debugging or deeper analysis to \textit{STDOUT}.

Below is an example of a simple Python trick script that tests whether the container can read the contents of the \texttt{/etc/shadow} file. Under standard Docker security settings, access to this file should be restricted. If the script is able to read it, the trick is considered to have failed, indicating a misconfiguration or insufficient isolation. Otherwise, it passes.

import os

def check_shadow_access():
    path = "/etc/shadow"
    if os.path.exists(path):
        try:
            with open(path, 'r') as f:
                print("Able to read /etc/shadow:")
                print("Trick passed")
        except PermissionError:
            print("Permission denied to read /etc/shadow.")
            print("Trick failed")
        except Exception as e:
            print(f"Unexpected error: {e}")
            print("Trick failed")
    else:
        print("/etc/shadow does not exist.")
        print("Trick failed")

check_shadow_access()
\end{lstlisting}
\end{figure}


This example demonstrates how a trick can evaluate a specific security assumption, file access control in this case, and produce a deterministic result that Houdini can log and interpret. More advanced tricks may incorporate conditionals, environment checks, or IPC mechanisms, but the basic structure remains the same: run a check and report a pass/fail outcome in a transparent and reproducible manner.



\subsection{Dockerfile}

The Dockerfile is responsible for setting up the container's runtime environment so that the trick script can execute reliably and with all necessary dependencies. It defines how the container image is built, including the selection of a base image, the installation of packages or libraries required by the trick script, and the inclusion of the trick file itself.

Tricks in Houdini can be written in a variety of languages, such as Python or Bash, so the Dockerfile must ensure that the corresponding runtime (e.g., the Python interpreter or Bash shell) is available inside the container. This often involves installing system packages using the package manager provided by the base image, for example, using \texttt{apt} in Debian-based images or \texttt{apk} in Alpine.

Another essential part of the Dockerfile is copying the trick script into the container's filesystem. This step ensures that the logic defined by the user is available at a known path when the container starts. Houdini standardizes this by copying the trick to a predefined directory (e.g., \texttt{/houdini/trick.py}) so that all containers follow the same execution convention.

The base image is selected based on the needs of the trick. Lightweight images like Alpine Linux are often preferred for simple tests because of their small size and fast startup time. However, more feature-rich images like Debian or Python-based official images may be used when additional dependencies or language runtimes are required.

Finally, the Dockerfile specifies an entrypoint or \texttt{CMD} directive to automatically run the trick script when the container launches. This ensures that the trick executes without requiring user intervention or manual commands. The entrypoint is usually a direct call to the interpreter (e.g., \texttt{python3 /houdini/trick.py}).

The example in~\ref{fig:dockerfile-example} demonstrates a simple Dockerfile used in Houdini to run a Python-based trick. It uses the official Python image, copies the trick from the VM to the container, and sets the default command to execute the script.

\section{Python-Based Expansion Definition}

In addition to supporting single-trick YAML-like definitions, Houdini provides a Python-based mechanism to define a matrix of configurations by specifying Docker configuration parameters as lists. Houdini automatically expands these parameters into a Cartesian product and generates a full suite of test cases. This approach is powerful for scaling up experiments, allowing researchers to explore the interaction of various container runtime settings systematically.

\begin{lstlisting}[language=bash, caption={Trick parameter sets defined in Python}, label={lst:apparmor-trick}, numbers=left, numberstyle=\tiny, stepnumber=1, breaklines=true, frame=single, backgroundcolor=\color{gray!10}, basicstyle=\ttfamily\footnotesize, showspaces=false, showstringspaces=false]

\section{Flask Server}

The Flask server plays a central role in Houdini's architecture by acting as the primary communication bridge between the physical host system and the guest VM. Once the QEMU-based VM boots, it establishes a connection to this Flask server to initiate trick execution. The server runs as a lightweight HTTP service on the host, exposing a set of well-defined endpoints that orchestrate the full test workflow. The Flask server is automatically started with the help of a BusyBox init script (see~\ref{lst:start-flask-server}).

\begin{lstlisting}[language=python, caption={BusyBox init file that starts the Flask server}, label={lst:start-flask-server}, numbers=left, numberstyle=\tiny, stepnumber=1, breaklines=true, frame=single, backgroundcolor=\color{gray!10}, basicstyle=\ttfamily\footnotesize, showspaces=false, showstringspaces=false]
#!/bin/sh
# Description: Example service script

PATH=/sbin:/bin:/usr/sbin:/usr/bin:/usr/local/bin
DAEMON=/usr/bin/python3
DAEMON_ARGS="/houdini/server.py"
PIDFILE=/var/run/houdini-server.pid
LOGFILE=/var/log/houdini-server.log

case "$1" in
    start)
        echo "Starting my service..."
        $DAEMON $DAEMON_ARGS >> $LOGFILE 2>&1 &
        ;;
    stop)
        echo "Stopping houdini-server..."
        kill $(cat $PIDFILE)
        ;;
    restart)
        echo "Restarting houdini-server..."
        $0 stop
        sleep 1
        $0 start
        ;;
    *)
        echo "Usage: $0 {start|stop|restart}"
        exit 1
        ;;
esac

exit 0
\end{lstlisting}

The core endpoints exposed by the server are \texttt{/server-status}, \texttt{/version-status}, \texttt{/run-trick}, and \texttt{/run-command-in-vm}. The \texttt{/server-status} endpoint is used for health checking and indicates whether the Houdini server is actively running on the host. This enpoint uses the subprocess module to check whether a specific process is running on the system. It executes the \textit{pgrep -f <service\_name>} command, which searches for all currently running processes whose full command lines match the given service name. In our case, the servie name is \textit{/usr/bin/python3 /houdini/server.py}. The stdout=subprocess.PIPE option captures the output (i.e., the matching process IDs), allowing the script to access the result programmatically. The check=True flag ensures that if no matching process is found, the command will raise a subprocess.CalledProcessError, which can be used to detect and handle the case where the service is not running.

\section{Trick Execution}

The execution of a trick in Houdini begins with the activation of a VM by using the \textit{./houdini --start\_vm}. See ~\ref{lst:start-vm} for the full QEMU command used to activate the VM.

\begin{lstlisting}[language=python, caption={Python method to start the QEMU VM in Houdini}, label={lst:start-vm}, numbers=left, numberstyle=\tiny, stepnumber=1, breaklines=true, frame=single, backgroundcolor=\color{gray!10}, basicstyle=\ttfamily\footnotesize, showspaces=false, showstringspaces=false]
def start_vm(self, kernel=get_absolute_path(f"/kernels/{KERNEL_VERSION}/arch/x86/boot/bzImage"), drive=get_absolute_path("/buildroot/output/images/rootfs.ext2")):
qemu_cmd = [
"qemu-system-x86_64",
"-smp", str(CPU_CORES),
"-m", str(VM_RAM),
"-kernel", kernel,
"-drive", f"file={drive},if=virtio,format=raw",
"-append", "apparmor=1 security=apparmor rootwait root=/dev/vda console=tty1 console=ttyS0 loglevel=0 cgroup_enable=cpuset cgroup_enable=memory",
"-serial", "mon:stdio",
"-net", "nic,model=virtio",
"-net", f"user,hostfwd=tcp::{PORT}-:{PORT}",
"-nographic",
"-virtfs", "local,path=/home/huzi/Desktop,mount_tag=hostshare,security_model=mapped-file,id=hostshare"
]
\end{lstlisting}

The following options in the QEMU command are critical to Houdini's testing workflow:

\begin{itemize}
\item \texttt{-kernel}: Loads a specific Linux kernel, enabling experiments across kernel versions or with custom patches.
\item \texttt{-drive if=virtio}: Uses a virtio-backed root filesystem for fast disk access and compatibility with Buildroot images.
\item \texttt{-append}: Passes kernel boot parameters, including enabling AppArmor and cgroups for isolation enforcement.
\item \texttt{-serial mon:stdio}: Routes guest output to the host terminal for logging and debugging.
\item \texttt{-nographic}: Disables the graphical interface to simplify deployment and speed up boot time.
\item \texttt{-virtfs}: Mounts a host folder into the VM using Plan 9 FS, useful for accessing logs or artifacts.
\item \texttt{-net nic} and \texttt{-net user,hostfwd}: Sets up a virtual NIC and forwards a TCP port for communication between the host and guest (e.g., for Flask server requests).
\end{itemize}

During booting, the guest VM automatically connects to a lightweight Flask server running on the host with the help of a BusyBox init script. This server acts as the communication bridge between the physical host and the guest environment. In other words, it exposes a simple HTTP API for transferring configuration data and receiving test results.

Following this, the execution of a Houdini trick begins on the physical host system, where the user selects a trick to run via a Bash terminal. For example, to run a trick, a user would enter \textit{./houdini --runtrick example\_trick}. Houdini's Flask server parses this command, verifies its correctness, and prepares the test case for execution. Validation includes checking that the required trick file, configuration file, and Dockerfile exist for that particular trick (in this case \textit{example\_trick}).

Following a successful validation of running the command \textit{./houdini --runtrick example\_trick}, the Flask server calls a function to execute the Docker container with the given configuration. It begins by building the Docker image using the provided Dockerfile, copying the trick script into the container, and applying all specified configurations provided by the configuration file (see \~ref{fig:running-a-docker-container-implementation}).

Following this, the trick file runs automatically inside the container, performing its test logic and writing its output to standard output. The trick listener monitors the container's execution, capturing the exit code, output, and any diagnostic messages produced by the trick. These results are packaged together and returned to the host via the Flask server.

On the host side, Houdini stores all test results in structured logs indexed by test ID. This log includes the whole configuration, trick output, and container exit status, making it easy to trace, compare, and debug results. The entire pipeline from configuration parsing to result capture is designed to run without manual intervention, which enables users to queue and evaluate large sets of tests in a reliable and repeatable manner.

\section{Reproducibility Over Time with Version Pinning}

This experiment evaluates Houdini’s ability to reliably reproduce test results over time using a version-pinned container environment. The purpose of this experiment is to determine whether Houdini can serve as a reliable testing framework when executed repeatedly over time under controlled, version-pinned conditions. Version pinning refers to explicitly locking the versions of software components, such as Docker, runc, and the Linux kernel, to prevent variation due to automatic updates, rebuilds, or environmental drift. The AppArmor detection trick (see Listing~\ref{lst:apparmor-trick}) is used to check if the container is running with AppArmor security enabled, specifically under the `docker-default` profile. It’s a simple and effective way to see if Linux’s AppArmor is active inside the container. If the profile includes `docker-default`, the trick passes, meaning AppArmor is working correctly. If the profile is missing or different, the trick fails, which could mean that AppArmor is turned off or not supported. This trick helps identify whether the container's security setup has changed across different Docker versions, kernel versions, or system settings.

The \texttt{apparmor\_check.sh} script is placed in \texttt{/usr/bin/} and included via the overlay. Its purpose is to detect whether Docker applies AppArmor confinement, which varies by Docker version. The script attempts to write to /proc/sys/kernel/randomize\_va\_space, a location typically blocked by the default AppArmor profile.

\begin{lstlisting}[language=bash, caption={AppArmor Enforcement Trick Script}, label={lst:apparmor-trick}, numbers=left, numberstyle=\tiny, stepnumber=1, breaklines=true, frame=single, backgroundcolor=\color{gray!10}, basicstyle=\ttfamily\footnotesize, showspaces=false, showstringspaces=false]
#!/bin/sh

if [ $? -eq 0 ]; then

else

fi
\end{lstlisting}

This trick is sensitive to Docker version behavior. Older Docker versions may not apply AppArmor profiles by default, resulting in successful writes and a failed trick. In contrast, modern versions typically enforce the \texttt{docker-default} profile, causing the trick to pass.

One potential concern in cross-machine testing is that physical host-level kernel settings, such as security modules, sysctl values, or namespace policies, could leak into or interfere with the VM and affect test behavior. For example, Linux’s Yama security module controls ptrace restrictions via the ptrace\_scope sysctl, which varies across distributions. On a typical Ubuntu host, ptrace\_scope may default to 1 (restricted), while hardened environments might use 2 or 3, disallowing debugging even with capabilities.

However, Houdini’s design explicitly mitigates this threat. All tests are executed inside a QEMU VM that runs its own Linux kernel, fully isolated from the host. Host kernel modules like Yama are not visible or inherited by the guest kernel. This means even if Machine A has ptrace\_scope=3 and Machine B uses the default 1, the VM loaded into Machine A will behave identically as the VM in Machine B. More generally, no physical host-level AppArmor profiles, SELinux settings, or LSM configurations apply inside the VM. Even sysctl values, such as those affecting networking, file descriptor limits, or namespaces, are isolated to the VM’s kernel and cannot be influenced by the physical host. As a result, machine-specific hardening policies do not affect the determinism of trick execution.

This design choice is central to Houdini’s reproducibility goal: by treating the guest VM as a sealed, deterministic black box, it ensures that only explicitly configured inputs like Docker version, kernel version, runc version, and trick code affect the outcome.
































\section{Host Isolation Validation}

This experiment is designed as an informal security evaluation rather than a rigorous formal verification. Its goal is not to prove beyond all possible doubt that VM escape vulnerabilities are absent. Instead, the aim is to provide practical evidence that, under typical conditions, Houdini’s architecture does not expose any clear or unintended paths through which a containerized workload could influence or compromise the physical host.

To assess this, we use a controlled test: a container attempts to write to a file path that would typically point to a host-mounted directory, if such sharing were accidentally enabled. This simulated path acts as a canary, alerting us to any misconfigurations or unexpected leakages, such as shared folders or improperly scoped namespaces, that could break the intended isolation. If the container is able to write to this location, it would indicate a breach in the containment model.

While this approach cannot detect deeper issues such as hypervisor vulnerabilities, low-level device exploits, or side-channel attacks, it is well-suited for detecting more common and operational misconfigurations. In real-world scenarios, these kinds of setup errors are often the cause of unintended host exposure. Thus, this method offers a practical way to confirm that Houdini’s default setup maintains strong separation between the host and guest environments.

A full formal security analysis, including techniques like fuzzing, symbolic execution, or hypervisor introspection, would provide deeper coverage but is out of scope for this specific evaluation.

We designed a trick (see Listing~\ref{lst:escape-trick}) to evaluate whether a container running inside Houdini's VM can access the physical host system. This test simulates an escape attempt by trying to write to a file path that would typically point to a shared folder if one were configured.

While shared folders are a common method for transferring files between a VM and its physical host, their use inherently weakens the isolation boundary. If a container within the VM has access to a host-mounted directory, it may write or overwrite files that become visible outside the VM. This creates a deliberate escape route that must be managed with caution.

However, Houdini avoids this problem entirely by not relying on shared folders for interprocess communication or result reporting of tricks. As mentioned prior, this is because Houdini uses a lightweight Flask-based HTTP server running on the host. When a trick completes execution inside the VM, it sends its result, such as pass/fail status or diagnostic output back to the host via an HTTP POST request over a user-mode QEMU network port.

This design has several advantages:
\begin{itemize}
    \item It eliminates the need to mount any part of the host filesystem inside the VM.
    \item It decouples file I/O from test reporting, reducing the attack surface.
    \item It enables fine-grained control over what data leaves the VM and how it is structured.
\end{itemize}


This experiment confirms that Houdini provides strong host isolation by default. Malicious trick code that attempts to write to host-accessible paths is safely confined within the VM. The inclusion of a clearly defined threat model ensures that the assumptions and limits of containment are well-scoped. Furthermore, the use of a Flask-based communication channel, rather than shared folders, enhances isolation by avoiding any direct file-based interaction between the guest and host. Overall, Houdini’s VM-based architecture, combined with controlled, network-based result reporting, offers a secure foundation for container security testing.


\subsection{Threat Model}

The threat model for this evaluation assumes that the attacker has full control over arbitrary code executed inside a container running within the VM. This reflects a realistic scenario where untrusted or potentially malicious container workloads are tested to evaluate security boundaries. The attacker may attempt to exploit kernel vulnerabilities, access unintended resources, or perform file system operations that target the host. Typical actions include attempting to write to host-mounted directories, reading sensitive data, or interacting with other host processes.

However, the attacker’s capabilities are strictly confined to the VM. They have no access to the physical host machine, nor are they granted elevated privileges beyond what is available inside the containerized guest. The container may share namespaces with the host, and the kernel it interacts with is the one booted inside the VM, not the host kernel.

However, in Houdini’s design, these namespace-sharing configurations are restricted to the context of the VM only. That is, even if a container is launched with \texttt{--pid=host}, it shares the PID namespace only with the VM, not the physical host. Likewise, shared network or IPC namespaces remain confined to the QEMU instance. This ensures that while Houdini supports evaluation of shared-namespace behavior, any unintended access or compromise remains sandboxed inside the VM. The attacker cannot affect the physical host’s kernel, and cannot persist beyond the lifecycle of the VM.

The goal of this threat model is to validate that Houdini can safely execute such container scenarios without compromising the integrity of the physical host. Even if the attacker succeeds in exploiting the container or VM environment, the outer boundary provided by QEMU must prevent any direct impact on the physical host.

\subsection{Baseline Comparison: Without VM Isolation}

To better understand the value of Houdini’s VM-based architecture, it is useful to compare it to traditional container deployments that run directly on the physical host. In such environments, containers share the host's kernel and rely on namespace and cgroup isolation to enforce security boundaries. While these mechanisms are generally effective, they are not foolproof, especially when advanced Docker features or misconfigurations come into play.

Flags like \texttt{--pid=host}, \texttt{--net=host}, and \texttt{--ipc=host} allow containers to join the host’s namespaces. When used, these flags remove key layers of isolation by allowing the container to see or interact with physical host-level (in this case) resources such as process IDs, network interfaces, or shared memory segments. These options are sometimes enabled for debugging, performance, or compatibility reasons, but significantly expand the container’s visibility and control over the host environment.

Even more critically, the use of volume mounts (e.g., \texttt{-v /:/host}) can give a container direct access to the host filesystem. If write access is granted intentionally or through misconfiguration, an attacker could overwrite sensitive files such as \texttt{/etc/passwd}, replace binaries, or inject persistent malware. In practice, many container escapes and privilege escalations have stemmed from overly permissive volume mounts or the misuse of the \texttt{--privileged} flag, which grants broad access to kernel interfaces and devices.

In contrast, Houdini enforces a strict boundary between the containerized workload and the physical host by placing containers inside a disposable VM. Even if a container is launched with aggressive options like \texttt{--privileged} or \texttt{--pid=host}, these privileges are scoped only to the VM, not the physical host. This means that even misconfigured or malicious containers cannot directly interact with the physical host's kernel, devices, or filesystem.

Additionally, Houdini’s architecture ensures that test environments are short-lasting. Each container runs inside a fresh VM instance with no persistence beyond the test lifecycle. This further reduces risk by eliminating opportunities for long-term compromise or lateral movement.

Ultimately, this baseline comparison shows that Houdini provides a stronger isolation guarantee than conventional Docker deployments. By decoupling the guest environment from the host through virtualization, Houdini limits the potential for container exploits and enforces a security boundary that is significantly harder to breach.

\subsection{Consideration of VM Escape Attacks}

VMs are widely regarded as strong isolation boundaries between guest and host systems. However, they are not immune to attack. A VM escape occurs when code executing inside the guest environment breaks out of its confinement and gains unauthorized access to the host. These attacks typically target vulnerabilities in the hypervisor, emulated device interfaces, or low-level system components.

Several high-profile vulnerabilities demonstrate the feasibility of VM escapes. For example, CVE-2015-3456 (VENOM) exploited a flaw in QEMU's virtual floppy disk controller to achieve arbitrary code execution on the host \cite{venom}. Similarly, speculative execution vulnerabilities such as CVE-2017-5715 (Spectre) \cite{spectre} and CVE-2019-11135 (ZombieLoad) \cite{zombieload} enabled attackers to leak host memory data from within a guest. These examples, though rare and usually mitigated through timely patches, underscore the importance of minimizing the attack surface of the virtualization layer.

Houdini is not designed to test the security of QEMU or the underlying hypervisor. However, its architecture incorporates multiple safeguards that reduce the risk and impact of VM escape attempts. First, Houdini uses QEMU in user-mode without access to host hardware, kernel modules, or direct device passthrough. Second, the guest OS is a minimal Buildroot-based system, which avoids unnecessary services, drivers, and user-facing software that could be exploited from within the container. Third, common high-risk configurations such as shared folders, USB passthrough, or dynamic device mounting are explicitly avoided.

While no virtualized system is immune to escape-class vulnerabilities, Houdini's design adheres to best practices for secure VM isolation. Its architecture limits exposure to known escape vectors, confines all container execution to a disposable environment, and avoids risky host-guest integration mechanisms. These decisions ensure that even in the presence of an unknown or unpatched vulnerability, the practical risk to the physical host remains minimal.


















\section{Extensibility Evaluation}

Here, we evaluate Houdini’s extensibility by introducing a new custom trick to demonstrate that no modifications to the core orchestration logic is required. The goal is to confirm that new security scenarios can be added through configuration alone, and with the goal of highlighting Houdini’s modular and scalable testing capabilities.

To implement the new trick, two components were created:
(1) a configuration file defining the test matrix, and
(2) a trick script that contains the logic executed inside the container.


A new configuration file was placed in the \texttt{trick\_configs/} directory. This file specifies the test parameter space, such as Docker runtime flags and container-level security settings. The following variables were defined:

\subsection*{Generalizability}

The success of this new trick demonstrates more than just a single functional test; it confirms the correctness and generality of Houdini’s extensibility model. This is because Houdini treats all tricks as interchangeable components, executed through the same standardized interface. Once a new trick is defined and referenced through a configuration file, Houdini automatically performs the following actions regardless of the trick’s internal logic:

\begin{itemize}
\item Loads the associated configuration without requiring logic changes.

This property demonstrates that Houdini’s design is not tailored to specific tests but is built around a flexible, configuration-driven framework. As long as future tricks conform to the same simple interface, they can be added without modifying the system, validating that the extensibility mechanism is generalizable.

This workflow demonstrates Houdini’s modular architecture. Test logic (the trick file) and configuration are fully decoupled from orchestration logic. New scenarios can be added with minimal effort, requiring only a trick script and a config file. The core system remains unchanged, which makes Houdini highly extensible and suitable for evaluating new runtime behaviors, emerging vulnerabilities, or evolving isolation mechanisms in a scalable and automated fashion.

These findings validate Houdini’s suitability as a version-agnostic security regression testing framework, capable of catching both intended fixes and unintended regressions across evolving container platforms.

This level of compatibility makes Houdini suitable not just for point-in-time security evaluation, but also for long-term regression tracking, archival vulnerability research, and continuous integration pipelines that must accommodate diverse and evolving container environments.

\section{Evaluating the Accuracy of CVE-2024-21626}
\label{sec:CVE-2024-21626}
CVE-2024-21626 \cite{runc-cve-2024-21626} is a container escape vulnerability in runc, the low-level container runtime used by Docker and other container engines. It allows a malicious container to escape its isolation and execute arbitrary commands on the host system.

The root cause of this vulnerability lies in how runc handles cgroups for containers, which are used to manage system resources like CPU and memory. During container creation, runc opens a file descriptor to the host's \texttt{/sys/fs/cgroup} directory to configure resource limits. This descriptor remains open throughout the container’s lifecycle and is exposed inside the container via \texttt{/proc/self/fd/}, which lists all open file descriptors of the running process. The vulnerability arises when an attacker sets the working directory in the Dockerfile to point to one of these exposed descriptors, such as \texttt{/proc/self/fd/N}, where \texttt{N} refers to the specific file descriptor inherited from runc that points to the host’s cgroup hierarchy. This causes the container’s current working directory to resolve to a privileged host path. As a result, all subsequent relative file operations in the container are interpreted from the host’s cgroup filesystem rather than the container’s own root, allowing unintended access or modification of host resources.

This behavior is enabled by Linux's treatment of \texttt{/proc/self/fd/N} as dynamic symlinks to open file descriptors. When dereferenced, these symlinks resolve to the original host-side path, regardless of container filesystem restrictions. Because runc and Docker do not restrict access to inherited file descriptors or sanitize the working directory path during initialization, attackers can exploit this oversight to escape isolation. By simply changing the container's working directory to a leaked file descriptor, a malicious container can directly interact with host-managed control groups.
To test the exploitability of CVE-2024-21626, we designed a Houdini trick that executes the following steps on Docker and runc versions listed in Table~\ref{tab:cve201626}:
\begin{enumerate}
    \item Set the working directory to \texttt{/proc/self/fd/<fd>}, pointing to a controlled file descriptor.
    \item Attempt to break out of the container by leveraging the misconfigured working directory.
    \item Validate whether commands can be executed on the host system.
\end{enumerate}

The CVE for this vulnerability indicates that the affected runc versions are $\geq$ \texttt{1.0.0-rc93}, $\leq$ \texttt{1.1.11}. This suggests the vulnerability was introduced in runc version rc93 and fixed in version 1.1.12. However, our tests conducted with Houdini revealed a significant discrepancy with this assertion. Our testing showed that earlier runc versions, such as \texttt{1.0.0-rc1}, \texttt{1.0.0-rc2}, \texttt{1.0.0-rc3}, and \texttt{1.0.0-rc4} also exhibited the same vulnerability. This discovery expands the scope of the CVE by revealing that the issue existed well before version \texttt{rc93}.

This discrepancy highlights a recurring issue in vulnerability disclosure processes: CVEs often rely on assumptions from static code analysis or limited testing. Without rigorous empirical validation across historical versions, critical edge cases can be missed. In the case of CVE-2024-21626, this oversight could have allowed vulnerable deployments relying on older runc versions to remain unpatched under the false belief that they were unaffected.

\section{Evaluating Host Process Manipulation}


In this evaluation, we examine whether a Docker container running as a non-privileged user with \texttt{UID 1000} can interact with and manipulate host processes that are also owned by \texttt{UID 1000}. Under a default Docker configuration, the PID namespace provides process isolation by restricting a container's visibility and access to processes outside its own namespace. However, when the container is launched with the \texttt{--pid=host} flag, it shares the host’s PID namespace, allowing it to enumerate and interact with host processes. This configuration effectively bypasses one of the core isolation mechanisms provided by containers. To assess the security implications of this namespace sharing, we investigate whether process-level interactions, such as sending signals or attaching debuggers, are permitted between the container and host processes when UID ownership is aligned. Our objective here is to investigate how various security flags interact with each other, and to determine the minimum set of privileges required for a container to manipulate host processes. Specifically, we looked at the following flags:

\begin{itemize}
    \item \texttt{--pid=host}
    \item \texttt{CAP\_KILL}
    \item \texttt{CAP\_SYS\_PTRACE}
    \item \texttt{--privileged}

The evaluation began by assessing whether a container launched with \texttt{--pid=host} could list host processes using \texttt{ps aux}. As expected, the container displayed all processes running on the host, confirming that sharing the host PID namespace fully exposes the host's process table to the container.

Following this, we tested whether a container process could send a \texttt{SIGKILL} signal to a host process owned by \texttt{UID 1000}. The container was launched with \texttt{--pid=host}, allowing it to see and interact with host processes. Despite not being granted \texttt{CAP\_KILL}, the signal was successfully delivered. This is because by default, both processes share the same UID and PID namespace, and under standard Linux permission checks, a process can send signals to another process it owns by UID without requiring special capabilities. However, if the target host process is owned by a different UID (another non-root user), \texttt{CAP\_KILL} is required for the signal to be delivered. That capability must also be effective in the user namespace of the target process. Similarly, signaling host processes owned by \texttt{UID 0} remains restricted even with \texttt{CAP\_KILL}, unless the container process itself is also running as root.

Combining \texttt{--pid=host} with \texttt{CAP\_SYS\_PTRACE} enables nearly the same level of interaction with host processes as granting \texttt{--privileged} mode. Specifically, it allows a containerized process to list host processes, send signals, and attach a debugger to them, all key capabilities typically associated with privileged containers. However, unlike \texttt{--privileged}, this more targeted configuration avoids giving the container unnecessary capabilities such as access to all of the host's devices. These results demonstrate that it is unnecessary to over-privilege containers when finer-grained controls can achieve the same functional outcomes with a significantly better security posture.

When the container is confined by AppArmor's \texttt{docker-default} profile, its ability to interact with host processes becomes significantly restricted. Specifically, \texttt{docker-default} explicitly denies system calls such as \texttt{signal} and \texttt{ptrace}, which are required for sending signals and attaching debuggers to other processes. As a result, even if the container shares the PID namespace with the host and possesses the necessary capabilities, these operations will fail. 

However, including the \texttt{--privileged} flag when starting the container overrides AppArmor confinement by disabling the \texttt{docker-default} profile entirely. This lifts all AppArmor-imposed restrictions, allowing the container full access to the previously restricted system calls. As a result, operations that were previously blocked, such as sending signals or attaching debuggers to host processes, are now permitted, even if AppArmor would typically deny them.

It is also important to note that granting capabilities such as \texttt{CAP\_KILL} and \texttt{CAP\_SYS\_PTRACE} alone are not sufficient for interacting with host processes unless the container shares the host’s PID namespace. Without the \texttt{--pid=host} flag, the container operates in its own isolated PID namespace, meaning it cannot see or reference host PIDs at all. As a result, any attempt to send signals or attach to host processes will fail.

We note that the explanation above was derived after a substantial amount of testing and analysis. The Docker documentation alone does not clarify this behavior. Instead, users are expected to understand both the Docker tooling and the underlying Linux kernel security model to select these flags correctly. 

When the container shares the same user namespace as the host (or has aligned UID mappings), and the container process runs under the same UID as the host processes, it can bypass security restrictions that would usually prevent such interactions. In this case, the container may be able to perform operations like sending signals or attaching debuggers to host processes, even without elevated capabilities like \texttt{CAP\_KILL} or \texttt{CAP\_SYS\_PTRACE}. These capabilities, which are typically required for such actions, are not necessary when the container and host share UID mappings, as the container process is considered the same user as the host processes it targets.

This case study highlights a core strength of Houdini, which is its ability to systematically explore and identify the least privilege for a given operation. By allowing users to modify container configurations declaratively, Houdini makes it easy to test a wide range of privilege combinations in a repeatable and automated way. Instead of relying on trial and error or defaulting to the overly permissive \texttt{--privileged} mode, users can incrementally grant permissions and observe the effect of each change. Houdini thus enables security practitioners, developers, and researchers to precisely determine the minimum set of permissions required for a given trick to succeed. As a result, Houdini not only serves as a testing framework for container escapes and misconfigurations, but also as a practical tool for privilege minimization and hardening container deployments.

This case study highlights the complexity of security policies in containerized environments, highlighting that the runtime behavior of security configurations is not always straightforward or predictable. While administrators may configure a container with \texttt{--pid=host} to enable the container to monitor host processes, there is an assumption that certain operations, such as sending signals or attaching debuggers, remain restricted. However, these assumptions may not hold at runtime due to the interplay of various factors such as user namespaces and UID mappings.

Even if an organization maintains the same container configuration and security policies, upgrading Docker to a newer version can inadvertently expand container capabilities, allowing behaviors that were once restricted. This version-induced drift can lead to a false sense of security, where administrators believe containers are still confined by earlier policy expectations, when in fact those policies are no longer fully enforced.



















































\section{Evaluating ptrace Enforcement Across Linux Distributions}
\label{sec:evaluating-ptrace-enforcement-across-linux-distributions}

To assess the effectiveness of Linux kernel mechanisms in enforcing process isolation within containerized environments, we conducted a series of controlled experiments targeting the ptrace system call under various configurations. These experiments were designed to evaluate how different kernel versions, Yama security module settings, and process capabilities affect the ability of a containerized process to trace other processes, both inside and outside its container boundary.

To conduct this study, we used Houdini to run a standardized trick that attempts to use ptrace(PTRACE\_ATTACH) inside a Docker container. The experiments were run across 10 major Linux distributions, covering kernel versions ranging from 2.6.32 to 6.8. Each distribution was tested using its default Yama ptrace\_scope setting, as found in /proc/sys/kernel/yama/ptrace\_scope. For each configuration, we tested the behavior both with and without CAP\_SYS\_PTRACE, isolating the influence of this capability on tracing permissions.

Each test followed the same methodology. A container was launched with a known configuration, and a background process was started within it. The container then attempted to attach to this process using ptrace. A successful or failed attempt was recorded based on the return code of the ptrace system call and the associated error message.

The results, summarized in Table~\ref{tab:ptrace-default-yama}, reveal strong correlations between the default Yama scope and ptrace enforcement. In contrast, distributions that default to Yama scope 0, such as Debian 8, Alpine 3.19, and CentOS 6, allowed tracing even without CAP\_SYS\_PTRACE, which poses a potential security risk. Fedora 40, which defaults to Yama scope 2, exhibited the strictest behavior: ptrace failed in all test cases, even when the container was granted CAP\_SYS\_PTRACE, demonstrating a highly restrictive enforcement model. These results also confirm that the kernel version alone is not sufficient to predict ptrace behavior; the default Yama configuration plays a critical role.

Overall, this case study highlights the lack of uniformity in ptrace enforcement across Linux distributions.

\section{Summary of Findings}

The case studies in this chapter illustrate how Houdini enables systematic, reproducible testing of container security across a diverse range of configurations and software versions. Each evaluation reveals subtle inconsistencies, version-specific behaviors, or silent enforcement gaps in container confinement mechanisms that would be difficult to detect through static analysis alone.

In the CVE-2024-21626 evaluation, Houdini uncovered that the vulnerability affects a broader range of `runc` versions than originally disclosed. This highlights how real-world testing can expose gaps in vulnerability reporting based on assumptions or limited validation.

The host process manipulation case study demonstrates that seemingly secure configurations can lead to dangerous process-level interactions when UID mappings, capabilities like `CAP_KILL` and `CAP_SYS_PTRACE`, and namespace flags such as `--pid=host` interact in complex ways. Houdini was able to identify the exact conditions under which a container could signal or trace host processes, even without `--privileged` mode, thus enabling least-privilege policy design.

In the privileged port forwarding case study, Houdini revealed that Docker’s evolving security model silently changed default behaviors—allowing containers to bind to low-numbered ports without root or `NET_BIND_SERVICE` starting from version 20.03. These shifts can undermine existing security assumptions if unnoticed.

Lastly, the ptrace enforcement study across Linux distributions showed a lack of uniformity in how Yama policies are enforced by default. While newer distributions such as Fedora 40 and Ubuntu 24.04 apply stricter controls, others like Debian 8 and Alpine 3.19 allow tracing without `CAP_SYS_PTRACE`, potentially weakening isolation guarantees.

Together, these case studies underscore Houdini’s effectiveness in revealing discrepancies between expected and actual security enforcement. They emphasize the need for dynamic testing when evaluating container confinement, especially in environments where assumptions about kernel behavior, runtime capabilities, or Docker defaults may no longer hold.

\chapter{Related Work}

Container security depends on several low-level Linux features that work together to keep applications isolated. These include technologies like namespaces, cgroups, AppArmor, and Seccomp, which help control what a container can see, do, or access. Over the years, researchers and developers have created tools and systems that rely on these features to prevent containers from escaping or causing harm. But these protections are not perfect. Misconfigurations, outdated policies, or changes in the Linux kernel can all lead to serious security issues, such as containers breaking out, gaining extra privileges, or leaking data.

This chapter reviews past work related to container confinement. It covers areas like VM and sandbox escapes, Linux security tools such as AppArmor and cgroups, system call filtering with Seccomp, and monitoring tools built with eBPF. Each section looks at how these tools work, what problems they solve, and where their limitations are. We also explore rule-based security systems and kernel changes that try to improve isolation at a deeper level. Along the way, we explain how Houdini can fill the gaps left by existing approaches.

We finish the chapter with a look at popular tools used for scanning, hardening, and even attacking container setups. These tools show that while many solutions exist, verifying strong isolation still requires hands-on testing.

\section{Virtual Machine Escapes} 

VM escapes occur when an attacker successfully breaks out of a virtualized confined environment, gaining unauthorized access to the host system. Given that hypervisors manage multiple VMs on shared hardware, such escapes can lead to host compromise, cross-VM attacks, and lateral movement within cloud environments. One of the most notable VM escape vulnerabilities is VENOM (CVE-2015-3456) \cite{abdoul2018novel}, which exploited a flaw in the virtual floppy disk controller (FDC) implementation in QEMU, affecting platforms like Xen, KVM, and VirtualBox. Other significant VM escape vulnerabilities include Cloudburst (2009), which exploited VMware's virtual graphics driver; CVE-2018-6981 and CVE-2018-6982, which targeted VMware ESXi, Workstation, and Fusion \cite{vmware2018escape}; and multiple VirtualBox vulnerabilities (2017) enabling guest-to-host code execution \cite{virtualbox2017bugs}. Additionally, side-channel attacks like MDS/ZombieLoad (2019) demonstrated how speculative execution flaws could be leveraged across VMs \cite{mds2019attack}. More recent research has uncovered weaknesses in encrypted virtualization, such as the SEVered attack (2018), which extracted plaintext memory from AMD SEV-protected VMs \cite{severed2018}, and the Heckler attack (2024), which manipulated non-timer interrupts to compromise confidential VMs in AMD SEV-SNP and Intel TDX \cite{heckler2024}.\\

Houdini’s reliance on virtualization acknowledges the potential for VM-level vulnerabilities, but treats the VM boundary as a strong, but not a foolproof line of defense. It uses VMs not as a security guarantee, but as a practical containment layer to isolate test environments from the host. By doing so, Houdini can safely execute untrusted or experimental configurations and observe whether container confinement fails, while minimizing the impact of potential exploitation.

\section{Sandbox Escapes} 

Sandboxing is a critical security mechanism for restricting the execution of untrusted code, commonly used in browsers, mobile apps, and security tools. A sandbox escape occurs when an attacker bypasses these restrictions, executing arbitrary code with higher privileges and potentially leading to full system compromise. Modern web browsers heavily rely on sandboxing to isolate JavaScript execution from the underlying OS. However, several high-profile vulnerabilities have enabled sandbox escapes. For example, CVE-2019-5786 \cite{chromezeroday}, a use-after-free vulnerability in the FileReader API of Google Chrome, allowed attackers to escape Chrome's sandbox and execute code on the host. Other notable sandbox escape vulnerabilities include CVE-2022-26706, which exploited a flaw in macOS's App Sandbox to execute code outside of restricted permissions \cite{macossandboxescape}; CVE-2023-36719, a stack corruption vulnerability in Windows OS that enabled escape from the Chromium sandbox \cite{chromiumsandboxescape}; and CVE-2024-4040, which was actively exploited to break out of CrushFTP’s Virtual File System (VFS) \cite{crushftpsandboxescape}. Additionally, vulnerabilities in Judge0, an online code execution system, exposed systems to full takeover by allowing attackers to escape its sandbox \cite{judge0sandboxescape}. Research has also uncovered critical flaws in vm2, a JavaScript sandbox library, which could be exploited to bypass its security restrictions and gain remote code execution \cite{vm2sandboxescape}.

\section{Process and Resource Isolation}

\subsection{Apparmor}

AppArmor is a Linux security framework based on mandatory access control, similar to SELinux, but it focuses on restricting individual programs \cite{zhu2021lic}. It works by applying predefined security profiles that limit what a program can do \cite{zhu2021lic}. In Docker, AppArmor can be used to load these profiles into containers to restrict their behavior. If no profile is specified, Docker automatically applies a default one \cite{zhu2021lic}.

Mattetti et al. \cite{mattetti2015securing} developed LiCShield as a framework that uses AppArmor as its enforcement backend. It automatically generates custom AppArmor security profiles by analyzing container behavior in a pre-production environment. These profiles are then used to tightly confine both the container’s runtime behavior and its interactions with the host system, ensuring that only authorized actions are permitted during execution.

Sun et al. \cite{sun2018security} extend AppArmor to work independently inside containers by introducing a new concept called a security namespace. Normally, AppArmor is global, it enforces one set of security rules for the whole system, which means containers cannot define or apply their own AppArmor policies. The authors solve this problem by modifying the Linux kernel so that each container can have its own separate AppArmor namespace. This allows a container to load and enforce its own AppArmor profiles for its applications, independent of the host system's policies.

With this change, both the host and the container can apply AppArmor protections at the same time. For example, while the host might enforce a general container confinement policy, the container itself can load a specific profile to restrict what Firefox or MySQL can do \cite{sun2018security}. 

Zhu et al. \cite{zhu2021lic} create Lic-Sec, which is an enhanced AppArmor profile generator that improves Docker container security by combining the strengths of Docker-sec and LiCShield. The reason for creating a similar tool to LiCShield is that LiCShield is incompatible with recent versions of Docker. Lic-Sec automatically creates fine-grained profiles based on container behavior, restricting capabilities, network access, file operations, mounts, and shell execution. By using both Auditd and SystemTap for tracing, Lic-Sec generates stricter, more comprehensive profiles that block privilege escalation and container escape attacks. It adapts to container use cases and enforces these profiles at runtime for stronger and automated protection.

Houdini could have influenced Zhu et al. \cite{zhu2021lic} work by providing an automated framework to evaluate Lic-Sec's effectiveness across diverse environments. For example, instead of manually testing exploits against a fixed kernel version, docker version and set of container images, the authors could have used Houdini to run the same exploit across multiple kernel versions, Docker versions, configurations, and AppArmor profiles to identify gaps in enforcement. Additionally, Houdini’s ability to replay tricks across time and machines would have allowed for more reliable validation of Lic-Sec’s defenses, such as verifying whether blocking /bin/bash consistently prevents privilege escalation across real-world images.



\subsection{Control Groups}

cgroups (short for control groups) are a Linux kernel feature used to manage and limit system resources like CPU, memory, and I/O for groups of processes \cite{chelladhurai2016securing}. They allow administrators or container runtimes like Docker to control how much of a resource each container can use. For example, Docker can apply cgroup settings to restrict a container’s CPU time or memory usage. This helps prevent a single container from consuming too many resources and affecting others on the system \cite{chelladhurai2016securing}. While cgroups are not designed to stop one container from accessing or interfering with another container’s data or processes \cite{chelladhurai2016securing}, they are essential for defending against certain types of Denial-of-Service (DoS) attacks by limiting the damage a container can cause through resource exhaustion \cite{chelladhurai2016securing}.

Chelladhurai et al. \cite{chelladhurai2016securing} identifies DoS attacks as a significant threat in containerized environments like Docker. The authors emphasize that while containers offer process isolation, they lack strong guarantees against resource abuse, which can allow a malicious container to exhaust host resources and impact other containers.

To address this, they propose several practical mitigation strategies using Linux cgroups \cite{chelladhurai2016securing}. They argue that cgroups are essential for defending against DoS attacks by limiting a container’s access to CPU, memory, and I/O resources. However, they also note that cgroups alone do not provide full isolation between containers. Their proposed DoS mitigation technique includes three test cases: setting memory limits directly in the docker run command using -m=512mb, applying default memory limits in the Docker configuration file (/etc/default/docker), and enforcing a system-wide memory limit for containers that do not specify their own \cite{chelladhurai2016securing}. For evaluation, the paper includes sample attack code to simulate DoS scenarios. One example allocates memory indefinitely using malloc, while another consumes CPU resources by endlessly calculating prime numbers. These tests demonstrate how resource limits can effectively prevent containers from overwhelming the host.

The original paper takes a manual approach to testing DoS attacks by running memory and CPU-intensive scripts inside containers with various resource limits. While this method demonstrates the effectiveness of using cgroups to mitigate DoS risks, it is limited in scale and reproducibility. Houdini can automate and greatly expand this type of testing. Instead of running scripts manually, Houdini can encode these attacks as repeatable tricks, such as infinite memory allocation or continuous CPU-bound computations. These tricks can then be executed systematically across a wide range of Docker versions, kernel versions, and container configurations (e.g., with or without memory limits like the -m flag). This is especially important because the implementation and enforcement behavior of cgroups can differ between kernel versions, particularly between cgroups v1 and v2, or in how specific resource limits are handled. By capturing and comparing results, Houdini enables a scalable and repeatable evaluation framework. It can identify which combinations of settings are vulnerable to DoS and which configurations effectively block the attacks, providing a more comprehensive assessment than manual testing.


\subsection{System Call Filtering}

System call filtering is a security technique used to control which system calls a program is allowed to make to the operating system. Since system calls are the primary way that applications interact with the kernel, restricting them helps reduce the attack surface and prevent malicious behavior. On Linux, this is commonly done using Seccomp, which lets developers create filters to allow or block specific syscalls. Traditional filtering with classic BPF (cBPF) is simple and efficient but limited, it only supports static rules and cannot track complex behavior or context. More advanced techniques, such as those using eBPF, improve flexibility by allowing filters to maintain state, inspect arguments, and respond dynamically to syscall patterns. 

This paper used system call filtering as a key part of its security monitoring approach. Gantikow et al. \cite{gantikow2019rule} used two tools named Sysdig and Falco that rely on a kernel module to capture and analyze system calls made by containers. By watching these low-level operations, the system can spot unusual or potentially harmful behavior. Sysdig collects all system calls and lets users filter them by container, process, or syscall type to reduce noise. Falco adds a layer of security by letting users define rules that flag suspicious behavior based on these system calls.

For example, the authors created rules to detect when a container tries to access files outside its expected directories using the open() syscall. They also detected unauthorized programs being run inside containers by monitoring execve calls. Attempts to break out of containers were flagged by watching for the setns syscall, and unexpected network connections were detected by tracking relevant network-related system calls.

While Falco can only detect individual suspicious events, not patterns or sequences of events like those involved in buffer overflows or denial-of-service attacks, the use of system call filtering still proved effective in catching many types of threats with low performance impact.

Ghavamnia et al. \cite{ghavamnia2020confine} present Confine, a system that automatically generates restrictive system call policies for Docker containers. Instead of relying solely on dynamic analysis (which often misses rare or conditional execution paths), Confine uses a hybrid approach: it performs a short dynamic analysis to discover all executables launched during container startup and then uses static analysis on those binaries to extract the complete set of system calls they may invoke. This includes both libc-invoked and directly invoked syscalls.

The goal of this syscall filtering is to allow containers access only to the syscalls they truly need, thereby blocking access to the rest, many of which may contain vulnerabilities or provide attack vectors for privilege escalation or container escape. By creating custom Seccomp BPF profiles that deny all unnecessary syscalls, Confine ensures that even if an attacker gains access to a container, they cannot exploit most of the kernel interface.

The evaluation showed that Confine could disable 145 or more system calls (out of 326) for over half of the tested containers, neutralizing 51 known kernel CVEs. This significantly exceeds Docker’s default Seccomp filter, which only disables 49 syscalls.

Houdini could be used to dynamically test whether Confine’s generated Seccomp profiles are too restrictive or too permissive. For instance, if Houdini can successfully run an attack trick under a Confine policy, it might indicate an over-permissive profile. Conversely, if legitimate workloads fail under Confine’s policy in Houdini’s environment, this suggests over-restriction.

Confine assumes that policies generated statically will remain correct across systems. But Linux syscall implementations and Docker behavior change over time. Houdini could systematically evaluate if the same Confine-generated profile works consistently across kernel versions, and flag new vulnerabilities.

Jiao et al. \cite{jia2023programmable} used system call filtering to improve the security of Linux systems by controlling which system calls a program is allowed to make. Normally, this is done using a tool called Seccomp, which filters system calls based on simple rules written in a limited language called cBPF. However, cBPF is very basic, as it can only check the syscall number and some simple arguments. It cannot remember past behavior, check syscall sequences, or read memory safely. This makes it hard to write strong security rules.

Jiao et al. \cite{jia2023programmable} solve this by creating a new system called Seccomp-eBPF, which uses the more powerful eBPF language instead of cBPF. eBPF allows writing filters that can remember past system calls, count how many times a system call was used, block system calls if they’re too frequent, or only allow them in certain program phases. It can also safely inspect data passed by pointer (like file paths), and prevent known bugs caused by racing system calls.

With these improvements, Seccomp-eBPF can block real-world attacks that cBPF cannot. It also helps reduce the number of system calls allowed in early stages of a program (reducing attack surface) by over 50\% in some cases. The paper shows that this system is both safer and faster than older methods that rely on user-space monitoring, and it works well in environments like containers.


\section{Extended Berkeley Packet Filter}


eBPF (extended Berkeley Packet Filter) is a Linux kernel technology that allows small, sandboxed programs to run safely inside the kernel without modifying kernel source code or loading kernel modules. Originally designed for network packet filtering, eBPF has evolved into a general-purpose tool for tracing, monitoring, and security enforcement. In essence, eBPF lets developers attach custom logic to various kernel events, like system calls, network activity, or file operations, and collect data or enforce rules with minimal performance overhead. Because eBPF programs run in a restricted environment and are verified for safety before execution, they offer a powerful but secure way to extend kernel behavior dynamically.


Lopes et al. \cite{lopes2020container} use eBPF as the core mechanism for tracing system calls made by containerized applications. The goal of the system is to automatically generate custom Seccomp profiles that strictly limit the syscalls a container can perform, thereby reducing the attack surface. To achieve this, the authors use eBPF's powerful kernel-level tracing capabilities to hook into every syscall. Specifically, they implement a BCC (BPF Compiler Collection) program that attaches eBPF probes to all system calls and logs detailed information such as the syscall name, timestamp, process ID, and the namespace from which the syscall originated.

For Lopes et al. \cite{lopes2020container}, the goal is to automatically generate Seccomp profiles by tracing the actual system calls used by a containerized application. While their approach uses eBPF for runtime tracing, Houdini could have provided complementary value by automating and scaling this profiling process across many container configurations, Docker versions, and kernel versions. Houdini’s test matrix model allows systematic exploration of diverse runtime flags (e.g., --privileged, --cap-add, AppArmor profiles) to evaluate whether the generated Seccomp profile remains effective across different settings. Additionally, Houdini could validate whether the reduced syscall profile indeed blocks known exploits, as done in Lopes' Apache test case, but at scale.

This namespace information is crucial because it allows the system to filter out irrelevant syscalls made by the host or other processes, ensuring that only syscalls from the target container are recorded. These logs are then processed to generate a Seccomp profile that whitelists only the syscalls actually used by the application during testing. One of the key advantages of using eBPF is its runtime-agnostic nature. It works not only with Docker but also with Podman or any other container technology, since the tracing happens at the kernel level. Additionally, eBPF's integration into the CI/CD pipeline enables automatic profile generation whenever code changes are committed, making it easy to keep Seccomp profiles up to date with minimal manual effort. As a proof of concept, the authors applied their system to a vulnerable Apache container and demonstrated that, after tracing and generating a Seccomp profile using eBPF, the container was no longer susceptible to a known RCE vulnerability (CVE-2018-11776).

He et al. \cite{he2023cross} found a new type of attack where eBPF can be misused to break container isolation in shared-kernel environments like the cloud. eBPF was designed to safely let programs interact with the Linux kernel for things like monitoring and debugging. But the paper shows that attackers inside a container can use eBPF helper functions, such as ones that read or write other processes’ memory to spy on or interfere with programs running outside the container, including on the host. These attacks can steal sensitive data, crash important services like systemd, or even escape the container by taking over a root-level process on the host.

One key problem is that eBPF tracing programs are not limited by namespaces, so they can see and interact with processes system-wide. The authors tested this in real-world services like Jupyter notebooks and Kubernetes clusters and successfully escaped containers or spread attacks across nodes. Even trusted tools like Cilium and Datadog that use eBPF for monitoring could be at risk if used in containers with the wrong settings.

To fix this, the paper proposes a new system called CapBits. It gives each process fine-grained control over which eBPF features it can use or be targeted by. CapBits is faster and more secure than previous methods and can stop attacks where eBPF is used to hijack sensitive processes. Overall, the paper warns that while eBPF is a powerful tool, its risks in container environments are not well understood and need better protection.

Jiao et al. \cite{jia2023programmable} introduce Seccomp-eBPF, a new way to improve system call filtering on Linux using the extended Berkeley Packet Filter (eBPF). System call filtering is a key technique used to protect the operating system from untrusted applications, such as containers, by controlling which system calls are allowed. The current standard, Seccomp with classic BPF (cBPF), is widely used but has serious limitations. It only allows basic, static checks and cannot store information or respond to complex patterns of behavior, making it hard to implement advanced security policies.

Seccomp-eBPF solves this by allowing developers to write more powerful and flexible filters using eBPF, a newer language already used in many parts of the Linux kernel. With Seccomp-eBPF, filters can track state (such as counting how many times a system call has been used), detect specific sequences of system calls, prevent race-condition attacks by forcing certain system calls to run one at a time, and safely examine data passed from user programs. These features make it possible to block sophisticated attacks that cBPF cannot handle.

The authors implemented this system in the Linux kernel and added support for it in the crun container runtime. They showed that it works well in practice. For example, it reduced the number of allowed system calls during the startup of common server applications by up to 55\%, significantly shrinking the attack surface. Despite its added flexibility, Seccomp-eBPF maintained performance similar to optimized cBPF filters and was much faster than user-space alternatives like Seccomp Notifier. Overall, Seccomp-eBPF offers a safer and more powerful way to secure Linux systems, especially in environments like containers that rely heavily on system call filtering.

Findlay et al. \cite{findlay2021bpfcontain} use eBPF to build a new security system called BPFCONTAIN that improves container security on Linux. Containers often rely on tools like seccomp, AppArmor, and SELinux for isolation, but these tools can be complicated, inconsistent, and not designed specifically for containers. To solve this problem, BPFCONTAIN uses eBPF to monitor and control what containers are allowed to do directly inside the Linux kernel. It checks actions like file access, network use, and system calls, and blocks anything not allowed by the container’s policy. These rules are written in a simple YAML file, making it easy to manage. BPFCONTAIN loads these rules and programs at runtime, without changing the Linux kernel or container tools like Docker. It also adds extra protections to block known container attacks, such as privilege escalation.



\section{Rule-based Systems}

A rule-based system is one that makes decisions or detects events based on a predefined set of rules. These rules are usually written by security experts or administrators and follow simple if-then logic. For example, a rule might state that if a certain system call is made by an unexpected process, the system should flag it as suspicious or block it. This approach allows for clear, predictable behavior because every decision is based on explicitly defined conditions.

In the context of container or system security, rule-based monitoring is often used to detect abnormal behavior. Tools like Falco apply rules to system call traces to identify activities that deviate from what is considered normal or safe. For example, rules can be written to detect unauthorized file access, unusual network activity, or attempts to escalate privileges. These systems are easy to understand and customize, making them widely used in production environments.

However, rule-based systems also have limitations. They can only detect behaviors that have been anticipated and written into the rules. This makes them less effective against new or complex attack patterns that do not match existing rules.

A proposed method by Jian et al. \cite{jian2017defense} implemented as a shell script that runs on the host and follows a sequence of fixed rules to identify suspicious activity. It first collects metadata about all running containers and their processes, including each process’s PID, name, and namespace tag (Nsid). Then, it compares the namespace tag of each container process against the namespace tag of that container’s init process. According to the authors, if a process inside a container has a different namespace tag than its init process, it likely indicates that the process has escaped its namespace—an early sign of a container escape attempt.

This comparison logic is rule-based because it applies a deterministic rule: if Nsid(process) does not equal Nsid(init), then mark the process as suspicious. Further, the script checks whether the suspicious process resembles a shell (based on the process name). If both conditions are met, the system takes action: it kills the process and tries to trace the attacker (e.g., by retrieving the user ID or IP address).

Houdini could have helped improve the work by Jian et al. \cite{jian2017defense} by making the testing more thorough, automated, and easier to repeat. In the paper, the authors propose a way to detect Docker escape attacks by checking if a process inside the container has a different namespace tag than the container’s main process. They test this using only two known attacks: one involving the recvmsg system call and another using the Dirty COW vulnerability.

With Houdini, the authors could have gone much further. Houdini can automatically run many different escape tricks, both known and custom-made across a wide range of Docker versions, Linux kernel versions, and settings like user privileges, Seccomp filters, and namespace configurations. This would help find out whether the detection method works well in more situations or if it fails in certain cases.

Gantikow et al. \cite{gantikow2019rule} propose a rule-based monitoring system that detects security violations in containerized workloads by analyzing system call activity. This is accomplished using two open-source tools: Sysdig and Falco. Sysdig provides a kernel module that captures all system calls made by containers, while Falco builds upon this by applying predefined rules to flag suspicious behavior. These rules are written in a declarative format and can describe conditions such as unauthorized file access, unexpected application launches, or privilege escalation attempts.

In this rule-based model, each rule defines a pattern of behavior that is considered abnormal or malicious. For example, a rule might detect a container process trying to access files outside its designated working directory (indicating a possible information leakage or path traversal attack), or flag execution of unknown binaries inside a container (which might imply a crypto-miner or reverse shell). Rules can be whitelist-based (defining what is allowed) or blacklist-based (defining what is forbidden), and are matched against real-time system call events.

The paper presents various attack scenarios like container breakout, unauthorized networking, or loading kernel modules, and shows how each can be detected with carefully written Falco rules. While the rule-based approach is effective for many types of misuse, the authors acknowledge limitations. Notably, Falco cannot detect frequency-based or multi-event anomalies (e.g., Denial of Service or buffer overflows), as it only supports detection of single-event anomalies.

the paper by Brady et al. \cite{brady2020docker} uses a rule-based system as part of its approach to securing Docker containers. The authors incorporate Anchore Engine into their CI/CD pipeline, which applies a set of predefined security rules, also known as policies, to each Docker image. These rules include checks for known security vulnerabilities and for unsafe Dockerfile configurations, such as whether the image exposes port 22. In their implementation, the authors use Anchore's default rules, but they note that developers can create and apply their own custom rules based on specific security needs. This rule-based system allows the pipeline to automatically detect and block images that do not meet the defined security standards. It helps developers identify and fix issues early in the development process, improving the overall security of containerized applications.

The paper by Zhu et al. \cite{zhu2021lic} describes three tools Docker-sec, LiCShield, and the proposed Lic-Sec all of which rely on generating and enforcing rule-based security profiles using AppArmor. These profiles consist of explicit allow/deny rules that define what operations a containerized application can perform, such as file accesses, network operations, and use of Linux capabilities.

Docker-sec uses dynamic monitoring to learn what capabilities and network accesses a container actually uses, then generates an AppArmor profile with rules that only permit those actions. LiCShield, on the other hand, uses SystemTap to trace kernel-level operations and generates rules for more types of actions, such as file mounts and execution paths. Lic-Sec combines both tools to generate a more comprehensive rule set that includes deny rules for unnecessary shell commands and tighter restrictions on mounts and execution behavior.

In all cases, the tools use observed behavior during a training phase to produce explicit, rule-based security profiles that constrain container behavior at runtime. These rules are enforced by the AppArmor Linux Security Module, making this a clear example of a rule-based system in container security.

The paper by Chen et al. \cite{chen2022seaf} uses a rule-based system as part of its SEAF framework to detect security flaws in Docker container images. SEAF defines a set of detection primitives that act as basic operations for writing flexible detection rules. These primitives include content matching, feature matching, data recording, usage frequency analysis, and file extraction. Each type of vulnerability, such as misconfiguration, unauthorized access, sensitive information leakage, malware, and software vulnerabilities, is detected by combining specific primitives into rules. For example, to detect unauthorized access in Redis containers, SEAF extracts configuration files and uses regular expressions to search for insecure settings like missing passwords. These rule combinations allow SEAF to systematically inspect container layers and identify flaws by applying consistent logic across images. This rule-based approach is modular, meaning new rules can be added easily to address emerging threats without changing the underlying system. As a result, SEAF can adapt to various application scenarios and detect a wide range of security issues using well-defined and reusable rule patterns.

\section{OS Changes}

Luo Yang et al. \cite{luo2016whispers} investigates how containers can still leak information through covert channels, even when isolation mechanisms are in place. It focuses on Docker and shows that the default security features such as namespaces and cgroups are not enough to prevent secret communication between containers. These covert channels take advantage of shared physical resources, allowing containers to bypass the expected security boundaries.

The authors present five high-capacity covert channel techniques. These include CPU load modulation, cache-based covert channels, disk I/O delay signaling, memory bus contention, and file lock contention. Each method allows a sender container to encode data into patterns of resource usage. The receiver container then decodes this data by observing how these patterns affect performance. For example, a sender might create bursts of CPU activity to represent binary data, while the receiver measures CPU latency to interpret the signal. These attacks are a form of side-channel communication, where indirect changes in system behavior are used to leak information.

The paper describes scenarios where a sender container transfers hidden information to a receiver container, despite there being no authorized communication path between them. This demonstrates that containers can communicate by exploiting shared hardware such as CPU caches or memory bandwidth. Even without network access or shared filesystems, the sender can affect system behavior in ways that the receiver can detect and interpret.

In this paper, Sun et al. \cite{sun2018security} introduce the idea of security namespaces, a new feature in the Linux kernel that lets each container have its own security settings using tools like AppArmor and IMA. Normally, these tools are set by the host and apply to all containers. This means containers can’t create or manage their own security rules, which is a problem when you want containers to be more isolated or run different policies. The paper’s solution is to separate these security settings so that each container can have its own, without affecting the host or other containers.

To make this work, the authors made small changes to the Linux kernel, only about 1,000 to 1,500 lines of code. They tested their changes in two ways. First, with IMA, containers were able to set their own policies, like only allowing signed programs to run. The containers correctly blocked unsigned or changed programs, and they couldn’t get around the host’s security rules, which stayed in place. Second, with AppArmor, they tested 20 common programs that already had security profiles. Sixteen of them ran correctly inside containers using both the container’s and the host’s security rules. For the four that didn’t, the system gave warnings ahead of time to avoid crashes.

Even though this new design is useful, it doesn’t work with systems like Houdini. Houdini depends on the way Linux currently handles security, where rules like AppArmor and IMA are shared across the whole system. If Houdini had to work with these new security namespaces, it would need to be redesigned from the ground up. Because of that, this paper’s approach, while creative and effective, isn’t compatible with how Houdini is built today.

The paper by Sun et al. \cite{sun2018security} relate to OS changes because it shows that even though microVMs are meant to be isolated, some of their operations are still handled by the host operating system, creating security risks. The paper finds that parts of the system such as virtiofsd and kernel threads like kvm pit and vhost are not fully isolated. They run with too much access or are not limited by cgroups. To fix this, the authors suggest changing how the OS manages these components by placing kernel threads into the correct cgroups and reducing unnecessary permissions.


\section{Secure Computing}

Lopes et al. \cite{lopes2020container} present a method to improve container security by automating the creation and maintenance of Seccomp profiles. Seccomp is a Linux kernel feature that limits the system calls a containerized application can make, significantly reducing the potential attack surface. However, maintaining these profiles is difficult because it requires a detailed understanding of which syscalls are needed and must be updated whenever the application changes. To address this, the authors develop a system that integrates with CI/CD pipelines to automatically trace the syscalls made during unit and integration testing using eBPF. These syscalls are collected, and a custom Seccomp profile is generated that whitelists only those calls, blocking everything else by default. For applications with incomplete test coverage, the system can use fuzzing to stimulate additional syscall paths. The approach ensures that each container has a tailored Seccomp profile, improving security without manual configuration. The authors show that this method can mitigate real-world vulnerabilities, such as CVE-2018-11776, by blocking the syscalls required for exploitation.

Ghavamnia et al. \cite{ghavamnia2020confine} present a static analysis-based system named Confine that generates restrictive system call policies for Docker containers. Unlike previous solutions that rely on dynamic training with realistic workloads, which can miss rarely executed paths, Confine uses static analysis of container binaries and their dependencies to identify the complete superset of system calls required for correct operation. This allows it to generate Seccomp (Secure Computing Mode) profiles that deny all other system calls, significantly reducing the container’s kernel attack surface.

The authors evaluated Confine on 150 Docker images and found that it could disable over 145 system calls out of 326 for more than half the containers, far more than Docker’s default Seccomp policy. This reduction effectively neutralized 51 known kernel CVEs, demonstrating strong security gains without breaking application functionality. The approach also handles direct syscall invocations, language-specific system call mechanisms such as Go and Java, and dynamic library loading.

Confine directly builds on Seccomp as its enforcement mechanism. It generates custom Seccomp BPF profiles that define allow and deny lists for system calls per container. By statically analyzing what syscalls are truly necessary, Confine tailors these Seccomp profiles to the exact needs of each container, minimizing the set of syscalls exposed to potentially malicious applications and enhancing the host’s protection. This use of Seccomp is central to the paper’s method for reducing kernel attack surfaces and mitigating container escape vulnerabilities.

\section{Practical Tools and Framework Design}

At the time of this writing, to our knowledge, Houdini is the first comprehensive approach for evaluating and comparing \textit{container confinement mechanisms}. Much of the container security literature to date has focused on either vulnerability scanning of container images, building offensive/attack tools for container escapes, or proposing best practices for securing container runtimes. While these papers, tools, and documents do not directly share our research objectives, they still broadly fit into the container security landscape. Additionally, research on VM escapes and sandbox escapes has provided valuable insights into isolation vulnerabilities, many of which relate to container security. Techniques used to break out of hypervisors and sandboxed environments often share similarities with container escape methods, which the importance of strong confinement mechanisms. The remainder of this section does not aim to exhaustively enumerate all container security tools and systems, but rather to highlight the various salient methods, including prior research on times the confinement of VMs and sandboxes have been escaped as it is related to work. \subsection{Regression Testing.} 

One common practice in continuous integration/continuous deployment (CI/CD) pipelines is the use of automated vulnerability scanning tools to detect known vulnerabilities in container images. Tools such as Trivy \cite{trivy} and Clair \cite{clair} are often integrated into CI pipelines to perform vulnerability assessments during the image build process. These tools automatically scan for security flaws in the container image, ensuring that only secure images are deployed to production. For example, GitLab’s CI/CD pipeline includes built-in features for Container Scanning with Trivy, automatically running vulnerability scans whenever new Docker images are built or updated.

In addition to security scanning and policy enforcement, CI/CD pipelines also use container hardening tools like Docker Bench for Security \cite{docker_bench} and Kube-bench \cite{kube_bench} to ensure containers are securely configured. These tools can be integrated into the pipeline to automatically check container configurations against security best practices, such as ensuring that containers run as non-root users or that unnecessary ports are closed. CircleCI \cite{circleci}, for example, integrates Docker Bench to verify that new container builds follow best practices before they are pushed to production.\\

\subsection{Vulnerability Scanners} 

Many free, open, and closed-source tools exist for identifying the presence of known vulnerabilities in container images. Shu \etal~\cite{shu2017study} developed a vulnerability scanning tool to scan Docker Hub container images at scale. They found that on average, official and community images have concerning amounts of vulnerabilities (180+), and that these vulnerabilities remain unpatched for hundreds of days. Their study utilized the Docker Image Vulnerability Analysis (DIVA) framework, which automates the discovery, download, and analysis of over 300,000 Docker images. The findings revealed that more than 80\% of both official and community images contained at least one high-severity vulnerability, and many images were not updated for extended periods. Moreover, vulnerabilities were often inherited from parent images to child images, further increasing security risks.\\

\subsection{Best Practices} 

Users in search of (often high-level) advice on how to improve the security of their container deployments can consult one of many best practices guides available online. One such guide is the Center for Internet Security (CIS) Docker Benchmark \cite{CIS}. In our experience, guides tend to offer generic advice (e.g., ``\textit{Only allow read access to the root filesystem}''). This is problematic because it oversimplifies container security. Generic advice may seem straightforward, but it doesn't account for the specific context or unique configuration of an individual deployment. Such one-size-fits-all recommendations can lead users to believe that simply following these broad guidelines is enough to secure their systems, potentially leaving critical vulnerabilities unaddressed. In reality, effective container security requires a nuanced, tailored approach that considers the particular needs and threat models of each environment. Houdini fills the gap between generic advice and practical security by enabling one to objectively evaluate the effectiveness of your container confinement measures.\\

\subsection{Offensive Tools} 

The offensive security community has developed a range of specialized tools aimed at identifying and exploiting vulnerabilities within containerized environments. Containers, while providing strong isolation, are not immune to attacks, and these tools focus on testing the robustness of container defenses. CDK\footnote{\url{https://github.com/cdk-team/CDK}} and DEEPCE\footnote{\url{https://github.com/stealthcopter/deepce}} are two widely used, open-source container penetration testing toolkits that leverage a collection of known exploits to gain persistence, escape the container, and gather sensitive information about the container environment. These tools aim to bypass isolation mechanisms like namespaces, cgroups, and SELinux, often using a variety of aggressive techniques to identify weaknesses in container security. CDK specifically uses any available method to circumvent security measures, providing a broad toolkit to test the limits of a container's defense. Meanwhile, DEEPCE, developed by stealthcopter, focuses on privilege escalation and container enumeration, attempting to exploit specific weaknesses to achieve container escapes, thereby compromising the host system. In contrast, Houdini takes a more systematic and structured approach to container security testing. Rather than focusing solely on exploiting vulnerabilities, Houdini allows for the direct comparison of defensive techniques by clearly defining the testing environment, outlining the exploit steps, and documenting the expected outputs.\\

\subsection{Understanding Time Metrics in Microbenchmarking}

In performance benchmarking, especially in systems research and software profiling, several time-based metrics are commonly used to assess how a program or process utilizes computing resources. These include wall clock time, user time, system time, and CPU utilization. Each of these captures a different aspect of execution behavior and provides insight into how efficiently a task runs.

\textbf{Wall clock time}, also known as elapsed time or real time, is the total time taken from the start of a program to its completion. It includes all delays, such as waiting for I/O operations, context switches, or sleep intervals. Wall clock time is measured as the actual duration perceived by a user, typically using timestamps recorded before and after the process runs.

\textbf{User time} refers to the amount of CPU time spent running code in user space. This includes the program’s own instructions and any library code it uses. It excludes time spent in the kernel or operating system. This metric is measured by the operating system and tracks how much CPU time was directly consumed by the application itself.

\textbf{System time} (or kernel time) accounts for the time spent by the CPU in the operating system kernel on behalf of the program. This includes handling system calls, managing I/O, allocating memory, and other interactions with hardware or privileged OS routines. Like user time, it is reported by the operating system’s process accounting.

\textbf{CPU utilization} is the percentage of total available CPU time that the process actively used during its lifetime. It is computed as the ratio of the sum of user and system time to the wall clock time. High CPU utilization indicates that the process is CPU-bound, meaning it spends most of its time doing computations. Low CPU utilization may suggest the process is I/O-bound or waiting on external events.

Together, these metrics offer a multifaceted view of a program’s execution profile. They help developers identify bottlenecks, assess performance regressions, and understand whether inefficiencies stem from computation, system overhead, or external delays.

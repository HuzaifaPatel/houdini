\chapter{Introduction}

Containers have become a cornerstone of modern cloud infrastructure, revolutionizing how applications are developed, deployed, and scaled, particularly within microservices architectures and DevOps workflows. Unlike hypervisor-based virtual machines (VMs), which each require a whole operating system and rely on a hypervisor for hardware virtualization, containers are lightweight, share the host system's kernel, and incur minimal overhead. This efficiency makes them exceptionally well-suited for continuous integration and rapid scaling, allowing organizations to optimize resource utilization and reduce costs while ensuring quick, consistent deployments. Furthermore, containers enable seamless portability by packaging all userspace dependencies into a unified image, thereby avoiding the common problem of environment-specific discrepancies. Yet, despite containers' numerous benefits, they also introduce new security challenges, especially where container confinement is concerned.

Linux kernel features such as \gls{cgroups} and \gls{namespaces} are designed to isolate container resources, processes, and networks. However, these mechanisms are not foolproof. Kernel vulnerabilities such as buffer overflows and privilege escalation bugs can allow malicious processes to bypass isolation boundaries entirely. At the same time, misconfigurations like granting unnecessary capabilities, mounting sensitive host directories, or enabling privileged mode can weaken a container's confinement from the start. These issues open the door to container escapes, where attackers break out of their isolated environment and interact directly with the host system. Once this boundary is breached, they may interfere with other containers, access sensitive data, or compromise the entire infrastructure.

We describe \gls{Houdini}, the first test suite for verifying container confinement. \footnote{Harry Houdini (1874–1926) was a world-famous escape artist and illusionist. The name “Houdini” is appropriate here because the framework tests whether containers can “escape” their confinement boundaries, much like Houdini escaped from locks, chains, and sealed enclosures.} It is an execution framework that runs test cases (\glspl{trick}, as we call them) inside a controlled VM to empirically evaluate security mechanisms. Given a \gls{Docker} container configuration (including the kernel, Docker, and runtime version), Houdini will instantiate the container in a standalone QEMU-based VM and perform tests to evaluate the container's security posture. Houdini can explore any user-defined security test, such as improper resource allocation, inadequate isolation, and insecure filesystem setups. Houdini is written in Python and provides an extension language for writing tricks.

Houdini is designed to provide a systematic approach, meaning container confinement mechanisms are tested automatically and in a consistent manner, rather than in an ad hoc or manual way. One of its primary goals is to evaluate whether container security features, such as namespaces, cgroups, \gls{seccomp}, and \gls{Linux capabilities}, are effectively enforcing isolation. Many container security tools rely on theoretical guarantees or static analysis \cite{clair}, but Houdini focuses on empirical validation by executing controlled security tests that verify the correct enforcement of security mechanisms. By doing so, Houdini ensures that container security mechanisms are correctly configured.

Houdini serves not only as a tool for testing container isolation but also as a means to optimize container configurations. By systematically simulating various tasks within different containers, Houdini can help determine the minimal set of privileges required for a container to perform its intended function (see Section \ref{sec:evaluating-docker-privileged-port-forwarding-restrictions}). For example, administrators can start with a container configured with broad privileges and then incrementally reduce permissions, such as Linux capabilities, seccomp filters, or resource limits, while monitoring task success. Houdini's testing framework will identify the point at which functionality is maintained while unnecessary privileges are removed, thereby pinpointing the least privilege configuration that still allows the container to operate effectively. Minimizing the privileges granted to a container reduces its attack surface, making it more difficult for an attacker to exploit vulnerabilities.

Although runtime monitoring and anomaly detection, such as with eBPF-based tracing \cite{findlay2021bpfcontain}, can provide immediate insights into container behavior, our goal isn't to implement an exhaustive, continuous surveillance system. Instead, we aim to focus on auditing and validating the underlying isolation mechanisms to ensure they are correctly configured and consistently enforced.

With the introduction of Houdini, several things are now possible in container security testing that were previously impractical. Before Houdini, testing whether container security features worked as expected across different versions of Docker, \gls{runc}, and the Linux kernel was tedious and manual. It was difficult to tell if a failure was due to a misconfiguration, a version-specific behavior, or a host system detail. Now, users can systematically test container security policies across hundreds of version combinations and get consistent results, no matter the host machine or time of execution. Houdini also makes it easy to spot silent failures, cases where a security policy appears to be applied, but is not enforced. This was hard to detect without controlled and repeatable experiments. Additionally, Houdini helps validate new defenses or configurations by running real-world attack simulations and comparing their behavior under different setups. This allows researchers and developers to observe how confinement mechanisms behave across Docker configurations, kernel versions, and runtime versions, and to catch regressions in security enforcement early. Here, \gls{regression testing} does not refer to testing Houdini itself, but to using Houdini as a framework for regression testing of container confinement. By systematically re-running the same tricks across different kernel, Docker, and runc versions, Houdini can detect regressions in security enforcement, in which previously functioning isolation guarantees silently weaken or fail after a software update. Houdini is primarily intended for experts in container security and systems research, who possess the technical background to configure complex test scenarios and interpret empirical results.


\section{Problem}

Containers are now a core part of how software is deployed. They’re used everywhere from large cloud systems to small edge devices because they help keep applications isolated, make it easier to manage dependencies, and allow services to scale efficiently. Their lightweight design and smooth integration with DevOps tools have made them the go-to choice across the industry. However, as containers are increasingly used to run critical or sensitive services, such as authentication systems, microservices, or data pipelines, ensuring their security becomes essential \cite{sultan2019container}. True isolation between containers, and between a container and the host system, doesn’t happen automatically. It relies on a range of security features built into the Linux kernel and container runtime. These include namespaces, cgroups, seccomp filters, \gls{AppArmor} or \gls{SELinux} policies, Linux capabilities, and filesystem restrictions. All of these work together to form the boundary that keeps containers safely confined.

The challenge, however, is that container confinement is not a monolithic entity. A container’s actual security posture depends on a complex and evolving set of mechanisms provided by the kernel and container runtime. Kernel features may be enabled or disabled, runtime behaviors can shift across Docker or runc versions, and default security profiles often change silently between distributions (See Section \ref{sec:evaluating-ptrace-enforcement-across-linux-distributions}). The sheer number of tunable settings, which we refer to as security knobs, creates a combinatorial explosion of possible configurations. These knobs include namespace settings, Linux capabilities, seccomp profiles, AppArmor or SELinux policies, cgroup limits, and more. Importantly, the goal is not to reduce the number of knobs, as they provide valuable flexibility and control. Instead, the real challenge lies in understanding what each knob does in practice and whether the intended confinement is being enforced as expected. Even experienced developers can overlook subtle misconfigurations, resulting in containers that appear secure but are missing critical enforcement. To make matters worse, tools like Docker rarely surface these issues through warnings or validation, allowing insecure setups to persist unnoticed.

These challenges highlight a broader problem: it is often difficult to tell whether container security settings are working as intended. Administrators may believe containers are isolated based on documentation or default behaviors, but in practice, policies can be silently overridden, misapplied, or broken by version changes. Sometimes, no explicit policy is set, and the system falls back on insecure defaults. In other cases, configurations conflict with one another, leading to unintentional privilege leaks. Even when no changes are made to container settings, updates to the kernel, Docker, or runc can subtly shift how security features behave. This creates a gap between how containers are supposed to be confined and how they behave in the real world. What’s needed is a way to test container security empirically and repeatedly, across versions and configurations, to uncover these unexpected behaviors before attackers do.

Despite the growing adoption of containers, there exists no systematic and empirical method to evaluate whether a container is confined. Existing tools primarily fall into two categories: static scanners that inspect images for known vulnerabilities, and policy generators that attempt to produce security profiles from application behavior. These tools are helpful but insufficient for our goal. They do not test the actual runtime behavior of a container in the context of its complete configuration and environment. There is a critical gap: developers have no means to verify whether their containers behave securely under realistic execution conditions and across the full range of kernel and runtime versions that may exist in production.

This lack of runtime validation creates a serious blind spot in container security. A container may pass static security checks, such as configuration audits or image scans, and still be vulnerable at runtime. This is because many security failures do not arise from obviously incorrect settings, but from subtle interactions between components, missing kernel support, or changes across versions of Docker, runc, or the Linux kernel. For instance, a seccomp profile designed to block dangerous system calls might silently fail if the underlying runtime or kernel does not support the necessary filtering features. Similarly, a container that is assigned limited Linux capabilities may still escape confinement due to a change in how the runtime applies namespace isolation or grants privileges internally. The container runs, the settings look correct, but the intended isolation is not enforced.

\section{Thesis Outline}

This thesis is made up of eight chapters and an appendix. Chapter 1 introduces the main problem: making sure containers are truly secure and properly confined. It explains why this is difficult in practice and motivates the need for a testing framework like Houdini. The chapter also highlights the key contributions of this work.

Chapter 2 gives background information to help readers understand how container security works. It covers the basics of Docker and containers, explains the difference between virtualization and containerization, and introduces key Linux features like namespaces, cgroups, capabilities, seccomp, AppArmor, SELinux, and \gls{Yama}. These are all essential tools used to isolate containers from each other and the host system.

Chapter 3 describes how Houdini was designed. It explains the system’s architecture and the main goals behind it, such as making tests reproducible, easy to scale, isolated from the host, flexible across different setups, and easy to debug. The chapter also gives examples of how Houdini can be used in practice.

Chapter 4 goes into the details of how Houdini was built. It describes how Buildroot is used to create a minimal virtual machine, how tests (called “tricks”) are defined using YAML-like files, and how the system uses Python and Flask to manage and run these tests. It also explains how Houdini handles \gls{version pinning} to make sure tests are consistent over time.

Chapter 5 shows how well Houdini works through a series of experiments. It proves that the system gives consistent results over time and across different machines, that it keeps the host safe by using virtual machines, and that it can support many different versions of Docker, runc, and the Linux kernel. It also includes performance tests to show that Houdini can handle many test cases efficiently.

Chapter 6 presents real-world case studies to show how Houdini can find problems in container security. These include testing a known vulnerability (CVE-2024-21626), checking if containers can interact with host processes, looking at privileged port restrictions, and testing how \gls{ptrace} enforcement works across different Linux distributions.

Chapter 7 reviews related work in the field of container and system security. It discusses other tools and research on topics like sandboxing, system call filtering, eBPF tracing, security frameworks like AppArmor and seccomp, and tools for scanning or testing containers. This chapter shows how Houdini fills a gap that existing tools do not address.

Chapter 8 wraps up the thesis with a summary of what was learned and suggestions for future work. This includes expanding Houdini to support more container runtimes, integrating it into CI/CD pipelines, and building a larger set of test tricks.

The appendix includes some preliminary performance benchmarking results. These tests measure aspects such as the time required to make the root filesystem, booting the VM, building Docker images, and executing specific commands. They give a basic view of how Houdini performs in practice.

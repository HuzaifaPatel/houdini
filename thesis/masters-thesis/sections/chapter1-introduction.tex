\chapter{Introduction}

Container-based workloads have become a cornerstone of modern cloud infrastructure, revolutionizing how applications are developed, deployed, and scaled, particularly within microservices architectures and DevOps workflows. Unlike hypervisor-based virtual machines (VMs), which each require a full operating system and rely on a hypervisor for hardware virtualization, containers are lightweight, share the host system’s kernel, and incur minimal overhead. This efficiency makes them exceptionally well-suited for continuous integration and rapid scaling, allowing organizations to optimize resource utilization and reduce costs while ensuring quick, consistent deployments. Furthermore, containers enable seamless portability by packaging all userspace dependencies into a unified image, thereby avoiding the common problem of environment-specific discrepancies. Yet, despite containers’ numerous benefits, they also introduce new security challenges, especially where container confinement is concerned.

Linux kernel features such as cgroups and namespaces provide resource, process, and network isolation for containers. However, this separation is not without issues. Kernel vulnerabilities, such as, buffer overflows or privilege escalation flaws can allow a process to circumvent the very mechanisms designed to confine it. Misconfigurations can similarly open holes in container security by granting unnecessary capabilities, mounting sensitive host directories, or running containers in privileged mode. Container escapes exploit these weaknesses to break out of the container’s resource and namespace isolation. Once an attacker gains elevated privileges or direct access to the host system, they can disrupt other containers, exfiltrate data, or compromise the entire infrastructure.

As container adoption has skyrocketed across industries, particularly in multi-tenant cloud environments, these security challenges have become more pronounced.

Tools such as network scanners aid in identifying misconfigurations, outdated software versions, and unintended service exposures, helping organizations proactively mitigate security risks. However, a significant gap remains in the context of containers. There are currently no standardized or widely adopted test suites designed specifically to evaluate container confinement, functionality, or isolation effectiveness. This absence leaves organizations to rely on ad hoc methods, which are often inadequate for uncovering subtle misconfigurations or ensuring robust confinement. Given the growing reliance on containerized environments in modern infrastructure, the development of comprehensive test suites tailored for containers is imperative.

We describe Houdini, the first test suite for verifying container confinement. Given a Docker container configuration (including the kernel, docker, and runc version), Houdini will instantiate the container in a standalone QEMU-based VM and perform tests (or \textit{tricks}, as we call them) to evaluate the container's security posture. Houdini can explore any user-defined security test such as improper resource allocation, inadequate isolation, and insecure filesystem setups. Houdini is written in Python and provides an extension language for writing tricks.

Houdini is designed to provide a systematic and reproducible approach to testing container confinement mechanisms. One of its primary goals is to evaluate whether container security features, such as (but limited to) namespaces, cgroups, seccomp, and Linux capabilities are effectively enforcing isolation. Many container security tools rely on theoretical guarantees or static analysis \cite{clair}, but Houdini focuses on empirical validation by executing controlled security tests that verify the correct enforcement of security mechanisms. By doing so, Houdini ensures that container security mechanisms are correctly configured.

Houdini is not only for testing container isolation but also as a means to optimize container configurations. By systematically simulating various tasks within different containers, Houdini can help determine the minimal set of privileges required for a container to perform its intended function. For example, administrators can start with a container configured with broad privileges and then incrementally reduce permissions, such as Linux capabilities, seccomp filters, or resource limits, while monitoring task success. Houdini’s testing framework will identify the point at which functionality is maintained while unnecessary privileges are removed, thereby pinpointing the least privilege configuration that still allows the container to operate effectively. Minimizing the privileges granted to a container reduces its attack surface, making it more difficult for an attacker to exploit vulnerabilities.

Although runtime monitoring and anomaly detection, such as with eBPF-based tracing \cite{findlay2021bpfcontain} can provide immediate insights into container behavior, our goal isn't to implement an exhaustive, continuous surveillance system. Instead, we aim to focus on auditing and validating the underlying isolation mechanisms to ensure they are correctly configured and consistently enforced.

With the introduction of Houdini, several things are now possible in container security testing that were previously impractical. Before Houdini, testing whether container security features worked as expected across different versions of Docker, runc, and the Linux kernel was tedious and manual. It was difficult to tell if a failure was due to a misconfiguration, a version-specific behavior, or a host system detail. Now, users can systematically test container security policies across hundreds of version combinations and get consistent results, no matter the host machine or time of execution. Houdini also makes it easy to spot silent failures, cases where a security policy appears to be applied, but is not actually enforced. This was hard to detect without controlled and repeatable experiments. Additionally, Houdini helps validate new defenses or configurations by running real-world attack simulations and comparing their behavior under different setups. This allows researchers and developers to see how confinement mechanisms behave across time, distributions, and system configurations, and to catch regressions early. In short, Houdini makes container security testing scalable, repeatable, and much more trustworthy.

\section{Motivation}

Containers are now a core part of how software is deployed. They’re used everywhere from large cloud systems to small edge devices because they help keep applications isolated, make it easier to manage dependencies, and allow services to scale efficiently. Their lightweight design and smooth integration with DevOps tools have made them the go-to choice across the industry. But as containers are increasingly used to run important or sensitive services like authentication systems, microservices, or data pipelines, making sure they are secure becomes essential \cite{sultan2019container}. True isolation between containers, and between a container and the host system, doesn’t happen automatically. It relies on a range of security features built into the Linux kernel and container runtime. These include namespaces, cgroups, seccomp filters, AppArmor or SELinux policies, Linux capabilities, and filesystem restrictions. All of these work together to form the boundary that keeps containers safely confined.

The challenge, however, is that confinement is not monolithic. A container’s actual security posture depends on an evolving ecosystem of configurations and software versions. Kernel features may be enabled or disabled, runtime behaviors may shift across Docker or runc updates, and default security profiles may silently change between distributions. Even worse, the combinatorial complexity of these settings what we call “security knobs” means that even experienced developers can easily overlook subtle misconfigurations. A container that appears secure may in fact be running without the intended enforcement mechanisms due improper configuration. Compounding the problem is the fact that Docker and other tools rarely provide explicit warnings or validation when requested security policies are not applied as expected.

Despite the growing adoption of containers, there exists no systematic and empirical method to evaluate whether a container is actually confined. Existing tools primarily fall into two categories: static scanners that inspect images for known vulnerabilities, and policy generators that attempt to produce security profiles from application behavior. These tools are useful but insufficient. They do not test the actual runtime behavior of a container in the context of its full configuration and environment. There is a critical gap: developers and operators have no means to verify whether their containers behave securely under realistic execution conditions and across the full range of kernel and runtime versions that may exist in production.

This lack of runtime validation creates a dangerous blind spot. A container may pass all static scans and appear properly configured, yet still be vulnerable because of version-specific regressions, unsupported features, or unforeseen interactions between configuration layers. For example, a seccomp profile may be ignored because the runtime does not support the required filters on a particular kernel. Similarly, a container granted limited capabilities may still break confinement due to a change in how runc or crun interprets namespaces. These issues are difficult to detect without executing the container under controlled test scenarios. The community lacks a principled framework for surfacing these discrepancies.

The motivation behind Houdini is to address this unmet need. Houdini provides a reproducible and extensible framework for empirically validating container confinement. It enables users to specify container configurations by defining everything from capabilities to user mappings, and execute real tests inside a clean, minimal virtual machine environment. Unlike static tools, Houdini observes how containers behave in practice. Its trick-based architecture allows users to encode confinement expectations (e.g., “this container should not read this file” or “this container should not kill a sibling process”), and determine whether those expectations hold across different combinations of Docker, runtime, and kernel versions.

By making container confinement observable, Houdini empowers researchers, developers, and security auditors to gain confidence in their deployments. Rather than assuming that a security knob is being enforced, users can test it directly. Houdini encourages a shift from blind trust in documentation and defaults toward evidence-based validation. This approach not only improves the robustness of individual container configurations but also contributes to the broader understanding of how isolation mechanisms evolve over time, and where they may fail.

\section{Thesis Outline}

This thesis is organized into eight chapters and an appendix, each contributing to a systematic exploration and evaluation of container confinement through the Houdini framework. 

Chapter 1 introduces the motivation behind this research, defines the container confinement problem, and outlines the key contributions of the thesis. It also highlights the challenges in container security and explains how Houdini enables reproducible, version-pinned security testing. Chapter 2 provides the necessary background, covering core technologies such as containers, Docker, virtualization, cgroups, namespaces, Linux capabilities, seccomp, AppArmor, SELinux, and Yama. These concepts are important for understanding the mechanisms that underpin container confinement.

Chapter 3 surveys related work in the field, including vulnerability scanners, regression testing frameworks, sandbox and VM escape research, offensive security tools, and prior systems built on seccomp and AppArmor. This chapter identifies the limitations of existing approaches and establishes the need for a more empirical and extensible framework like Houdini. Chapter 4 presents the design of Houdini, focusing on system architecture, design goals such as reproducibility and scalability, and how the framework achieves isolation and transparency. Chapter 5 follows with a detailed discussion of the implementation, including the YAML-based trick system, the Python execution pipeline, version management, VM setup, and host integration components.

Chapter 6 evaluates Houdini’s capabilities through empirical testing, demonstrating its effectiveness in reproducing results across machines and time, validating isolation, supporting version variability, and executing large-scale trick batches. Chapter 7 applies Houdini to real-world case studies, including an analysis of CVE-2024-21626, host process manipulation, privileged port binding, and ptrace behavior across distributions. These examples showcase Houdini’s practical utility in uncovering security inconsistencies. Finally, Chapter 8 concludes the thesis by summarizing key findings and suggesting future research directions, such as extending Houdini to additional container runtimes and exploring deeper integration with CI/CD pipelines. The appendix provides technical details of the experimental setup, including performance benchmarking and configuration parameters used during testing.

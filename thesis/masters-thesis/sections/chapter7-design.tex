\chapter{Design}

The design of Houdini is guided by a set of core principles aimed at enabling reliable, large-scale testing of container security confinement. At its core, Houdini seeks to ensure \textbf{reproducibility}, so that each test yields the same result when run under identical conditions, and behaves consistently across time and environments. This is achieved by pinning exact versions of all key components, such as the kernel, Docker, and runc—and executing each test inside a clean, stateless VM.

Alongside reproducibility, Houdini is also built for \textbf{scalability}. Despite running one test at a time, the framework can execute large test matrices automatically, without requiring users to script each case manually. Instead, users define test configurations declaratively, and Houdini expands them into all valid combinations and runs each as an isolated test case. This makes it easy to scale experiments across hundreds or thousands of container configurations with minimal effort.

It also enforces strong \textbf{host isolation} by executing potentially dangerous container workloads inside tightly controlled VMs, preventing any impact on the host system. The framework supports \textbf{flexibility across configurations}, allowing users to test a wide range of Docker flags, Linux capabilities, AppArmor profiles, and runtime versions. It emphasizes \textbf{performance} by reducing overhead through lightweight VMs and precompiled binaries. Finally, Houdini prioritizes \textbf{transparency and debuggability} by logging all configuration inputs and test results in a structured format, enabling users to trace and interpret outcomes. The rest of this chapter describes how each of these design goals are achieved in Houdini.



\section{System Architecture}
Houdini is a modular framework designed to enable secure and reproducible testing of container confinement across diverse configurations. Its architecture is divided into host-side and guest-side components, each with a specific and isolated role. This separation of responsibilities ensures strong test isolation, determinism, and ease of scaling to large test matrices.

On the host side, users interact with Houdini through a lightweight Python-based command-line interface (CLI). The CLI is responsible solely for parsing user input, such as selecting a trick, running a VM, or building the Buildroot-based filesystem. It does not manage execution logic itself. Once the user provides input to run a trick, the CLI delegates control to a programmatic API, which is responsible for managing the execution flow.

In Houdini, a single test case is referred to as a \textit{trick}, which encapsulates a specific container security scenario. Each trick consists of three parts: a configuration file, a Dockerfile, and an executable script. The configuration file defines how the container should be launched, including its security parameters and references to the other two components. The Dockerfile specifies how to build the container image, installing dependencies and copying the script. The trick script (which can be written in any buildroot-supported language) contains the logic for performing the security test, such as attempting to read a protected file or escalate privileges. It is expected to emit a clear "pass" or "fail" message based on whether the action succeeds.

The API communicates with a Flask-based server that manages the lifecycle of a QEMU-based VM. Each trick is executed in a newly booted VM, built from a minimal, stateless image generated by Buildroot. This clean-slate approach ensures that every test runs in a predictable and reproducible environment, free from side effects caused by previous tests or host-level conditions. No persistent data is shared between executions, and the guest environment is intentionally stripped down. No background daemons, user services, or external dependencies exist inside the VM unless explicitly configured by the test.

The Flask server sends the test configuration and trick information into the VM via an HTTP request. Inside the guest system, a listener process continuously waits for such requests. When a test arrives, the listener prepares the environment by building a Docker image using the specified Dockerfile, and launches a container with the defined security parameters. These includes, but is not limited to Linux capabilities, namespace settings, seccomp profiles, AppArmor rules, volume mounts, and user privileges. The container is then launched with these constraints, ensuring that the environment inside aligns exactly with the configuration described by the user.

Once the container is running, the trick script is automatically executed. This script could perform a targeted security check, such as reading protected files, sending signals across namespaces, or attempting privilege escalation, and prints a clear "pass" or "fail" message to standard output. The listener captures the output, exit code, and any standard error, and sends this result data back to the host’s Flask server. On the host, the result is logged in a \texttt{.log} file. This enables precise traceability, post-run analysis, and side-by-side comparison of multiple configurations.

\section{Reproducibility}

A central design goal of Houdini is to ensure that container security tests are reproducible, meaning that the same test, when run under the same conditions, will produce identical results regardless of when or where it is executed. Houdini achieves reproducibility through a combination of strict version control, deterministic execution environments, and isolation from external influences.

Each test in Houdini runs inside a new VM that is freshly booted from a Buildroot-based image. This means that every test starts in a clean environment, with no leftover data or settings from previous runs. As soon as a test finishes, the VM is thrown away, so nothing carries over into the next test. This helps make sure that results are consistent and not affected by what happened before.

The Buildroot image is very minimal, it only includes what’s absolutely needed to run the test. It doesn’t have background programs like update services, SSH, or scheduled tasks, which could introduce randomness or unexpected behavior. By keeping things simple and stripped down, Houdini ensures that the only things running in the VM are the ones the user specifically added for the test.

This clean and predictable setup makes it much easier to get the same results every time a test is run. Even if a trick is repeated many times or on different machines, the outcome stays consistent because the environment is always the same.

To avoid changes caused by updates or host system drift, Houdini uses a version pinning mechanism. Version pinning refers to the practice of explicitly specifying and using fixed versions of software components rather than relying on the latest or system-default versions. This ensures that tests always use the same binaries, regardless of when or where they are run, and prevents unexpected changes in behavior due to automatic updates or upstream changes. In the context of container security testing, version pinning is essential because even minor updates to Docker, runc, or the kernel can introduce subtle behavioral differences.

To ensure reproducibility, Houdini enforces strict control over the versions of all critical software components involved in test execution. Critical software components include the Linux kernel, Docker, and runc. Container behavior can change significantly between versions of these tools, even when the container configuration remains unchanged. To eliminate variability caused by software drift, Houdini adopts a comprehensive version pinning strategy.

Each test in Houdini explicitly declares the versions of Docker, runc, and the Linux kernel to be used. These components are downloaded from official release sources, precompiled, and stored in a structured local cache. This guarantees that the same binaries are reused across repeated runs. For example, if a trick is intended to evaluate a vulnerability in runc 1.0.0-rc2 but verify its resolution in 1.1.12, Houdini retrieves the exact binaries for each version and uses them directly, without relying on system package managers or external internet access. Similarly, multiple Docker versions such as 20.10.3, 23.0.1, or 27.0.3 can be tested against the same logic to study behavioral drift.

Houdini uses an overlay filesystem to make testing both efficient and consistent. Instead of rebuilding the entire VM image from scratch for every test case, it starts with a common, precompiled base image generated using Buildroot. On top of this base, Houdini layers only the necessary test-specific components, such as particular versions of Docker, runc using an overlay. This means the same lightweight VM can be reused across multiple tests, while still ensuring that each test runs with precisely the versions of the tools it is supposed to evaluate. By isolating these versions from the host system, Houdini guarantees a controlled and repeatable testing environment regardless of changes on the host machine.


\section{Scalability}

Houdini is built to support large-scale container security evaluations without requiring extensive manual effort or scripting. While each test is executed serially to maintain isolation and determinism, the overall framework is designed to scale efficiently across hundreds or thousands of test configurations.

At the core of Houdini’s scalability is its matrix-based testing model. Instead of manually defining each test case, users specify sets of options, such as Docker flags, Linux capabilities, namespace settings, or user identities that they want to explore. Houdini then automatically generates the Cartesian product of these options, producing a comprehensive list of test cases. This allows for systematic evaluation of all meaningful combinations without the need for custom scripts or duplicated logic.

Houdini’s internal scheduler ensures that each test is executed in isolation within a clean virtual machine. It manages the lifecycle of each VM, booting, running the trick, capturing the output, and tearing down the environment, without user intervention. This automation allows large batches of tests to be run back-to-back, making it possible to evaluate broad security surfaces such as how different container configurations behave across Docker and runc versions, or how changes to namespace settings influence process visibility.

To handle high test volumes efficiently, Houdini optimizes performance through the reuse of lightweight Buildroot-based VM images and precompiled runtime binaries. It avoids rebuilding environments from scratch and instead layers test-specific components on top of a shared base image using an overlay filesystem. This not only saves time but also reduces system resource usage.


\section{Host Isolation}

Houdini is explicitly designed to safely execute potentially dangerous or privilege-escalating container workloads without risking the security or stability of the host system. This is achieved through strict isolation enforced by running all tests inside QEMU-based virtual machines (VMs). This approach ensures strong separation between the test environment and the host, providing both safety and reproducibility.

Each trick is executed within its own QEMU VM, which serves as a hardware-level isolation boundary. Unlike approaches that rely solely on Linux container isolation, this VM-level sandbox guarantees that even if a container successfully escapes its sandbox, it remains confined to the guest environment. No test payload can reach or affect the host operating system, making Houdini suitable for executing untrusted or potentially malicious code safely.

Houdini further avoids any direct linkage between the host and the guest environment. No host directories are mounted into the guest, and no namespaces are shared between the host and VM. Containers are launched entirely within the guest’s user, mount, PID, and network namespaces. As a result, containers inside the VM have no visibility into host processes, filesystems, or resources. Flags such as \texttt{--pid=host} only apply within the VM context and never expose the physical host-level information.

Houdini’s reliance on QEMU offers several key advantages over alternative virtualization platforms such as VMware or VirtualBox. First, QEMU supports both full system emulation and hardware-assisted virtualization through KVM, allowing it to run unmodified Linux kernels and minimalist userland environments generated by Buildroot. It can boot directly from a raw kernel image (e.g., \texttt{bzImage}) without requiring a bootloader or full OS, enabling precise control over the testing environment.

Second, QEMU supports complete command-line configuration, including CPU model, memory size, disk images, network interfaces, and serial ports. This makes it ideal for automated and reproducible test workflows. In contrast, VMware and VirtualBox rely on graphical interfaces and more static configurations, which hinder automation and scripting.

Third, QEMU is architecture-agnostic. It supports x86, ARM, MIPS, RISC-V, and other architectures, allowing for cross-platform testing. While Houdini currently focuses on x86\_64, the use of QEMU ensures that it can easily be extended to other architectures in the future. VMware and VirtualBox are limited to x86-based virtualization and do not support full system emulation for other CPU architectures.


\section{Transparency and Debuggability}

Houdini is designed not only to execute tests reliably, but also to make results easy to interpret and debug. To support transparency and effective diagnosis, the framework implements structured logging for every test.

Each test execution generates a structured log file that includes the container's standard output, standard error, exit code, and a timestamped record of the configuration parameters used. These logs are stored in a standardized format and organized by test ID, making it straightforward to trace the provenance of any result. Whether a trick passed, failed, or encountered an unexpected runtime error, the corresponding log provides clear visibility into what occurred during execution.

Houdini also tags every test result with its full configuration metadata. This includes the container runtime version, kernel version, Docker flags, capabilities, namespace modes, and any AppArmor or seccomp profiles in effect. These tags are recorded alongside the test result, enabling automated analysis, filtering, and regression tracking. For example, a user can easily compare how the same trick behaves under different runc versions or with different namespace settings, based on the metadata attached to each result.


\subsection{Other Design Goals}
In order to support the use cases mentioned above, we designed Houdini with the following goals:

\begin{enumerate}
  \item \label{dg:repro}\textit{Reproducible Results.} A key goal of Houdini is to ensure that tests yield consistent and repeatable results. By controlling system variables and maintaining a structured testing environment, Houdini allows researchers and practitioners to compare results across different system configurations and security policies.

  \item \label{dg:container}\textit{Separation from the Host.} Houdini is designed to run tests inside a controlled containerized environment within a virtual machine (VM), ensuring that even if a trick triggers a security vulnerability, it does not compromise the host system running the tests. This design choice enhances the safety of security evaluations, preventing unintended side effects on the underlying infrastructure.

  \item \label{dg:test}\textit{Test Case Expressiveness.} Houdini tricks should be maximally expressive, such that some combination of steps can be used to achieve and test any desired result. It should be possible to define a new Houdini trick and modify existing tricks without modifying the Houdini binary. Moreover, it should be clear from reading a defined trick precisely what steps are involved, the consequences of each step passing or failing, and the overall nature of the exploit being tested.

  \item \label{dg:failures}\textit{Focus on Observing Failures, Not Preventing Them.} Houdini is built to identify security weaknesses rather than defend against attacks.
\end{enumerate}

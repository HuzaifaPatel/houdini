\section{Building a VM via Buildroot}

Buildroot is an open-source tool that automates the process of building custom Linux systems, primarily for embedded or minimal environments. It simplifies the creation of a complete Linux distribution by compiling the Linux kernel, root filesystem, bootloader (if needed), and a wide range of userland tools from source. Users define their system configuration through a menu-driven interface or configuration files, specifying which components to include, which versions to use, and how the resulting image should be structured. Because it builds everything from scratch using version-pinned sources, Buildroot is ideal for producing highly reproducible and minimal Linux environments. In the context of Houdini, Buildroot enables precise control over the guest VM, ensuring that all kernel features and userland components required for container security testing are present, consistent, and isolated from host system variability.

The Buildroot construction pipeline (see~\ref{fig:buildroot-construction})is a sequential process that transforms high-level system specifications into a bootable Linux image. It begins with a configuration phase, where users define the system's architecture, target packages, kernel version, and root filesystem type using a `.defconfig` file or the menuconfig interface. Once configured, Buildroot fetches all required source code, including the Linux kernel, toolchains, and any selected userland packages, and applies patches if specified. These sources are then compiled from scratch using a cross-compilation toolchain that Buildroot generates specifically for the target architecture. As part of this process, the root filesystem is assembled by installing all compiled binaries and scripts into a staged directory. 


To enable container runtime support in a virtualized environment, Houdini must activate several groups of kernel features beyond just namespaces and cgroups. One such group includes networking and virtualization options, which are essential for simulating realistic container deployments. Enabling kernel options like \textit{CONFIG\_VETH}, \textit{CONFIG\_BRIDGE}, \textit{CONFIG\_MACVLAN}, and \textit{CONFIG\_VXLAN} allows containers within the guest VM to create and use virtual Ethernet devices, participate in bridged networks, and simulate more complex network topologies. These features are critical when testing container isolation at the network layer or evaluating capabilities such as port forwarding, network namespaces, or virtual NICs. Similarly, \textit{CONFIG\_NETFILTER}, \textit{CONFIG\_NF\_NAT}, and related options enable firewall rules, NAT, and packet filtering within containers, capabilities that many real-world container setups rely on and which are required to run Docker's iptables-based networking stack.

In addition to networking, Houdini must support advanced filesystem operations that are frequently used by container runtimes. Docker relies heavily on layered filesystems to manage images and containers. To this end, enabling \textit{CONFIG\_OVERLAY\_FS} allows the use of OverlayFS, the default storage driver for Docker. \textit{CONFIG\_BTRFS\_FS} is included to support setups using Btrfs as an alternative union filesystem with snapshotting features. Additionally, \textit{CONFIG\_EXT2\_FS} ensures basic compatibility for traditional disk images used in Houdini's root filesystem. Without these filesystems enabled, many containers would fail to start due to missing storage backend support.

Another critical group of options revolves around virtual I/O and hypervisor support, which is essential in QEMU-based virtual machines. Enabling \textit{CONFIG\_VIRTIO\_NET}, \textit{CONFIG\_VIRTIO\_BLK}, and \textit{CONFIG\_VIRTIO\_PCI} allows the guest VM to communicate efficiently with the host through QEMU's paravirtualized drivers. These options improve I/O performance, reduce emulation overhead, and ensure compatibility with typical QEMU virtual hardware. Without these, the guest VM may fail to boot correctly or experience degraded performance, especially during heavy I/O operations such as pulling container images or writing logs.

Finally, several security and cryptographic features are enabled to mirror real-world deployments and ensure complete runtime functionality. These include \textit{CONFIG\_SECCOMP} and \textit{CONFIG\_SECCOMP\_FILTER} for syscall filtering, \textit{CONFIG\_SECURITY\_APPARMOR} for enforcing AppArmor profiles, and cryptographic primitives like \textit{CONFIG\_CRYPTO\_GCM}, \textit{CONFIG\_CRYPTO\_SEQIV}, and \textit{CONFIG\_CRYPTO\_GHASH}. Docker and runc depend on these options to enforce container restrictions and protect against kernel-level attacks. Without them, security policies such as seccomp profiles or AppArmor confinement would silently fail, leading to inaccurate or incomplete test results.

By carefully assembling this kernel configuration, Houdini ensures that every kernel compiled through Buildroot is not only compatible with Docker and `runc`, but also remains minimal, reproducible, and isolated from host system dependencies. This tailored defconfig plays a critical role in enabling full container runtime functionality inside the guest while preserving the deterministic nature of the testbed.

A key feature of Houdini's Buildroot-based design is its use of the overlay filesystem mechanism. Buildroot allows users to inject arbitrary files into the target root filesystem through an overlay directory. Houdini takes advantage of this by maintaining a structured overlay that contains all required runtime components, custom configuration files, and initialization scripts. For example, the overlay includes statically compiled versions of Docker Engine, `runc` for each version being tested. These binaries are placed in appropriate locations such as `/usr/bin`, ensuring they are accessible at runtime within the VM without requiring package installation or network access within the guest. While Buildroot includes official packages for Docker and `runc`, Houdini deliberately avoids using them. This decision stems from the fact that many older versions of Docker and `runc` (which are critical for longitudinal security analysis) are no longer supported or even buildable within the current Buildroot ecosystem. Buildroot frequently removes or breaks compatibility with older software versions due to upstream changes, deprecated dependencies, or toolchain incompatibilities. As a result, attempting to evaluate historical versions of container runtimes using Buildroot's native package management would lead to build failures. By embedding all required components directly into the root filesystem at build time, Houdini avoids reliance on dynamic installation, networking, or user intervention. The overlay mechanism not only simplifies the build process but also strengthens reproducibility and isolation, which are key pillars of Houdini's design.

In addition to binaries, the overlay contains service definitions and startup scripts that initialize the environment when the VM boots. One critical element is the embedded Python Flask server, which runs automatically inside the guest and listens for incoming test instructions from the host. This server enables Houdini to remotely execute "tricks" from the physical host to the VM. Configuration files, test logic, and Docker files are also placed into the overlay, ensuring they are bundled directly into the root filesystem without external dependencies.

The final output of the Buildroot construction pipeline consists of a complete, bootable Linux system tailored for container security testing. Specifically, Buildroot produces two critical artifacts: a compressed Linux kernel image (`bzImage`) and a root filesystem image (e.g., `rootfs.ext2`). The `bzImage` contains the monolithic kernel with all necessary container-related features enabled, including namespaces, cgroups, AppArmor, and virtual I/O drivers. The `rootfs.ext2` image is a minimal Linux environment populated with userland tools such as BusyBox, Python 3, the embedded Flask API server, and pre-injected container runtimes like Docker and `runc`, along with all relevant test scripts and configuration files. These outputs are stored under the `output/images/` directory within the Buildroot tree and are used directly by Houdini to boot a virtual machine via QEMU. Together, they form a fully isolated and reproducible guest environment, allowing for deterministic execution of container-based tricks and security tests, independent of the host system's configuration.

\section{Houdini Client}

The Houdini client is a Python-based orchestration tool that runs on the host machine and serves as the primary interface for executing tricks. It is responsible for coordinating the entire lifecycle of a test, including selecting specific versions of Docker and `runc`, launching the corresponding Buildroot-based VM via QEMU, injecting prebuilt container tricks, and collecting results. The client exposes a command-line interface (CLI) that allows researchers to run tricks. Once the VM is running, the client communicates with the guest's embedded Flask server over a forwarded network port, issuing trick execution requests and monitoring their outcome. This separation between host-side control logic and guest-side execution logic ensures that experiments remain reproducible, isolated, and portable across systems. The client also handles logging and output parsing.

\section{YAML-Like Trick Definition}
\label{sec:yaml-trick}

Houdini supports two modes for defining and executing tricks. The first is a YAML-like approach where a single trick is fully specified through a standalone configuration file (see~\ref{fig:version-pinning-configuration-implementation}). This method is ideal for running individual tests with carefully controlled settings, making it well-suited for targeted investigations of container confinement. The second mode is a Python-based approach that allows users to define parameter sets as lists, which Houdini expands into a Cartesian product to form a complete test matrix. For example, Docker configuration parameters can be defined in Python, and Houdini will automatically generate all combinations to be tested.

The YAML-like Trick definition is one of two ways to define a trick in Houdini. In this section, we will go through the implementation of it and provide examples of its use.

Each trick in Houdini is composed of three modular components that work together to define and execute a container-based security test: a configuration file, a trick script, and a Dockerfile. The configuration file (see~\ref{sec:configuration}) is a YAML-like document that specifies the Docker parameters for launching the container, including security-related settings such as Linux capabilities, namespace modes, AppArmor profiles, user privileges, and resource limits. These parameters are parsed by Houdini and translated directly into Docker's Python SDK, ensuring that containers are created with precise and repeatable configurations.

The second component is the trick file (see~\ref{sec:trick_file}), which contains the logic of the test and is executed inside the container. It is typically written in Python or Bash. This script attempts a specific action, such as reading a sensitive file, sending a signal to a process, or escalating privileges, and reports the outcome by printing a success or failure message, or however your implementation wishes to output it. The semantics of what constitutes a pass or fail are entirely defined by the script, giving users complete control over the evaluation criteria.

The final component is the Dockerfile, which builds the container image and defines the runtime environment. It includes instructions for copying the trick file into the container by using the \textit{COPY} instruction/directive. We also use the Dockerfile to install any necessary dependencies, and specify the base image to use.

Next, we will explain each of these files in more detail.

\subsection{Configuration File}
\label{sec:configuration}

Each Houdini trick begins with a configuration file, written in YAML-like format, that defines the runtime parameters used to launch the container. This file acts as the Docker command for how the container is constructed and executed. It specifies a range of Docker options including Linux capabilities (via \texttt{cap\_add} and \texttt{cap\_drop}), namespace settings (such as \texttt{pid\_mode} and \texttt{userns\_mode}), resource limits (e.g., \texttt{cpu\_shares}, \texttt{mem\_limit}), volume mounts, user identity, and security options such as AppArmor profiles or seccomp settings. See~\ref{fig:configuration-file} for an example.

The configuration is declarative and follows a structured YAML-like schema that maps directly to Docker's Python SDK API. For example, if a user wants to disable privilege escalation, enable a read-only filesystem, or run the container as a non-root user with dropped capabilities, these settings can be encoded clearly in the configuration file by giving it a simple \textit/t{True} or \textit{False} value. This abstraction allows users to focus on the security scenario being tested without needing to handcraft long and error-prone Docker command-line arguments.

When Houdini executes a test, the CLI parses the YAML-like configuration and validates it before test execution begins. It checks for required fields, ensures that runtime versions and trick paths are valid, and performs consistency checks to catch errors like incompatible or conflicting flags. Once validated, the configuration is sent to the trick listener and translated into a Docker run command within the guest environment. 

The configuration file is parsed using the parse\_trick\_and\_run() function (see~\ref{fig:configuration-implementation}). This function serves as the entry point for executing a trick. This function begins by extracting the container name from the provided arguments and then checks if a container with the same name already exists on the system. If so, it terminates and removes the existing container to ensure a clean test environment and guarantee reproducibility.

After cleanup, Houdini changes its working directory to the trick path specified in the configuration. This path typically contains the Dockerfile and the trick script. It then calls build\_docker\_image(), which uses the Docker Python SDK to construct a container image from the Dockerfile. This image is tagged with the container name for easy reference. Once the image is built, Houdini proceeds to launch the container using run\_docker\_container(), passing all configuration parameters such as capabilities, network settings, user identity, namespace modes, and resource limits directly into the Docker API call. These values are extracted from the parsed configuration using key-index lookups based on the order in which they appear in the configuration file.

Inside run\_docker\_container() (see~\ref{fig:running-a-docker-container-implementation}), the Docker container is created and run in detached mode with a pseudo-TTY enabled. The standard output from the container is streamed live to the console using Python's codecs.iterdecode, which allows real-time observation of the trick's behavior to the terminal running Houdini. In other words, this allows all the stdout from the trick file to be redirected to the terminal running Houdini, so that the user can view the status of the trick.

\subsection{Trick File}
\label{sec:trick_file}

The trick script is the core component that defines the actual test logic to be executed inside the container. This script is typically written in a high-level language such as Python or Bash and is copied into the container during the build process specified by the Dockerfile. But, first, it is copied into the VM using a custom overlay filesystem script. Once the container is launched with the desired configuration, the trick script runs automatically and attempts a specific action, such as reading a sensitive file, accessing a kernel interface, or interacting with another process. Its purpose is the discretion of the implementer of the trick file.

Houdini does not impose restrictions on the scripting language used, though Python and Bash are most commonly employed due to their simplicity and compatibility with minimal container environments. The scripting interface is straightforward: the script performs a predefined action and prints a result indicating whether the trick passed or failed. These results are captured via standard output by the trick listener running inside the guest VM. The listener uses these outputs, along with exit codes, to classify the outcome of the test.

The evaluation criteria are entirely defined within the trick script, giving users complete control over what constitutes success or failure. This flexibility allows Houdini to support a wide range of test types, from low-level privilege checks to higher-level behavioral verifications. Scripts can also emit additional diagnostic messages to aid in debugging or deeper analysis to \textit{STDOUT}.

Below is an example of a simple Python trick script that tests whether the container can read the contents of the \texttt{/etc/shadow} file. Under standard Docker security settings, access to this file should be restricted. If the script is able to read it, the trick is considered to have failed, indicating a misconfiguration or insufficient isolation. Otherwise, it passes.

\begin{figure}[H]
\caption{Example trick implementation that checks for read access to \texttt{/etc/shadow}.}
\label{fig:trick-script}
\begin{lstlisting}[language=Python, numbers=left, numberstyle=\tiny, stepnumber=1, breaklines=true, frame=single, backgroundcolor=\color{gray!10}, basicstyle=\ttfamily\scriptsize, showspaces=false, showstringspaces=false]
import os

def check_shadow_access():
    path = "/etc/shadow"
    if os.path.exists(path):
        try:
            with open(path, 'r') as f:
                print("Able to read /etc/shadow:")
                print("Trick passed")
        except PermissionError:
            print("Permission denied to read /etc/shadow.")
            print("Trick failed")
        except Exception as e:
            print(f"Unexpected error: {e}")
            print("Trick failed")
    else:
        print("/etc/shadow does not exist.")
        print("Trick failed")

check_shadow_access()
\end{lstlisting}
\end{figure}


This example demonstrates how a trick can evaluate a specific security assumption, file access control in this case, and produce a deterministic result that Houdini can log and interpret. More advanced tricks may incorporate conditionals, environment checks, or IPC mechanisms, but the basic structure remains the same: run a check and report a pass/fail outcome in a transparent and reproducible manner.



\subsection{Dockerfile}

The Dockerfile is responsible for setting up the container's runtime environment so that the trick script can execute reliably and with all necessary dependencies. It defines how the container image is built, including the selection of a base image, the installation of packages or libraries required by the trick script, and the inclusion of the trick file itself.

Tricks in Houdini can be written in a variety of languages, such as Python or Bash, so the Dockerfile must ensure that the corresponding runtime (e.g., the Python interpreter or Bash shell) is available inside the container. This often involves installing system packages using the package manager provided by the base image, for example, using \texttt{apt} in Debian-based images or \texttt{apk} in Alpine.

Another essential part of the Dockerfile is copying the trick script into the container's filesystem. This step ensures that the logic defined by the user is available at a known path when the container starts. Houdini standardizes this by copying the trick to a predefined directory (e.g., \texttt{/houdini/trick.py}) so that all containers follow the same execution convention.

The base image is selected based on the needs of the trick. Lightweight images like Alpine Linux are often preferred for simple tests because of their small size and fast startup time. However, more feature-rich images like Debian or Python-based official images may be used when additional dependencies or language runtimes are required.

Finally, the Dockerfile specifies an entrypoint or \texttt{CMD} directive to automatically run the trick script when the container launches. This ensures that the trick executes without requiring user intervention or manual commands. The entrypoint is usually a direct call to the interpreter (e.g., \texttt{python3 /houdini/trick.py}).

The example in~\ref{fig:dockerfile-example} demonstrates a simple Dockerfile used in Houdini to run a Python-based trick. It uses the official Python image, copies the trick from the VM to the container, and sets the default command to execute the script.

\begin{figure}[H]

\label{fig:dockerfile-example}
\begin{lstlisting}[numbers=left, numberstyle=\tiny, stepnumber=1, breaklines=true, frame=single, backgroundcolor=\color{gray!10}, basicstyle=\ttfamily\scriptsize, showspaces=false, showstringspaces=false]

This Dockerfile is minimal yet sufficient for running Python scripts inside a container. It illustrates the typical pattern used in Houdini to prepare containers in a consistent and reproducible manner. More complex tricks may extend this file to install additional packages, configure environment variables, or mount external resources, but the core structure remains largely the same.

In addition to supporting single-trick YAML-like definitions, Houdini provides a Python-based mechanism to define a matrix of configurations by specifying Docker configuration parameters as lists. Houdini automatically expands these parameters into a Cartesian product and generates a full suite of test cases. This approach is powerful for scaling up experiments, allowing researchers to explore the interaction of various container runtime settings systematically.

\section{Flask Server}

The Flask server plays a central role in Houdini's architecture by acting as the primary communication bridge between the physical host system and the guest VM. Once the QEMU-based VM boots, it establishes a connection to this Flask server to initiate trick execution. The server runs as a lightweight HTTP service on the host, exposing a set of well-defined endpoints that orchestrate the full test workflow. The Flask server is automatically started with the help of a BusyBox init script (see~\ref{lst:start-flask-server}).

\begin{lstlisting}[language=python, caption={BusyBox init file that starts the Flask server}, label={lst:start-flask-server}, numbers=left, numberstyle=\tiny, stepnumber=1, breaklines=true, frame=single, backgroundcolor=\color{gray!10}, basicstyle=\ttfamily\footnotesize, showspaces=false, showstringspaces=false]
#!/bin/sh
# Description: Example service script

PATH=/sbin:/bin:/usr/sbin:/usr/bin:/usr/local/bin
DAEMON=/usr/bin/python3
DAEMON_ARGS="/houdini/server.py"
PIDFILE=/var/run/houdini-server.pid
LOGFILE=/var/log/houdini-server.log

case "$1" in
    start)
        echo "Starting my service..."
        $DAEMON $DAEMON_ARGS >> $LOGFILE 2>&1 &
        ;;
    stop)
        echo "Stopping houdini-server..."
        kill $(cat $PIDFILE)
        ;;
    restart)
        echo "Restarting houdini-server..."
        $0 stop
        sleep 1
        $0 start
        ;;
    *)
        echo "Usage: $0 {start|stop|restart}"
        exit 1
        ;;
esac

exit 0
\end{lstlisting}

The core endpoints exposed by the server are \texttt{/server-status}, \texttt{/version-status}, \texttt{/run-trick}, and \texttt{/run-command-in-vm}. The \texttt{/server-status} endpoint is used for health checking and indicates whether the Houdini server is actively running on the host. This enpoint uses the subprocess module to check whether a specific process is running on the system. It executes the \textit{pgrep -f <service\_name>} command, which searches for all currently running processes whose full command lines match the given service name. In our case, the servie name is \textit{/usr/bin/python3 /houdini/server.py}. The stdout=subprocess.PIPE option captures the output (i.e., the matching process IDs), allowing the script to access the result programmatically. The check=True flag ensures that if no matching process is found, the command will raise a subprocess.CalledProcessError, which can be used to detect and handle the case where the service is not running.

\begin{lstlisting}[language=python, caption={Server health check endpoint}, label={lst:server-status}, numbers=left, numberstyle=\tiny, stepnumber=1, breaklines=true, frame=single, backgroundcolor=\color{gray!10}, basicstyle=\ttfamily\footnotesize, showspaces=false, showstringspaces=false]
@app.route('/server-status', methods=['GET'])
def server_status():
    if is_service_running('/usr/bin/python3 /houdini/server.py'):
        response_data = str(True)
        return make_response(response_data, 200)
    else:
        response_data = str(False)
        return make_response(response_data, 503)


def is_service_running(service_name):
    result = subprocess.run(['pgrep', '-f', service_name], check=True, stdout=subprocess.PIPE)

    if not result.returncode:
        return True
    return False
\end{lstlisting}

For debugging and exploratory testing, the \texttt{/run-command-in-vm} endpoint allows arbitrary shell commands to be executed within the VM environment. This is particularly useful for checking environment settings or container state without needing a full trick configuration:


\begin{lstlisting}[language=python, caption={Run shell command in VM}, label={lst:run-command}, numbers=left, numberstyle=\tiny, stepnumber=1, breaklines=true, frame=single, backgroundcolor=\color{gray!10}, basicstyle=\ttfamily\footnotesize, showspaces=false, showstringspaces=false]
@app.route('/run-command-in-vm', methods=['GET'])
def run_command_in_vm():
    cmd = request.args.get('cmd')
    try:
        output_lines = []
        with subprocess.Popen(
            cmd, shell=True, stdout=subprocess.PIPE, stderr=subprocess.STDOUT, text=True
        ) as process:
            for line in process.stdout:
                output_lines.append(line)
        return jsonify({'output': ''.join(output_lines)})
    except Exception as e:
        return jsonify({'error': str(e)}), 500
\end{lstlisting}



\section{Trick Execution}

The execution of a trick in Houdini begins with the activation of a VM by using the \textit{./houdini --start\_vm}. See ~\ref{lst:start-vm} for the full QEMU command used to activate the VM.

\begin{lstlisting}[language=python, caption={Python method to start the QEMU VM in Houdini}, label={lst:start-vm}, numbers=left, numberstyle=\tiny, stepnumber=1, breaklines=true, frame=single, backgroundcolor=\color{gray!10}, basicstyle=\ttfamily\footnotesize, showspaces=false, showstringspaces=false]
def start_vm(self, kernel=get_absolute_path(f"/kernels/{KERNEL_VERSION}/arch/x86/boot/bzImage"), drive=get_absolute_path("/buildroot/output/images/rootfs.ext2")):
qemu_cmd = [
"qemu-system-x86_64",
"-smp", str(CPU_CORES),
"-m", str(VM_RAM),
"-kernel", kernel,
"-drive", f"file={drive},if=virtio,format=raw",
"-append", "apparmor=1 security=apparmor rootwait root=/dev/vda console=tty1 console=ttyS0 loglevel=0 cgroup_enable=cpuset cgroup_enable=memory",
"-serial", "mon:stdio",
"-net", "nic,model=virtio",
"-net", f"user,hostfwd=tcp::{PORT}-:{PORT}",
"-nographic",
"-virtfs", "local,path=/home/huzi/Desktop,mount_tag=hostshare,security_model=mapped-file,id=hostshare"
]
\end{lstlisting}

The following options in the QEMU command are critical to Houdini's testing workflow:

\begin{itemize}
\item \texttt{-kernel}: Loads a specific Linux kernel, enabling experiments across kernel versions or with custom patches.
\item \texttt{-drive if=virtio}: Uses a virtio-backed root filesystem for fast disk access and compatibility with Buildroot images.
\item \texttt{-append}: Passes kernel boot parameters, including enabling AppArmor and cgroups for isolation enforcement.
\item \texttt{-serial mon:stdio}: Routes guest output to the host terminal for logging and debugging.
\item \texttt{-nographic}: Disables the graphical interface to simplify deployment and speed up boot time.
\item \texttt{-virtfs}: Mounts a host folder into the VM using Plan 9 FS, useful for accessing logs or artifacts.
\item \texttt{-net nic} and \texttt{-net user,hostfwd}: Sets up a virtual NIC and forwards a TCP port for communication between the host and guest (e.g., for Flask server requests).
\end{itemize}

During booting, the guest VM automatically connects to a lightweight Flask server running on the host with the help of a BusyBox init script. This server acts as the communication bridge between the physical host and the guest environment. In other words, it exposes a simple HTTP API for transferring configuration data and receiving test results.

Following this, the execution of a Houdini trick begins on the physical host system, where the user selects a trick to run via a Bash terminal. For example, to run a trick, a user would enter \textit{./houdini --runtrick example\_trick}. Houdini's Flask server parses this command, verifies its correctness, and prepares the test case for execution. Validation includes checking that the required trick file, configuration file, and Dockerfile exist for that particular trick (in this case \textit{example\_trick}).

Following a successful validation of running the command \textit{./houdini --runtrick example\_trick}, the Flask server calls a function to execute the Docker container with the given configuration. It begins by building the Docker image using the provided Dockerfile, copying the trick script into the container, and applying all specified configurations provided by the configuration file (see \~ref{fig:running-a-docker-container-implementation}).

Following this, the trick file runs automatically inside the container, performing its test logic and writing its output to standard output. The trick listener monitors the container's execution, capturing the exit code, output, and any diagnostic messages produced by the trick. These results are packaged together and returned to the host via the Flask server.

On the host side, Houdini stores all test results in structured logs indexed by test ID. This log includes the whole configuration, trick output, and container exit status, making it easy to trace, compare, and debug results. The entire pipeline from configuration parsing to result capture is designed to run without manual intervention, which enables users to queue and evaluate large sets of tests in a reliable and repeatable manner.

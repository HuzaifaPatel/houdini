Houdini supports two modes for defining and executing tricks. The first is a YAML-like approach where a single trick is fully specified through a standalone configuration file (see~\ref{fig:configuration-file}). This method is ideal for running individual tests with carefully controlled settings, making it well-suited for targeted investigations of container confinement. The second mode is a Python-based approach that allows users to define parameter sets as lists, which Houdini expands into a Cartesian product to form a complete test matrix. For example, Docker configuration parameters can be defined in Python, and Houdini will automatically generate all combinations to be tested.



\section{YAML-Like Trick Definition}

The YAML-like Trick definition is one of two ways to define a trick in Houdini. In this section, we will go through the implementation of it and provide examples of its use.

Each trick in Houdini is composed of three modular components that work together to define and execute a container-based security test: a configuration file, a trick script, and a Dockerfile. The configuration file (see~\ref{sec:configuration}) is a YAML-like document that specifies the Docker parameters for launching the container, including security-related settings such as Linux capabilities, namespace modes, AppArmor profiles, user privileges, and resource limits. These parameters are parsed by Houdini and translated directly into Docker's Python SDK, ensuring that containers are created with precise and repeatable configurations.

The second component is the trick file (see~\ref{sec:trick_file}), which contains the logic of the test and is executed inside the container. It is typically written in Python or Bash, this script attempts a specific action, such as reading a sensitive file, sending a signal to a process, or escalating privileges, and reports the outcome by printing a success or failure message or however your implementation wishes to output it. The semantics of what constitutes a pass or fail are entirely defined by the script, giving users full control over the evaluation criteria.

The final component is the Dockerfile, which builds the container image and defines the runtime environment. It includes instructions for copying the trick file into the container by using the \textit{COPY} instruction/directive. We also use the Dockerfile to install any necessary dependencies, and specify the base image to use.

Next, we will explain each of these files in more detail.

\subsection{Configuration File}
\label{sec:configuration}

Each Houdini trick begins with a configuration file, written in YAML-like format, that defines the runtime parameters used to launch the container. This file acts as the Docker command for how the container is constructed and executed. It specifies a range of Docker options including Linux capabilities (via \texttt{cap\_add} and \texttt{cap\_drop}), namespace settings (such as \texttt{pid\_mode} and \texttt{userns\_mode}), resource limits (e.g., \texttt{cpu\_shares}, \texttt{mem\_limit}), volume mounts, user identity, and security options such as AppArmor profiles or seccomp settings. See~\ref{fig:configuration-file} for an example.

The configuration is declarative and follows a structured YAML-like schema that maps directly to Docker’s Python SDK API. For example, if a user wants to disable privilege escalation, enable a read-only filesystem, or run the container as a non-root user with dropped capabilities, these settings can be encoded clearly in the configuration file by giving it a simple \textit/t{True} or \textit{False} value. This abstraction allows users to focus on the security scenario being tested without needing to handcraft long and error-prone Docker command-line arguments.

When Houdini executes a test, the CLI parses the YAML-like configuration and validates it before test execution begins. It checks for required fields, ensures that runtime versions and trick paths are valid, and performs consistency checks to catch errors like incompatible or conflicting flags. Once validated, the configuration is sent to the trick listener and translated into a Docker run command within the guest environment. 

The configuration file is parsed using the parse\_trick\_and\_run() function (see~\ref{fig:configuration-implementation}). This function servers as the entry point for executing a trick. This function begins by extracting the container name from the provided arguments and then checks if a container with the same name already exists on the system. If so, it terminates and removes the existing container to ensure a clean test environment and guarantee reproducibility.

After cleanup, Houdini changes its working directory to the trick path specified in the configuration. This path typically contains the Dockerfile and the trick script. It then calls build\_docker\_image(), which uses the Docker Python SDK to construct a container image from the Dockerfile. This image is tagged with the container name for easy reference. Once the image is built, Houdini proceeds to launch the container using run\_docker\_container(), passing all configuration parameters such as capabilities, network settings, user identity, namespace modes, and resource limits directly into the Docker API call. These values are extracted from the parsed configuration using key-index lookups based on the order in which they appear in the configuration file.

Inside run\_docker\_container() (see~\ref{fig:running-a-docker-container-implementation}), the Docker container is created and run in detached mode with a pseudo-TTY enabled. The standard output from the container is streamed live to the console using Python’s codecs.iterdecode, which allows real-time observation of the trick’s behavior to the terminal running Houdini. In other words, this allows all the stdout from the trick file to redirect to the terminal running Houdini, so that the user can view the status of the trick.

\label{fig:running-a-docker-container-implementation}
\begin{lstlisting}[caption={Implementation for running a Docker container}, numbers=left, numberstyle=\tiny, stepnumber=1, breaklines=true, frame=single, backgroundcolor=\color{gray!10}, basicstyle=\ttfamily\scriptsize, showspaces=false, showstringspaces=false]

    container = None
    try:
        container = client.containers.run(
            image=image_name,
            name=container_name,
            detach=True,
            network_mode=network_mode,
            read_only=read_only,
            security_opt=security_opt,
            pid_mode=pid_mode,
            cpu_shares=cpu_shares,
            volumes=volumes,
            mem_limit=mem_limit,
            cpuset_cpus=cpuset_cpus,
            cpu_quota=cpu_quota,

            cap_drop=cap_drop,
            privileged=privileged,
            user=user,
            pids_limit=pids_limit,
            ipc_mode=ipc_mode,
            userns_mode=userns_mode,
            stdout=True,
            stderr=True,
            tty=True,
        )
    except docker.errors.APIError as e:
        print("Docker API error:", e)
        return None
    except docker.errors.ContainerError as e:
        print("Docker Container error:", e)
        return None
    except Exception as e:
        print("Unexpected error in run_docker_container():", e)
        return None

    print(f"Container '{container_name}' started successfully. {check_mark}")

    if image_name == "cpu_shares":
        run_program_on_vm(path)

    # Attach to the container's stdout
    for chunk in codecs.iterdecode(container.attach(stdout=True, stderr=False, stream=True, logs=False), "utf-8"):
        sys.stdout.write(chunk)

    # Wait for the container to finish
    exit_status = container.wait()
    
    # Get the exit code
    exit_code = exit_status['StatusCode']
    print(f"Container exited with code: {exit_code}")
    

    # Check if the container exited properly
    if exit_code == 0:
        print("Container exited successfully.")
    else:
        print("Container exited with errors.")

    return container

\subsection{Trick File}
\label{sec:trick_file}

The trick script is the core component that defines the actual test logic to be executed inside the container. This script is typically written in a high-level language such as Python or Bash and is copied into the container during the build process specified by the Dockerfile. But, first it is copied into the VM using a custom overlay filesystem script. Once the container is launched with the desired configuration, the trick script runs automatically and attempts a specific action, such as reading a sensitive file, accessing a kernel interface, or interacting with another process. Its purpose is the discretion of the implementer of the trick file.

Houdini does not impose restrictions on the scripting language used, though Python and Bash are most commonly employed due to their simplicity and compatibility with minimal container environments. The scripting interface is straightforward: the script performs a predefined action and prints a result indicating whether the trick passed or failed. These results are captured via standard output by the trick listener running inside the guest VM. The listener uses these outputs, along with exit codes to classify the outcome of the test.

The evaluation criteria are entirely defined within the trick script, giving users full control over what constitutes success or failure. This flexibility allows Houdini to support a wide range of test types, from low-level privilege checks to higher-level behavioral verifications. Scripts can also emit additional diagnostic messages to aid in debugging or deeper analysis to \textit{STDOUT}.

Below is an example of a simple Python trick script that tests whether the container is able to read the contents of the \texttt{/etc/shadow} file. Under standard Docker security settings, access to this file should be restricted. If the script is able to read it, the trick is considered to have failed, indicating a misconfiguration or insufficient isolation. Otherwise, it passes.

\begin{figure}[H]
\caption{Example trick implementation that checks for read access to \texttt{/etc/shadow}.}
\label{fig:trick-script}
\begin{lstlisting}[language=Python, numbers=left, numberstyle=\tiny, stepnumber=1, breaklines=true, frame=single, backgroundcolor=\color{gray!10}, basicstyle=\ttfamily\scriptsize, showspaces=false, showstringspaces=false]
import os

def check_shadow_access():
    path = "/etc/shadow"
    if os.path.exists(path):
        try:
            with open(path, 'r') as f:
                print("Able to read /etc/shadow:")
                print("Trick passed")
        except PermissionError:
            print("Permission denied to read /etc/shadow.")
            print("Trick failed")
        except Exception as e:
            print(f"Unexpected error: {e}")
            print("Trick failed")
    else:
        print("/etc/shadow does not exist.")
        print("Trick failed")

check_shadow_access()
\end{lstlisting}
\end{figure}


This example demonstrates how a trick can evaluate a specific security assumption, file access control in this case, and produce a deterministic result that Houdini can log and interpret. More advanced tricks may incorporate conditionals, environment checks, or IPC mechanisms, but the basic structure remains the same: run a check and report a pass/fail outcome in a clear and reproducible manner.



\subsection{Dockerfile}

The Dockerfile is responsible for setting up the container's runtime environment so that the trick script can execute reliably and with all necessary dependencies. It defines how the container image is built, including the selection of a base image, the installation of packages or libraries required by the trick script, and the inclusion of the trick file itself.

Tricks in Houdini can be written in a variety of languages such as Python or Bash, so the Dockerfile must ensure that the corresponding runtime (e.g., the Python interpreter or Bash shell) is available inside the container. This often involves installing system packages using the package manager provided by the base image, for example, using \texttt{apt} in Debian-based images or \texttt{apk} in Alpine.

Another essential part of the Dockerfile is copying the trick script into the container's filesystem. This step ensures that the logic defined by the user is available at a known path when the container starts. Houdini standardizes this by copying the trick to a predefined directory (e.g., \texttt{/houdini/trick.py}) so that all containers follow the same execution convention.

The base image is selected based on the needs of the trick. Lightweight images like Alpine Linux are often preferred for simple tests because of their small size and fast startup time. However, more feature-rich images like Debian or Python-based official images may be used when additional dependencies or language runtimes are required.

Finally, the Dockerfile specifies an entrypoint or \texttt{CMD} directive to automatically run the trick script when the container launches. This ensures that the trick executes without requiring user intervention or manual commands. The entrypoint is usually a direct call to the interpreter (e.g., \texttt{python3 /houdini/trick.py}).

The example in~\ref{fig:dockerfile-example} demonstrates a simple Dockerfile used in Houdini to run a Python-based trick. It uses the official Python image, copies the trick from the VM to the container, and sets the default command to execute the script.

\begin{figure}[H]
\caption{Example Dockerfile used to prepare the container environment for a Python-based trick.}
\label{fig:dockerfile-example}
\begin{lstlisting}[numbers=left, numberstyle=\tiny, stepnumber=1, breaklines=true, frame=single, backgroundcolor=\color{gray!10}, basicstyle=\ttfamily\scriptsize, showspaces=false, showstringspaces=false]
FROM python:3.9-slim

WORKDIR /houdini

COPY trick.py /houdini/trick.py

CMD ["python3", "/houdini/trick.py"]
\end{lstlisting}
\end{figure}


This Dockerfile is minimal yet sufficient for running Python scripts inside a container. It illustrates the typical pattern used in Houdini to prepare containers in a consistent and reproducible manner. More complex tricks may extend this file to install additional packages, configure environment variables, or mount external resources, but the core structure remains largely the same.


\section{Python-Based Expansion Definition}

In addition to supporting single-trick YAML-like definitions, Houdini provides a Python-based mechanism to define a matrix of configurations by specifying Docker configuration parameters as lists. Houdini automatically expands these parameters into a Cartesian product and generates a full suite of test cases. This approach is powerful for scaling up experiments, allowing researchers to explore the interaction of various container runtime settings systematically.

\begin{lstlisting}[language=bash, caption={Trick parameter sets defined in Python}, label={lst:apparmor-trick}, numbers=left, numberstyle=\tiny, stepnumber=1, breaklines=true, frame=single, backgroundcolor=\color{gray!10}, basicstyle=\ttfamily\footnotesize, showspaces=false, showstringspaces=false]
pid_mode = [None, "--pid=host"]
cap_kill = [False, True]
cap_sys_ptrace = [False, True]
privileged_opts = [False, True]
apparmor_profiles = ["apparmor=unconfined", "apparmor=docker-default"]
user = ["huzi"]
runtime = ["crun"]
\end{lstlisting}

Let $\mathcal{P}$ denote the parameter space. We define:

\[
\begin{aligned}
\mathcal{P}_{\text{pid}} &= \{\varnothing, \texttt{"--pid=host"}\} \\
\mathcal{P}_{\text{kill}} &= \{\texttt{False}, \texttt{True}\} \\
\mathcal{P}_{\text{ptrace}} &= \{\texttt{False}, \texttt{True}\} \\
\mathcal{P}_{\text{priv}} &= \{\texttt{False}, \texttt{True}\} \\
\mathcal{P}_{\text{apparmor}} &= \{\texttt{"apparmor=unconfined"}, \texttt{"apparmor=docker-default"}\} \\
\mathcal{P}_{\text{user}} &= \{\texttt{"huzi"}\} \\
\mathcal{P}_{\text{runtime}} &= \{\texttt{"crun"}\}
\end{aligned}
\]

The full parameter space is their Cartesian product:

\[
\mathcal{P} = \mathcal{P}_{\text{pid}} \times \mathcal{P}_{\text{kill}} \times \mathcal{P}_{\text{ptrace}} \times \mathcal{P}_{\text{priv}} \times \mathcal{P}_{\text{apparmor}} \times \mathcal{P}_{\text{user}} \times \mathcal{P}_{\text{runtime}}
\]

Each tuple $\vec{p} \in \mathcal{P}$ corresponds to a single command invocation:

\[
\texttt{docker run -i } + \text{flags}(\vec{p}) + \texttt{ \$IMAGE}
\]

Since \(|\mathcal{P}_{\text{pid}}| = |\mathcal{P}_{\text{kill}}| = |\mathcal{P}_{\text{ptrace}}| = |\mathcal{P}_{\text{priv}}| = |\mathcal{P}_{\text{apparmor}}| = 2\) and \(|\mathcal{P}_{\text{user}}| = |\mathcal{P}_{\text{runtime}}| = 1\), the total number of configurations is:

\[
|\mathcal{P}| = 2^5 = 32
\]

\section{Flask Server}

The Flask server plays a central role in Houdini’s architecture by acting as the primary communication bridge between the physical host system and the guest VM. Once the QEMU-based VM boots, it establishes a connection to this Flask server to initiate trick execution. The server runs as a lightweight HTTP service on the host, exposing a set of well-defined endpoints that orchestrate the full test workflow. The Flask server is automatically started with the help of a BusyBox init script (see~\ref{lst:start-flask-server}).

\begin{lstlisting}[language=python, caption={BusyBox init file that starts the Flask server}, label={lst:start-flask-server}, numbers=left, numberstyle=\tiny, stepnumber=1, breaklines=true, frame=single, backgroundcolor=\color{gray!10}, basicstyle=\ttfamily\footnotesize, showspaces=false, showstringspaces=false]
#!/bin/sh
# Description: Example service script

PATH=/sbin:/bin:/usr/sbin:/usr/bin:/usr/local/bin
DAEMON=/usr/bin/python3
DAEMON_ARGS="/houdini/server.py"
PIDFILE=/var/run/houdini-server.pid
LOGFILE=/var/log/houdini-server.log

case "$1" in
    start)
        echo "Starting my service..."
        $DAEMON $DAEMON_ARGS >> $LOGFILE 2>&1 &
        ;;
    stop)
        echo "Stopping houdini-server..."
        kill $(cat $PIDFILE)
        ;;
    restart)
        echo "Restarting houdini-server..."
        $0 stop
        sleep 1
        $0 start
        ;;
    *)
        echo "Usage: $0 {start|stop|restart}"
        exit 1
        ;;
esac

exit 0
\end{lstlisting}

The core endpoints exposed by the server are \texttt{/server-status}, \texttt{/version-status}, \texttt{/run-trick}, and \texttt{/run-command-in-vm}. The \texttt{/server-status} endpoint is used for health checking and indicates whether the Houdini server is actively running on the host. This enpoint uses the subprocess module to check whether a specific process is running on the system. It executes the \textit{pgrep -f <service\_name>} command, which searches for all currently running processes whose full command lines match the given service name. In our case, the servie name is \textit{/usr/bin/python3 /houdini/server.py}. The stdout=subprocess.PIPE option captures the output (i.e., the matching process IDs), allowing the script to access the result programmatically. The check=True flag ensures that if no matching process is found, the command will raise a subprocess.CalledProcessError, which can be used to detect and handle the case where the service is not running.

\begin{lstlisting}[language=python, caption={Server health check endpoint}, label={lst:server-status}, numbers=left, numberstyle=\tiny, stepnumber=1, breaklines=true, frame=single, backgroundcolor=\color{gray!10}, basicstyle=\ttfamily\footnotesize, showspaces=false, showstringspaces=false]
@app.route('/server-status', methods=['GET'])
def server_status():
    if is_service_running('/usr/bin/python3 /houdini/server.py'):
        response_data = str(True)
        return make_response(response_data, 200)
    else:
        response_data = str(False)
        return make_response(response_data, 503)


def is_service_running(service_name):
    result = subprocess.run(['pgrep', '-f', service_name], check=True, stdout=subprocess.PIPE)

    if not result.returncode:
        return True
    return False
\end{lstlisting}






The \texttt{/version-status} endpoint queries the current versions of critical components such as Docker and \texttt{runc}. It executes shell commands using Python’s \texttt{subprocess} module and returns a JSON-formatted response with version information:

\begin{lstlisting}[language=python, caption={Runtime version information endpoint}, label={lst:version-status}, numbers=left, numberstyle=\tiny, stepnumber=1, breaklines=true, frame=single, backgroundcolor=\color{gray!10}, basicstyle=\ttfamily\footnotesize, showspaces=false, showstringspaces=false]

The most critical endpoint is \texttt{/run-trick}, which handles the dispatching of a specific trick into the guest VM. When a request is made to this endpoint from a user on the physical host, the server loads the corresponding YAML-like configuration file, parses it, and executes the full Docker test pipeline.

\begin{lstlisting}[language=python, caption={Trick execution endpoint}, label={lst:run-trick}, numbers=left, numberstyle=\tiny, stepnumber=1, breaklines=true, frame=single, backgroundcolor=\color{gray!10}, basicstyle=\ttfamily\footnotesize, showspaces=false, showstringspaces=false]
@app.route('/run-trick/<trick_folder>/<trick>', methods=['GET'])
def run_trick(trick_folder, trick):
    TRICK_PATH = f'/houdini/tricks/{trick_folder}/{trick}'
    if not os.path.exists(TRICK_PATH):
        return jsonify({'error': f'Trick {trick} not found. PATH = {TRICK_PATH}'}), 404

    with open(TRICK_PATH, 'r') as file:
        trick_data = yaml.safe_load(file)

    output = io.StringIO()
    with contextlib.redirect_stdout(output):
        results = parse_trick_and_run(trick_data, request.args)

    return Response(output.getvalue())

For debugging and exploratory testing, the \texttt{/run-command-in-vm} endpoint allows arbitrary shell commands to be executed within the VM environment. This is particularly useful for checking environment settings or container state without needing a full trick configuration:


\begin{lstlisting}[language=python, caption={Run shell command in VM}, label={lst:run-command}, numbers=left, numberstyle=\tiny, stepnumber=1, breaklines=true, frame=single, backgroundcolor=\color{gray!10}, basicstyle=\ttfamily\footnotesize, showspaces=false, showstringspaces=false]
@app.route('/run-command-in-vm', methods=['GET'])
def run_command_in_vm():
    cmd = request.args.get('cmd')
    try:
        output_lines = []
        with subprocess.Popen(
            cmd, shell=True, stdout=subprocess.PIPE, stderr=subprocess.STDOUT, text=True
        ) as process:
            for line in process.stdout:
                output_lines.append(line)
        return jsonify({'output': ''.join(output_lines)})
    except Exception as e:
        return jsonify({'error': str(e)}), 500

\section{Trick Execution}

The execution of a trick in Houdini begins with the activation of a VM by using the \textit{./houdini --start\_vm}. See ~\ref{lst:start-vm} for the full QEMU command used to activate the VM.

The following options in the QEMU command are critical to Houdini's testing workflow:

\begin{itemize}
\item \texttt{-kernel}: Loads a specific Linux kernel, enabling experiments across kernel versions or with custom patches.
\item \texttt{-drive if=virtio}: Uses a virtio-backed root filesystem for fast disk access and compatibility with Buildroot images.
\item \texttt{-append}: Passes kernel boot parameters, including enabling AppArmor and cgroups for isolation enforcement.
\item \texttt{-serial mon:stdio}: Routes guest output to the host terminal for logging and debugging.
\item \texttt{-nographic}: Disables the graphical interface to simplify deployment and speed up boot time.
\item \texttt{-virtfs}: Mounts a host folder into the VM using Plan 9 FS, useful for accessing logs or artifacts.
\item \texttt{-net nic} and \texttt{-net user,hostfwd}: Sets up a virtual NIC and forwards a TCP port for communication between the host and guest (e.g., for Flask server requests).
\end{itemize}

During booting, the guest VM automatically connects to a lightweight Flask server running on the host with the help of a BusyBox init script. This server acts as the communication bridge between the physical host and guest environment. In other words, it exposes a simple HTTP API for transferring configuration data and receiving test results.

Followed by this, The execution of a Houdini trick begins on the physical host system, where the user selects a trick to run via a Bash terminal. For example, to run a trick, a user would enter \textit{./houdini --runtrick example\_trick}. Houdini’s Flask server parses this command, verifies its correctness, and prepares the test case for execution. Validation includes checking that required trick file exist, configuration file, and Dockerfile exists for that particular trick (in this case \textit{example\_trick}).

Following a successful validation of running the command \textit{./houdini --runtrick example\_trick}, the Flask server calls a function to execute the docker container with the configurations given. It begins by building the Docker image using the provided Dockerfile, copying the trick script into the container, and applying all specified configurations provided by the configuration file (see \~ref{fig:running-a-docker-container-implementation}).

Following this, the trick file runs automatically inside the container, performing its test logic and writing its output to standard output. The trick listener monitors the container’s execution, capturing the exit code, output, and any diagnostic messages produced by the trick. These results are packaged together and returned to the host via the Flask server.

On the host side, Houdini stores all test results in structured logs indexed by test ID. This log includes the full configuration, trick output, and container exit status making it easy to trace, compare, and debug results. The entire pipeline from configuration parsing to result capture is designed to run without manual intervention, which enables users to queue and evaluate large sets of tests in a reliable and repeatable manner.

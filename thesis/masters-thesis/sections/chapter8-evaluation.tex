\subsection{Requirements / Goals:}
\begin{itemize}

\item \textbf{Reproducibility:}
Houdini should produce consistent and repeatable results when run across different machines and environments. Identical configurations and test inputs should yield the same outcomes.

\item \textbf{Scalability:}
Houdini should support scalable execution, allowing users to easily configure, queue, and execute large batches of tests/tricks across multiple container configurations or versions. The framework should be designed to accept input declaratively and automate the full evaluation without requiring manual intervention.

\item \textbf{Performance:}
Houdini should execute tests efficiently, minimizing runtime overhead while maintaining accuracy. The framework’s performance should allow it to be integrated into larger workflows, such as continuous integration pipelines, without introducing significant delays.

\item \textbf{Security and Host Isolation:}
Houdini must isolate tests from the host system to ensure safety during the execution of potentially dangerous tricks. By running tests inside a virtual machine, Houdini should prevent container escapes or exploits from impacting the host. It should maintain a secure boundary between the test environment and the underlying system.

\item \textbf{Accuracy of Detection}
Houdini should correctly distinguish between successful and failed security isolation. Test results should reflect the actual runtime behavior of the container under evaluation without false positives or negatives.

\item \textbf{Flexibility Across Configurations}
The framework should support a wide range of container settings, including different Linux capabilities, namespaces, AppArmor profiles, seccomp filters, and Docker flags. It should also accommodate various versions of Docker, runc, crun, and the Linux kernel.

\item \textbf{Transparency and Debuggability}
Test runs should be transparent and easy to interpret. Logs, intermediate outputs, and error messages should be informative enough to help users understand why a trick passed or failed.


\item \textbf{Detect Configuration-Behavior Inconsistencies:}  
Evaluate whether containers behave as expected under different security configurations by empirically validating real-world runtime behavior. This helps identify mismatches between intended policy and actual enforcement.

\item \textbf{Assess Cross-Version Consistency and Enforcement Drift:}  
Determine whether the same container configuration yields consistent behavior across different versions of Docker, container runtimes (e.g., runc, crun), and Linux kernels.




\end{itemize}

\subsection{Methodology / How we will do that:}
    
    To evaluate the effectiveness and design properties of the Houdini framework, we conduct a series of controlled experiments targeting key aspects of its architecture and operation. Each experiment is designed to test a specific goal of the framework, including reproducibility, scalability, performance, and security isolation. 

    We structure our methodology as follows:

\begin{enumerate}
    \item \textbf{Reproducibility Across Machines} \\
    Run the same trick and configuration on two different machines (e.g., different CPU architectures or hardware specs) and verify that the output is identical.

    \item \textbf{Reproducibility Across Time with Version Pinning} \cmark \\
    Re-run a pinned Docker, kernel, and runc configuration at a later time to ensure consistent results, demonstrating Houdini's ability to reproduce experiments reliably.

    \item \textbf{Scalability via Bulk Execution} \\
    Execute a large batch of tricks (e.g., 32) across multiple configurations in one session. Measure runtime, memory usage, and failure rates to assess Houdini’s batch execution capabilities.

    \item \textbf{Performance Benchmarking} \cmark \\
    Measure the end-to-end time it takes Houdini to execute a single trick, including VM boot, container launch, and result collection. Compare this to a manually executed baseline outside Houdini.

    \item \textbf{Host Isolation Validation} \cmark \\
    Run a deliberately malicious trick (e.g., attempting to write to host directories) and verify that the host remains secure, demonstrating that Houdini’s use of VMs effectively isolates test environments.

    \item \textbf{Fault Tolerance and Crash Recovery} \\
    Introduce failing or crashing tricks (e.g., segmentation faults, infinite loops) and confirm that Houdini logs the failure and continues running subsequent tests without interruption.

    \item \textbf{Version Variability Support} \cmark \\
    Create a test matrix across different combinations of Docker, runc, and kernel versions. Confirm that Houdini successfully builds and runs tricks across all variations.

    \item \textbf{Extensibility Test} \cmark \\
    Develop a new custom trick (e.g., testing for a capability or syscall) and integrate it into Houdini. Measure the effort and steps needed to add and run it without modifying the core logic.

    \item \textbf{CI Integration Test} \\
    Integrate Houdini into a CI/CD system such as GitHub Actions or GitLab CI. Trigger it on container configuration changes and assess its stability and reporting in an automated pipeline.
\end{enumerate}

\section{Reproducibility Across Time with Version Pinning}

This experiment evaluates Houdini’s ability to reliably reproduce test results over time using a version-pinned container environment. Reproducibility is a core requirement in security evaluation, particularly when comparing behavior across different kernel versions or runtime configurations. Even slight changes to binaries or system dependencies can lead to unexpected behavioral drift. To address this, Houdini provides a controlled execution framework where all critical components are locked to specific versions.

Version pinning refers to explicitly locking the versions of software components, such as Docker, runc, and the Linux kernel to prevent variation due to automatic updates, rebuilds, or environmental drift. By re-executing a simple, deterministic ``Hello World'' trick across time and validating both behavior and binary integrity, this experiment assesses whether Houdini can produce identical results when the test configuration is held constant.

\subsection{Experimental Setup}

Rather than relying on Buildroot’s package infrastructure, we used an \texttt{overlayfs} directory to inject precompiled binaries of Docker and runc directly into the root filesystem. This approach allows full control over the environment and guarantees that only explicitly specified versions of components are used.

The following components were pinned in this experiment:

\begin{itemize}
    \item \textbf{Docker:} 27.0.3, installed at \texttt{/usr/bin/docker} and \texttt{/usr/bin/dockerd}
    \item \textbf{runc:} 1.1.13, placed at \texttt{/usr/bin/runc}
    \item \textbf{Linux Kernel:} 6.0, compiled using Buildroot and booted via QEMU
\end{itemize}

To ensure binary-level consistency between runs, we calculated the SHA256 hashes of each component and stored them in a version manifest file. These hashes act as a cryptographic fingerprint to confirm that the binaries remain unchanged throughout the experiment:

\subsection{Hello World Trick Logic}

The \texttt{hello\_world.sh} script is placed in \texttt{/usr/bin/} and included via the overlay. Its behavior is intentionally simple and deterministic: it checks for the presence of a file called \texttt{/run/trigger\_file} inside the container. If the file exists, the script prints ``Trick passed''; otherwise, it prints ``Trick failed.'' This condition allows us to control the outcome while keeping the logic repeatable and easily verifiable.

\begin{lstlisting}[language=bash, caption={Hello World Trick Script}, label={lst:hello-trick}, numbers=left, numberstyle=\tiny, stepnumber=1, breaklines=true, frame=single, backgroundcolor=\color{gray!10}, basicstyle=\ttfamily\footnotesize, showspaces=false, showstringspaces=false]
#!/bin/sh
if [ -f /run/trigger_file ]; then
    echo "Trick passed"
else
    echo "Trick failed"
fi
\end{lstlisting}


This trick is chosen not to test system vulnerabilities, but rather to validate that Houdini can reliably detect environmental consistency and reproduce test output based solely on deterministic conditions.

\subsection{Initial Execution (T0)}

At time T0, the environment was constructed using the pinned versions of Docker, runc, and the Linux kernel. The container was run without creating the trigger file:

\begin{lstlisting}[language=bash, caption={Running the Hello Trick in a Container}, label={lst:run-hello-trick}, numbers=left, numberstyle=\tiny, stepnumber=1, frame=single, breaklines=true, backgroundcolor=\color{gray!10}, basicstyle=\ttfamily\footnotesize, showspaces=false, showstringspaces=false]
docker run --rm myimage /hello_world.sh
\end{lstlisting}

\textbf{Expected Output: Trick failed}

All binary hashes were verified against the manifest, confirming that the test environment matched the intended configuration exactly. The result was recorded and used as a baseline for later comparison.

\subsection{Re-run Execution (T1)}

At time T1, after a delay, the Buildroot image was rebuilt using the same configuration and the original overlay directory. This ensured that all injected binaries were identical to those used at T0.

We re-verified the Docker and runc binaries inside the running VM using the following commands:

\begin{lstlisting}

\end{lstlisting}

Both values matched the entries in \texttt{version\_manifest.txt}, confirming no binary drift. The container was again executed without creating the trigger file:

docker run --rm myimage /hello_world.sh
\end{lstlisting}

\textbf{Output: Trick failed}


To test the positive condition, the trigger file was created within the container, and the trick was re-run:


\begin{lstlisting}[language=bash, caption={Running the Hello Trick in a Container}, label={lst:run-hello-trick}, numbers=left, numberstyle=\tiny, stepnumber=1, frame=single, breaklines=true, backgroundcolor=\color{gray!10}, basicstyle=\ttfamily\footnotesize, showspaces=false , showstringspaces=false]
docker run --rm myimage sh -c "touch /run/trigger_file && /hello_world.sh"
\end{lstlisting}

\textbf{Output: Trick passed}


These results exactly matched the expected behavior, confirming that the environment, logic, and outcome were all stable and reproducible.

\subsection{Analysis and Observations}

This experiment illustrates that when the container runtime stack is fully controlled through version pinning, overlay injection, and hash verification, Houdini can achieve bit-for-bit reproducibility. Moreover, this approach enables rigorous detection of behavioral drift caused by even minor environmental differences.

The results also highlight how small changes in the runtime environment, such as default mount behavior, file permissions, or base filesystem differences, could affect trick outcomes if not properly controlled. By tying the trick’s behavior to a simple file-based condition, we were able to simulate both pass and fail outcomes in a deterministic and easily verifiable way.

\subsection{Conclusion}

This reproducibility experiment confirms that Houdini provides a reliable framework for time-stable container testing when all components are version-pinned and verifiable. By injecting Docker and runc via \texttt{overlayfs}, verifying integrity with SHA256 hashes, and using deterministic logic inside the test container, Houdini ensures that security and behavioral tests yield consistent results across time. This makes Houdini well-suited for regression analysis, longitudinal container studies, and real-world vulnerability tracking.

















\section{Host Isolation Validation}

This experiment evaluates Houdini’s ability to isolate test environments from the physical host machine. Since Houdini executes potentially malicious or privilege-escalating code inside containers, it is critical to ensure that these operations cannot impact the host system. To validate this, we deliberately execute a container trick that attempts to write to a host-accessible path. The goal is to verify that Houdini's use of QEMU-based virtual machines effectively prevents the container from escaping the VM boundary.

\subsection{Threat Model}

The threat model for this evaluation assumes that the attacker has full control over arbitrary code executed inside a container running within Houdini’s virtual machine. This reflects a realistic scenario where untrusted or potentially malicious container workloads are tested to evaluate security boundaries. The attacker may attempt to exploit kernel vulnerabilities, access unintended resources, or perform file system operations that target the host. Typical actions include attempting to write to host-mounted directories, reading sensitive data, or interacting with other host processes.

However, the attacker’s capabilities are strictly confined to the virtual machine. They have no access to the physical host system, nor are they granted elevated privileges beyond what is available inside the containerized guest. The container may share namespaces with the host, and the kernel it interacts with is the one booted inside the VM, not the host kernel.

While Houdini containers by default operate in isolated namespaces, Docker allows optional sharing of specific namespaces with the host environment using flags such as --pid=host, --net=host, --ipc=host, or --uts=host. When enabled, these options allow the container to observe or interact with resources on the host namespace level, such as the full process table, network stack, or inter-process communication channels. In typical host environments, this would increase the attack surface and make lateral movement or privilege escalation more feasible.

However, in Houdini’s design, these namespace-sharing configurations are restricted to the context of the virtual machine only. That is, even if a container is launched with --pid=host, it shares the PID namespace only with the VM, not the physical host. Likewise, shared network or IPC namespaces remain confined to the QEMU instance. This ensures that while Houdini supports evaluation of shared-namespace behavior, any unintended access or compromise remains sandboxed inside the virtual machine. The attacker cannot affect the physical host’s kernel or global namespaces, and cannot persist beyond the lifecycle of the VM.

The goal of this threat model is to validate that Houdini can safely execute such container scenarios without compromising host integrity. Even if the attacker succeeds in exploiting the container or VM environment, the outer boundary provided by QEMU must prevent any direct impact on the host. This includes protection against file writes, process interference, or network communication with host resources outside the intended testing interface.

This evaluation, therefore, focuses on confirming that the default Houdini configuration—with no shared folders, no privileged mounts, and no host-level interaction—effectively isolates the testbed. Any data or control flow out of the VM must pass through carefully scoped and auditable channels such as the Flask-based result reporting interface.

\subsection{Malicious Trick Description}

We designed a trick to evaluate whether a container running inside Houdini's virtual machine can access the physical host system. This test simulates an escape attempt by trying to write to a file path that would typically point to a shared folder if one were configured.

\begin{lstlisting}[language=bash, caption={Escape Trick: Simulated Write to Host-Mounted Path}, label={lst:escape-trick}, numbers=left, numberstyle=\tiny, stepnumber=1, frame=single, breaklines=true, backgroundcolor=\color{gray!10}, basicstyle=\ttfamily\footnotesize, showspaces=false, showstringspaces=false]
#!/bin/sh
# Attempt to write to a path that would be host-mounted if shared folders were enabled
TOUCH_PATH="/mnt/host_root/hacked.txt"

echo "Attempting to write to possible host mount at $TOUCH_PATH"
echo "HACKED" > "$TOUCH_PATH" 2>/dev/null

# Try to detect if the write succeeded
if [ -f "$TOUCH_PATH" ]; then
    echo "Trick passed: Possible host write detected!"
else
    echo "Trick failed: No host write access."
fi

# Optional: Check if root of PID 1 differs (may indicate shared PID namespace)
echo "Probing /proc/1/root:"
ls /proc/1/root 2>/dev/null | head -n 5
\end{lstlisting}


\subsection{Execution Inside the VM}

The container was executed inside a QEMU-based Buildroot virtual machine that does not expose any host directories and uses no shared folders. The container was started using the following command:

\begin{lstlisting}[language=bash, caption={Running Escape Trick Inside VM}, numbers=none]
docker run --rm alpine /host_escape_trick.sh
\end{lstlisting}

\textbf{Example Output:}

\begin{lstlisting}[language=bash]
Attempting to write to possible host mount at /mnt/host_root/hacked.txt
Trick failed: No host write access.
\end{lstlisting}

No file named \texttt{hacked.txt} appeared on the physical host, confirming that the simulated attack was fully contained within the virtual machine. The output of \texttt{/proc/1/root} further suggests that there is no unexpected namespace exposure.

\subsection{Implications of Shared Folders}

While shared folders are a common method for transferring files between a virtual machine and its host, their use inherently weakens the isolation boundary. If a container within the VM has access to a host-mounted directory, it may write or overwrite files that become visible outside the VM. This creates a deliberate escape route that must be managed with caution.

However, Houdini avoids this problem entirely by not relying on shared folders for interprocess communication or result reporting. Instead, Houdini uses a lightweight Flask-based HTTP server running on the host. When a trick completes execution inside the VM, it sends its result, such as pass/fail status or diagnostic output back to the host via an HTTP POST request over a user-mode QEMU network port.

This design has several advantages:
\begin{itemize}
    \item It eliminates the need to mount any part of the host filesystem inside the VM.
    \item It decouples file I/O from test reporting, reducing the attack surface.
    \item It enables fine-grained control over what data leaves the VM and how it is structured.
\end{itemize}

As a result, Houdini preserves a strong isolation model while still allowing real-time, structured feedback from tests running inside the VM.

\subsection{Conclusion}

This experiment confirms that Houdini provides strong host isolation by default. Malicious trick code that attempts to write to host-accessible paths is safely confined within the virtual machine. The inclusion of a clearly defined threat model ensures that the assumptions and limits of containment are well-scoped. Furthermore, the use of a Flask-based communication channel, rather than shared folders, enhances isolation by avoiding any direct file-based interaction between the guest and host. Overall, Houdini’s VM-based architecture combined with controlled, network-based result reporting offers a robust and secure foundation for container security testing.
















\section{Extensibility Evaluation}

This experiment demonstrates Houdini’s extensibility by adding a new custom trick and running it without modifying any of the core orchestration logic. The goal is to evaluate whether new security scenarios can be introduced through configuration alone.

To implement the new trick, a configuration file was created inside the \texttt{trick\_configs/} directory. This file defines the parameter space for the new test, specifying Docker runtime flags and relevant security features. The file contained the following variables:

\begin{lstlisting}[language=Python, caption={Escape Trick: Simulated Write to Host-Mounted Path}, label={lst:escape-trick}, numbers=left, numberstyle=\tiny, stepnumber=1, frame=single, breaklines=true, backgroundcolor=\color{gray!10}, basicstyle=\ttfamily\footnotesize, showspaces=false, showstringspaces=false]
pid_mode = [None, "--pid=host"]
cap_kill = [False, True]
cap_sys_ptrace = [False, True]
privileged_opts = [False, True]
apparmor_profiles = ["apparmor=unconfined", "apparmor=docker-default"]
user = ["huzi"]
\end{lstlisting}

Each variable represents a dimension of the test configuration space:
\begin{itemize}
    \item \textbf{pid\_mode}: toggles between isolated and host PID namespace.
    \item \textbf{cap\_kill}: enables or disables the \texttt{CAP\_KILL} capability.
    \item \textbf{cap\_sys\_ptrace}: enables or disables the \texttt{CAP\_SYS\_PTRACE} capability.
    \item \textbf{privileged\_opts}: enables or disables \texttt{--privileged} mode.
    \item \textbf{apparmor\_profiles}: selects between \texttt{unconfined} and \texttt{docker-default} AppArmor profiles.
    \item \textbf{user}: specifies the user under which the container should run.
\end{itemize}

Houdini automatically loads this configuration file and generates all possible combinations of the parameters. For each configuration, Houdini builds a Docker image and executes the container with the specified flags, logging the results.

To run the new trick, the user must modify the \texttt{TRICK} variable inside constants/houdini\_config.py, setting it equal to the name of the new configuration file (e.g., TRICK = "check\_sys\_admin"). No changes are required to Houdini’s main logic or scripts.

Once the variable is set, Houdini performs the following automatically:
\begin{itemize}
    \item Loads the new configuration file.
    \item Builds the associated Docker image.
    \item Constructs the test matrix.
    \item Runs each configuration inside the QEMU-based virtual machine.
    \item Logs the results for analysis.
\end{itemize}

This process validates Houdini’s modular design and confirms that new test scenarios can be rapidly integrated by simply creating a new configuration file and updating a single variable. The minimal integration effort confirms that Houdini is scalable and extensible for diverse container security evaluations.




\section{Version Variability Support}

To evaluate Houdini’s ability to operate across a broad range of runtime environments, we constructed a test matrix covering diverse combinations of Docker, runc, and Linux kernel versions. We selected representative Docker versions from three eras—early (e.g., 17.03), mid-range (e.g., 20.10), and modern (e.g., 27.0.3)—along with their corresponding runc binaries. Each version set was tested on multiple kernel versions ranging from 5.4 to 6.5.

This version variability was essential for validating Case Study 1 (CVE-2024-21626). By running Houdini’s CVE trick across our version matrix, we confirmed that vulnerable runc versions (e.g., 1.0.0-rc2) allowed the exploit to succeed, while patched versions did not. This not only demonstrated Houdini’s accuracy in detecting confinement violations but also verified that its test logic remains functional and portable across changes in Docker’s and runc’s APIs, flags, and behaviors.

Houdini’s ability to build containers, run tricks, and collect output without modification across these versions highlights its value as a version-agnostic regression testing framework.

\section{Performance Benchmarking}

\subsubsection{Understanding Time Metrics in Microbenchmarking}

In performance benchmarking, especially in systems research and software profiling, several time-based metrics are commonly used to assess how a program or process utilizes computing resources. These include wall clock time, user time, system time, and CPU utilization. Each of these captures a different aspect of execution behavior and provides insight into how efficiently a task runs.

\textbf{Wall clock time}, also known as elapsed time or real time, is the total time taken from the start of a program to its completion. It includes all delays, such as waiting for I/O operations, context switches, or sleep intervals. Wall clock time is measured as the actual duration perceived by a user, typically using timestamps recorded before and after the process runs.

\textbf{User time} refers to the amount of CPU time spent running code in user space. This includes the program’s own instructions and any library code it uses. It excludes time spent in the kernel or operating system. This metric is measured by the operating system and tracks how much CPU time was directly consumed by the application itself.

\textbf{System time} (or kernel time) accounts for the time spent by the CPU in the operating system kernel on behalf of the program. This includes handling system calls, managing I/O, allocating memory, and other interactions with hardware or privileged OS routines. Like user time, it is reported by the operating system’s process accounting.

\textbf{CPU utilization} is the percentage of total available CPU time that the process actively used during its lifetime. It is computed as the ratio of the sum of user and system time to the wall clock time. High CPU utilization indicates that the process is CPU-bound, meaning it spends most of its time doing computations. Low CPU utilization may suggest the process is I/O-bound or waiting on external events.

Together, these metrics offer a multifaceted view of a program’s execution profile. They help developers identify bottlenecks, assess performance regressions, and understand whether inefficiencies stem from computation, system overhead, or external delays.


\subsection{Microbenchmark}

\subsubsection{Making the Root Filesystem}

To evaluate the performance of Houdini’s build and setup pipeline, we microbenchmarked the \texttt{mkfs} stage independently. This step is responsible for creating the root filesystem used by the virtual machine and typically takes around \texttt{60.21} seconds, as measured using the \texttt{/usr/bin/time} utility. The benchmark showed a \textbf{user time} of 19.43 seconds and a \textbf{system time} of 45.97 seconds, with the job receiving approximately \textbf{63\% CPU utilization}. This suggests that the operation is moderately CPU-bound but also involves significant I/O operations, such as copying files and formatting the disk image.

The \texttt{mkfs} process not only formats the filesystem but also populates it with all necessary binaries and files from the overlay directory, including the trick scripts, configuration files, and supporting assets required for execution. Importantly, this stage is only performed once per setup. Once the root filesystem is built, it can be reused across multiple Houdini runs without re-invoking \texttt{mkfs}, significantly reducing the startup time for subsequent executions. However, if a new trick is implemented or an existing one is modified, \texttt{mkfs} must be rerun to ensure that the updated trick is included in the root filesystem image.


\subsubsection{Booting the Virtual Machine}

To assess the overhead of launching Houdini’s virtual machine environment, we conducted a microbenchmark of the VM startup process. The virtual machine is started using QEMU with a prebuilt Buildroot root filesystem and a custom Linux kernel. The system is configured to launch a shell and immediately power off after a fixed delay, ensuring consistency in measurement.

We measured the total wall-clock time required to boot the VM, execute a trivial command, and power down. The benchmark was performed using the \texttt{/usr/bin/time -v} utility, capturing both user and system time. The wall-clock time for this process was approximately 28.47 seconds. The user time recorded was 3.52 seconds, while the system time was 9.38 seconds. Overall, the job utilized roughly 45\% of the CPU during execution.

These results indicate that the boot process introduces a moderate overhead in Houdini’s workflow, primarily due to QEMU’s emulation and the initialization of the Linux kernel and user space environment. Despite this, the startup time remains stable across multiple invocations, providing a consistent and reliable baseline for empirical testing. This microbenchmark reinforces the practicality of using QEMU as a platform for repeatable, isolated container security experiments.


\subsubsection{Building the Docker Image}

To evaluate the performance overhead of Docker image creation within the Houdini pipeline, we conducted a microbenchmark of the \texttt{docker build} process. The benchmark was executed using the \texttt{/usr/bin/time -v} utility to capture detailed runtime metrics, including user time, system time, wall-clock time, and CPU utilization.

The wall-clock time to complete the initial build process was measured at approximately \texttt{1 minute and 13.04 seconds}. During this time, the process consumed \texttt{0.33 seconds} of user CPU time and \texttt{0.30 seconds} of system CPU time. The CPU utilization was reported at \texttt{0\%}, indicating that the build process was largely I/O-bound, likely due to reading files, writing intermediate layers, and performing setup tasks for the container image.

It is important to note that this benchmark reflects the case where the Docker image did not previously exist. The initial build incurs higher latency due to downloading base layers, compiling dependencies, and writing the final image to disk. In subsequent builds where layers are cached and the image already exists locally, the build time is significantly reduced, and CPU utilization may increase due to reduced I/O waits.

These results highlight that while the initial Docker build may introduce measurable delay, especially in cold-start scenarios, this cost can be mitigated through caching and reuse of previously built images. For workflows like Houdini, where consistency and speed are critical, avoiding redundant rebuilds is key to maintaining performance.


\subsubsection{Running a Trick in Docker}

To evaluate the runtime characteristics of executing a Houdini trick, we measured the performance of the command \texttt{docker run -it 504de41abf9b}.

Despite the failure status, the resource usage remains relevant for benchmarking purposes. The user time recorded was \texttt{0.10 seconds}, and the system time was \texttt{0.07 seconds}, highlighting that the trick performed a minimal amount of computation and kernel-level operations. The total CPU utilization for the job was measured at \texttt{9\%}, suggesting that the container was idle or I/O-bound for most of its execution time.

These metrics confirm that even when a trick fails, its impact on system resources is negligible, making Houdini suitable for high-throughput and low-latency security testing across many configurations.


\subsubsection{Baseline Comparison Outside Houdini}

To contextualize Houdini’s efficiency, we measured a baseline workflow executed manually, without the automation Houdini provides. This baseline consisted of starting the virtual machine, building the Docker image, and executing a security trick—all performed via shell scripts without caching or orchestration.

We used \texttt{/usr/bin/time -v} to capture system-level performance metrics. The manually executed baseline took approximately \textbf{55.70 seconds} of wall-clock time, with a user time of \textbf{22.51 seconds} and a system time of \textbf{18.12 seconds}. The CPU utilization for this task was \textbf{73\%}, indicating moderate computational activity with some idle time.

Compared to Houdini’s streamlined execution, which achieves the same test in a fraction of the time through reuse of cached artifacts and fewer manual dependencies, this demonstrates that Houdini significantly reduces runtime overhead. In addition to speed, Houdini ensures consistent environments and eliminates the variability often introduced in manual workflows.





\subsection{Macobenchmark}

To evaluate Houdini’s runtime efficiency, we measured the total time required to execute a single trick, from virtual machine boot to container execution and result collection—using Python’s \texttt{time} module to record start and end timestamps. The initial execution took approximately \textbf{82.53 seconds}, which includes both the time to boot the QEMU-based virtual machine and the time required to build the Docker image from scratch. This image build step is a one-time cost, contributing significantly to the initial delay. In contrast, all subsequent runs reused the prebuilt Docker image, reducing execution time to an average of \textbf{22.02 seconds}. These measurements highlight the impact of caching and image reuse on performance. The bulk of the time in repeated executions is attributed to VM startup and trick orchestration, while container launch and trick evaluation themselves are relatively fast. Compared to direct execution on a host system without virtualization, where tricks typically complete in under 5 seconds, Houdini introduces additional isolation overhead in exchange for improved confinement and repeatability.

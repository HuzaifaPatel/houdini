% \section{Overview of Hypervisors}



The existance of cloud computing can be attributed to virtualization, which is a technology that makes it possible for multiple different operating systems (OSs) to run concurrently, and in an isolated environment on the same hardware. How does virtualization achieve this? It makes use of a machines hardware to support the software that creates and manages virtual machines (VMs). A \gls{vm} is a virtual environment that provides the functionality of a physical computer by using its own virtual central processing unit (VCPU), memory, network interface, and storage. The software that creates and manages \glspl{vm} is formally called a hypervisor or virtual machine monitor (VMM). The virtualization marketplace is comprised of four notable hypervisors, which are: (1) VMWare, (2) Xen, (3) Kernel-based Virtual Machine (KVM), and (4) Hyper-V. The operating system running a hypervisor is called the host OS, while the VM that uses the hypervisor is called the guest OS. To maintain consistency within this proposal, we will use the word "hypervisor" when referring to virtualization software. Hypervisors can be divided into two types, depending on where they are located on the machine: (1) type 1 and (2) type 2.

\section{Type 1 Hypervisor}

Type 1 hypervisors run directly on physical hardware to create, control, and manage VMs, and do not require support from the host OS. Type 1 hypervisors are also called native or bare-metal hypervisors. The first hypervisors, which IBM developed in the 1960s were type 1 hypervisors ~\cite{meier2008ibm}. Examples of type 1 hypervisors include, but are not limited to Xen, KVM, VMware ESX, and Microsoft Hyper-V ~\cite{bauman2015survey}.


\section{Type 2 Hypervisor}

Type 2 hypervisors (also called hosted hypervisors) are installed on the OS (Windows, Linux, MacOS), similar to how computer programs are installed onto an OS. In other words, a type 2 hypervisor runs as a process on the host OS. Type 2 hypervisors abstract guest OSs from the host OS by introducing a third software layer above the hardware, as shown in figure 2.1. Examples of type 2 hypervisors include but are not limited to VMware Workstation, VirtualBox, and QEMU ~\cite{bauman2015survey}.



\section{Problems With Type 1 \& Type 2 Hypervisor Classifications}

Although the definitions of type 1 and type 2 hypervisors are widely accepted, there are gray areas where the distinction between the two remain unclear. For instance, according to its creator RedHat, KVM is implemented and deployed using two Linux kernel modules that effectively convert the host Linux OS into a type-1 hypervisor ~\cite{graziano2011performance}. At the same time, KVM can be categorized as a type 2 hypervisor because KVM VM's are standard Linux processes that are competing with other Linux processes for CPU time given by the Linux kernel's native CPU scheduler ~\cite{kvmcpuschedule}. Due to disagreements and vagueness in the definitions of type 1 and type 2 hypervisors, two new classifications were defined: (1) native hypervisors and (2) emulation hypervisors ~\cite{10.1145/2775111}.



\section{Native Hypervisor}

Native hypervisors are hypervisors that push VM guest instructions directly to the physical machines CPU, by using virtualization extensions like Intel VT-x. ~\cite{10.1145/2775111}. Examples of Native hypervisors include but are not limited to Xen, KVM, VMware ESX, and Microsoft HyperV.


\section{Emulation Hypervisor}
Emulation hypervisors are hypervisors that emulate every VM guest instruction using software virtualization ~\cite{10.1145/2775111}. Emulated guest instructions are very easy to trace because all guest VM instructions are trapped to the hypervisor. Examples of emulation hypervisors include but are not limited to QEMU, Bochs, early versions of VMware-Workstation, and VirtualBox ~\cite{10.1145/2775111}.

On Linux, process containment relies on several key technologies, including Unix, cgroups, namespaces, Linux capabilities, apparmor, selinux, and seccomp. Below, we provide an overview of each of these mechanisms.

\section{cgroups}
Cgroups, or control groups, are a Linux kernel feature that allows system administrators to allocate and manage system resources (such as CPU, memory, disk I/O, and network bandwidth) for processes or groups of processes. When you create a cgroup, you are essentially grouping together processes and imposing resource constraints on them. This is crucial for resource management and isolation in multi-user or containerized environments. For instance, cgroups allow you to set a limit on the amount of memory a set of processes can use, preventing any single process from consuming excessive resources and affecting other processes or the system as a whole. Additionally, cgroups allow for the prioritization of resources, ensuring that critical processes receive more CPU or memory than less important ones. They also offer monitoring capabilities to track how much of each resource a process or cgroup is consuming. This feature is extensively used in containerization technologies like Docker, where containers are assigned their own resource limits via cgroups to ensure fairness and prevent resource hogging.

\section{namespaces}
Namespaces are another crucial Linux kernel feature that provides process isolation. A namespace isolates certain aspects of a system for a process or group of processes, ensuring that they have their own independent environment. There are several types of namespaces, including PID, network, mount, user, and UTS namespaces. For example, a PID namespace allows processes within it to have their own process IDs, meaning that processes in different PID namespaces can have the same process ID without interfering with each other. Similarly, network namespaces allow processes to have their own network stack, which includes IP addresses, routing tables, and network interfaces. This isolation is fundamental for containers, as it ensures that processes running in one container cannot see or interact with processes in another, even though they may be running on the same physical host. Namespaces, combined with cgroups, provide the foundation for building lightweight, secure containers in Linux systems.

\section{Linux capabilties}
Linux capabilities are a fine-grained security mechanism that splits the traditional superuser (root) privileges into smaller, more manageable pieces. Instead of giving a process full root access, Linux capabilities allow for the assignment of specific privileges to processes, such as the ability to bind to a network port or change the system time, without granting full administrative control. This is particularly useful for increasing system security, as it limits the potential damage caused by vulnerabilities in applications. For example, a web server might require the ability to bind to port 80 but should not need full root privileges. By assigning only the necessary capabilities to a process, the security surface area is reduced, making it harder for an attacker to exploit. This approach is commonly used in containerized environments, where processes are run with just the capabilities they need to function.

\section{Seccomp (Secure Computing Mode)}
Seccomp is a security feature in the Linux kernel that allows administrators to filter and restrict the system calls that processes can make. It provides a mechanism to limit the actions that a process can perform, which is particularly useful in reducing the attack surface of applications, especially in containerized environments. With seccomp, you can create a whitelist or blacklist of system calls, effectively controlling which parts of the operating system a process can access. For instance, you could block potentially dangerous system calls like execve, which is used to execute programs, or restrict the ability to open files by denying access to certain file descriptors. This reduces the risk of an attacker exploiting a process to gain control over the system. Seccomp is often used in combination with other security mechanisms like AppArmor and SELinux to provide an additional layer of protection.

\section{App Armor (Application Armor)}
AppArmor is a Linux security module that provides Mandatory Access Control (MAC) by enforcing security policies on individual programs. It restricts the actions that applications can perform by defining profiles that specify which files, directories, and capabilities the program can access. AppArmor operates by using a set of predefined or custom profiles, which are attached to programs, to limit their access to system resources. For example, an AppArmor profile for a web server might restrict the server’s access to specific directories and prevent it from executing arbitrary binaries or making network connections to external IP addresses. AppArmor is easier to configure and manage than some other security modules, and it provides a level of protection by ensuring that even if an application is compromised, the attacker has limited access to the system.

\section{selinux}
SELinux is a security module that provides more granular control than traditional discretionary access control (DAC) by using mandatory access control (MAC). It enforces policies that define which processes or users can access specific files or resources, based on security contexts. These contexts are applied through SELinux policies, which restrict access even if a process has standard permissions. SELinux is commonly used in high-security environments, such as government or financial systems, to prevent unauthorized access. While powerful, it requires careful configuration to avoid restricting legitimate processes and reduce the risk of privilege escalation.













\section{YAMA}


Yama is a Linux Security Module (LSM) that adds additional restrictions to the ptrace system call, which is commonly used for debugging and process tracing. While ptrace is a powerful tool for legitimate uses like debuggers and profilers, it can also be abused by malicious processes to interfere with or spy on other running processes. Yama was introduced to mitigate these risks by controlling and limiting which processes can use ptrace on others, providing a simple but effective hardening mechanism against certain types of attacks.

The core of Yama’s functionality revolves around the /proc/sys/kernel/yama/ptrace\_scope setting, which controls how restrictive the kernel is regarding ptrace access. The available levels range from 0 to 3, each enforcing progressively stricter controls. With ptrace\_scope=0, the system behaves traditionally, allowing any process to ptrace another process owned by the same user if the target is marked as dumpable. At 1, only parent processes can trace their children, limiting the risk of arbitrary tracing. Level 2 requires a process to have CAP\_SYS\_PTRACE capabilities (effectively root-level permissions) to trace any process, and level 3 completely disables ptrace system-wide, locking down the system from process tracing even by privileged users.

Yama is especially valuable in multi-user systems or environments where processes run under the same user account but should remain isolated from one another, such as in containerized or sandboxed environments. While it is a relatively lightweight security module compared to more comprehensive systems like SELinux or AppArmor, it adds a meaningful layer of defense against local privilege escalation attacks. However, it’s important to balance its restrictions with the need for debugging and profiling tools that rely on ptrace. In production environments focused on security, higher ptrace\_scope values (such as 2 or 3) may be appropriate, while development systems typically keep it at 0 or 1 to allow standard debugging workflows.

Yama does not enforce its `ptrace\_scope` restrictions when attempting to trace host processes from within a container because Yama’s enforcement is limited to the current process visibility defined by PID namespaces. In most container environments, the containerized process runs in an isolated PID namespace and cannot see or interact with host processes unless explicitly configured using options like `--pid=host`. Even when a container is started with `--pid=host`, allowing it to see host processes, Yama primarily governs interactions within the same namespace context and is not designed to enforce security policies across different namespaces.

Additionally, for Yama to restrict tracing of host processes, the containerized process would not only need visibility of host PIDs but also require sufficient privileges, such as `CAP\_SYS\_PTRACE`, in the host’s user namespace. In practice, other security mechanisms like AppArmor, SELinux, and seccomp often prevent such privilege escalation before Yama’s policies even apply. As a result, Yama’s effectiveness is primarily confined to preventing ptrace interactions between processes that are already within the same visibility scope, rather than serving as a cross-namespace isolation mechanism. This makes Yama a useful tool for hardening processes within the same environment but not a comprehensive defense against container-to-host process tracing attempts.


The behavior of Yama is controlled by the \texttt{/proc/sys/kernel/yama/ptrace\_scope} setting, which determines the level of restriction imposed on \texttt{ptrace} operations. The possible values are summarized below:

        \textbf{Value} & \textbf{Behavior} \\
        \hline
        0 & No additional restrictions. Processes can trace any other process they have permissions for. \\

When Yama’s ptrace\_scope is set to 2, processes cannot freely attach to other unrelated processes, even if they have administrative capabilities or are running as root. In this mode, the ability to trace or debug a process must be explicitly granted by the target process itself or configured through system-level controls.

This permission can be granted using the prctl() system call with the PR\_SET\_PTRACER option, allowing a specific process to act as a tracer. Alternatively, the system administrator can modify the global ptrace policy by lowering the ptrace\_scope value in /proc/sys/kernel/yama/ptrace\_scope. Without such explicit authorization, ptrace attempts will consistently fail, regardless of user privileges or capabilities. This design enforces stronger security boundaries by preventing unauthorized inspection or manipulation of processes, even by privileged users, unless the target process explicitly consents to being traced.



Yama is a Linux Security Module (LSM) that enforces additional restrictions on the \texttt{ptrace} system call and process debugging mechanisms. Its primary purpose is to reduce the attack surface for exploits that rely on process introspection and manipulation. By limiting the ability of processes to trace or interact with others, Yama enhances system security and makes privilege escalation attacks more difficult. This is particularly valuable in containerized environments and multi-user systems where process isolation is critical.

\section{Kernel Implementation}

Yama is implemented in the Linux kernel source file \texttt{security/yama/yama\_lsm.c}. It integrates with the kernel's LSM framework by registering specific hooks that intercept and evaluate \texttt{ptrace} operations. During initialization, Yama registers its hooks using the following function:

\begin{verbatim}
void __init yama_add_hooks(void)
{
    pr_info("Yama: becoming mindful.\n");
    security_add_hooks(yama_hooks, ARRAY_SIZE(yama_hooks), "yama");
    yama_init_sysctl();
}
\end{verbatim}

Here, \texttt{security\_add\_hooks} registers an array of hook functions defined in \texttt{yama\_hooks}. These hooks include:

\begin{itemize}
    \item \texttt{ptrace\_access\_check}
    \item \texttt{ptrace\_traceme}
    \item \texttt{task\_prctl}
    \item \texttt{task\_free}
\end{itemize}

Each hook is associated with a specific kernel operation, allowing Yama to enforce its security policies at critical points.

\section{Related Work}

At the time of this writing, to our knowledge, Houdini is the first comprehensive approach for evaluating and comparing \textit{container confinement mechanisms}. Much of the container security literature to date has focused on either vulnerability scanning of container images, building offensive/attack tools for container escapes, or proposing best practices for securing container runtimes. While these papers, tools, and documents do not directly share our research objectives, they still broadly fit into the container security landscape. Additionally, research on VM escapes and sandbox escapes has provided valuable insights into isolation vulnerabilities, many of which relate to container security. Techniques used to break out of hypervisors and sandboxed environments often share similarities with container escape methods, which the importance of strong confinement mechanisms. The remainder of this section does not aim to exhaustively enumerate all container security tools and systems, but rather to highlight the various salient methods, including prior research on times the confinement of VMs and sandboxes have been escaped as it is related to work.\\

\noindent\textbf{Regression Testing.} One common practice in continuous integration/continuous deployment (CI/CD) pipelines is the use of automated vulnerability scanning tools to detect known vulnerabilities in container images. Tools such as Trivy \cite{trivy} and Clair \cite{clair} are often integrated into CI pipelines to perform vulnerability assessments during the image build process. These tools automatically scan for security flaws in the container image, ensuring that only secure images are deployed to production. For example, GitLab’s CI/CD pipeline includes built-in features for Container Scanning with Trivy, automatically running vulnerability scans whenever new Docker images are built or updated.

In addition to security scanning and policy enforcement, CI/CD pipelines also use container hardening tools like Docker Bench for Security \cite{docker_bench} and Kube-bench \cite{kube_bench} to ensure containers are securely configured. These tools can be integrated into the pipeline to automatically check container configurations against security best practices, such as ensuring that containers run as non-root users or that unnecessary ports are closed. CircleCI \cite{circleci}, for example, integrates Docker Bench to verify that new container builds follow best practices before they are pushed to production.\\

\noindent\textbf{Vulnerability Scanners.} Many free, open, and closed-source tools exist for identifying the presence of known vulnerabilities in container images. Shu \etal~\cite{shu2017study} developed a vulnerability scanning tool to scan Docker Hub container images at scale. They found that on average, official and community images have concerning amounts of vulnerabilities (180+), and that these vulnerabilities remain unpatched for hundreds of days. Their study utilized the Docker Image Vulnerability Analysis (DIVA) framework, which automates the discovery, download, and analysis of over 300,000 Docker images. The findings revealed that more than 80\% of both official and community images contained at least one high-severity vulnerability, and many images were not updated for extended periods. Moreover, vulnerabilities were often inherited from parent images to child images, further increasing security risks.\\

\noindent\textbf{Best Practices.} Users in search of (often high-level) advice on how to improve the security of their container deployments can consult one of many best practices guides available online. One such guide is the Center for Internet Security (CIS) Docker Benchmark \cite{CIS}. In our experience, guides tend to offer generic advice (e.g., ``\textit{Only allow read access to the root filesystem}''). This is problematic because it oversimplifies container security. Generic advice may seem straightforward, but it doesn't account for the specific context or unique configuration of an individual deployment. Such one-size-fits-all recommendations can lead users to believe that simply following these broad guidelines is enough to secure their systems, potentially leaving critical vulnerabilities unaddressed. In reality, effective container security requires a nuanced, tailored approach that considers the particular needs and threat models of each environment. Houdini fills the gap between generic advice and practical security by enabling one to objectively evaluate the effectiveness of your container confinement measures.\\

\noindent\textbf{Offensive Tools.} The offensive security community has developed a range of specialized tools aimed at identifying and exploiting vulnerabilities within containerized environments. Containers, while providing strong isolation, are not immune to attacks, and these tools focus on testing the robustness of container defenses. CDK\footnote{\url{https://github.com/cdk-team/CDK}} and DEEPCE\footnote{\url{https://github.com/stealthcopter/deepce}} are two widely used, open-source container penetration testing toolkits that leverage a collection of known exploits to gain persistence, escape the container, and gather sensitive information about the container environment. These tools aim to bypass isolation mechanisms like namespaces, cgroups, and SELinux, often using a variety of aggressive techniques to identify weaknesses in container security. CDK specifically uses any available method to circumvent security measures, providing a broad toolkit to test the limits of a container's defense. Meanwhile, DEEPCE, developed by stealthcopter, focuses on privilege escalation and container enumeration, attempting to exploit specific weaknesses to achieve container escapes, thereby compromising the host system. In contrast, Houdini takes a more systematic and structured approach to container security testing. Rather than focusing solely on exploiting vulnerabilities, Houdini allows for the direct comparison of defensive techniques by clearly defining the testing environment, outlining the exploit steps, and documenting the expected outputs.\\

\noindent\textbf{Virtual Machine Escapes.} VM escapes occur when an attacker successfully breaks out of a virtualized confined environment, gaining unauthorized access to the host system. Given that hypervisors manage multiple VMs on shared hardware, such escapes can lead to host compromise, cross-VM attacks, and lateral movement within cloud environments. One of the most notable VM escape vulnerabilities is VENOM (CVE-2015-3456) \cite{abdoul2018novel}, which exploited a flaw in the virtual floppy disk controller (FDC) implementation in QEMU, affecting platforms like Xen, KVM, and VirtualBox. Other significant VM escape vulnerabilities include Cloudburst (2009), which exploited VMware's virtual graphics driver; CVE-2018-6981 and CVE-2018-6982, which targeted VMware ESXi, Workstation, and Fusion \cite{vmware2018escape}; and multiple VirtualBox vulnerabilities (2017) enabling guest-to-host code execution \cite{virtualbox2017bugs}. Additionally, side-channel attacks like MDS/ZombieLoad (2019) demonstrated how speculative execution flaws could be leveraged across VMs \cite{mds2019attack}. More recent research has uncovered weaknesses in encrypted virtualization, such as the SEVered attack (2018), which extracted plaintext memory from AMD SEV-protected VMs \cite{severed2018}, and the Heckler attack (2024), which manipulated non-timer interrupts to compromise confidential VMs in AMD SEV-SNP and Intel TDX \cite{heckler2024}.\\

\noindent\textbf{Sandbox Escapes.} Sandboxing is a critical security mechanism for restricting the execution of untrusted code, commonly used in browsers, mobile apps, and security tools. A sandbox escape occurs when an attacker bypasses these restrictions, executing arbitrary code with higher privileges and potentially leading to full system compromise. Modern web browsers heavily rely on sandboxing to isolate JavaScript execution from the underlying OS. However, several high-profile vulnerabilities have enabled sandbox escapes. For example, CVE-2019-5786 \cite{chromezeroday}, a use-after-free vulnerability in the FileReader API of Google Chrome, allowed attackers to escape Chrome's sandbox and execute code on the host. Other notable sandbox escape vulnerabilities include CVE-2022-26706, which exploited a flaw in macOS's App Sandbox to execute code outside of restricted permissions \cite{macossandboxescape}; CVE-2023-36719, a stack corruption vulnerability in Windows OS that enabled escape from the Chromium sandbox \cite{chromiumsandboxescape}; and CVE-2024-4040, which was actively exploited to break out of CrushFTP’s Virtual File System (VFS) \cite{crushftpsandboxescape}. Additionally, vulnerabilities in Judge0, an online code execution system, exposed systems to full takeover by allowing attackers to escape its sandbox \cite{judge0sandboxescape}. Research has also uncovered critical flaws in vm2, a JavaScript sandbox library, which could be exploited to bypass its security restrictions and gain remote code execution \cite{vm2sandboxescape}.

\subsection{Apparmor}

AppArmor is a Linux security framework based on mandatory access control, similar to SELinux, but it focuses on restricting individual programs [9]. It works by applying predefined security profiles that limit what a program can do [9]. In Docker, AppArmor can be used to load these profiles into containers to restrict their behavior. If no profile is specified, Docker automatically applies a default one [9].

Mattetti et al. [65] developed LiCShield as a framework that uses AppArmor as its enforcement backend. It automatically generates custom AppArmor security profiles by analyzing container behavior in a pre-production environment. These profiles are then used to tightly confine both the container’s runtime behavior and its interactions with the host system, ensuring that only authorized actions are permitted during execution.

Sun et al [13] extend AppArmor to work independently inside containers by introducing a new concept called a security namespace. Normally, AppArmor is global, it enforces one set of security rules for the whole system, which means containers cannot define or apply their own AppArmor policies. The authors solve this problem by modifying the Linux kernel so that each container can have its own separate AppArmor namespace. This allows a container to load and enforce its own AppArmor profiles for its applications, independent of the host system's policies.

With this change, both the host and the container can apply AppArmor protections at the same time. For example, while the host might enforce a general container confinement policy, the container itself can load a specific profile to restrict what Firefox or MySQL can do [13]. 

Zhu et al [9] create Lic-Sec, which is an enhanced AppArmor profile generator that improves Docker container security by combining the strengths of Docker-sec and LiCShield. The reason for creating a similar tool to LiCShield is that LiCShield is incompatible with recent versions of Docker. Lic-Sec automatically creates fine-grained profiles based on container behavior, restricting capabilities, network access, file operations, mounts, and shell execution. By using both Auditd and SystemTap for tracing, Lic-Sec generates stricter, more comprehensive profiles that block privilege escalation and container escape attacks. It adapts to container use cases and enforces these profiles at runtime for stronger and automated protection.

Houdini could have influenced Zhu et al [9] work by providing an automated framework to evaluate Lic-Sec's effectiveness across diverse environments. For example, instead of manually testing exploits against a fixed kernel version, docker version and set of container images, the authors could have used Houdini to run the same exploit across multiple kernel versions, Docker versions, configurations, and AppArmor profiles to identify gaps in enforcement. Additionally, Houdini’s ability to replay tricks across time and machines would have allowed for more reliable validation of Lic-Sec’s defenses, such as verifying whether blocking /bin/bash consistently prevents privilege escalation across real-world images.






\subsection{Control Groups}

cgroups (short for control groups) are a Linux kernel feature used to manage and limit system resources like CPU, memory, and I/O for groups of processes [72]. They allow administrators or container runtimes like Docker to control how much of a resource each container can use. For example, Docker can apply cgroup settings to restrict a container’s CPU time or memory usage. This helps prevent a single container from consuming too many resources and affecting others on the system [72]. While cgroups are not designed to stop one container from accessing or interfering with another container’s data or processes [72], they are essential for defending against certain types of Denial-of-Service (DoS) attacks by limiting the damage a container can cause through resource exhaustion [72].

Chelladhurai et al. [72] identifies DoS attacks as a significant threat in containerized environments like Docker. The authors emphasize that while containers offer process isolation, they lack strong guarantees against resource abuse, which can allow a malicious container to exhaust host resources and impact other containers.

To address this, they propose several practical mitigation strategies using Linux cgroups [72]. They argue that cgroups are essential for defending against DoS attacks by limiting a container’s access to CPU, memory, and I/O resources. However, they also note that cgroups alone do not provide full isolation between containers. Their proposed DoS mitigation technique includes three test cases: setting memory limits directly in the docker run command using -m=512mb, applying default memory limits in the Docker configuration file (/etc/default/docker), and enforcing a system-wide memory limit for containers that do not specify their own [72]. For evaluation, the paper includes sample attack code to simulate DoS scenarios. One example allocates memory indefinitely using malloc, while another consumes CPU resources by endlessly calculating prime numbers. These tests demonstrate how resource limits can effectively prevent containers from overwhelming the host.

The original paper takes a manual approach to testing DoS attacks by running memory and CPU-intensive scripts inside containers with various resource limits. While this method demonstrates the effectiveness of using cgroups to mitigate DoS risks, it is limited in scale and reproducibility. Houdini can automate and greatly expand this type of testing. Instead of running scripts manually, Houdini can encode these attacks as repeatable tricks, such as infinite memory allocation or continuous CPU-bound computations. These tricks can then be executed systematically across a wide range of Docker versions, kernel versions, and container configurations (e.g., with or without memory limits like the -m flag). This is especially important because the implementation and enforcement behavior of cgroups can differ between kernel versions, particularly between cgroups v1 and v2, or in how specific resource limits are handled. By capturing and comparing results, Houdini enables a scalable and repeatable evaluation framework. It can identify which combinations of settings are vulnerable to DoS and which configurations effectively block the attacks, providing a more comprehensive assessment than manual testing.

\subsection{Extended Berkeley Packet Filter}


eBPF (extended Berkeley Packet Filter) is a Linux kernel technology that allows small, sandboxed programs to run safely inside the kernel without modifying kernel source code or loading kernel modules. Originally designed for network packet filtering, eBPF has evolved into a general-purpose tool for tracing, monitoring, and security enforcement. In essence, eBPF lets developers attach custom logic to various kernel events, like system calls, network activity, or file operations, and collect data or enforce rules with minimal performance overhead. Because eBPF programs run in a restricted environment and are verified for safety before execution, they offer a powerful but secure way to extend kernel behavior dynamically.


Lopes et al. [55] use eBPF as the core mechanism for tracing system calls made by containerized applications. The goal of the system is to automatically generate custom Seccomp profiles that strictly limit the syscalls a container can perform, thereby reducing the attack surface. To achieve this, the authors use eBPF's powerful kernel-level tracing capabilities to hook into every syscall. Specifically, they implement a BCC (BPF Compiler Collection) program that attaches eBPF probes to all system calls and logs detailed information such as the syscall name, timestamp, process ID, and the namespace from which the syscall originated.

For Lopes et al. [55], the goal is to automatically generate Seccomp profiles by tracing the actual system calls used by a containerized application. While their approach uses eBPF for runtime tracing, Houdini could have provided complementary value by automating and scaling this profiling process across many container configurations, Docker versions, and kernel versions. Houdini’s test matrix model allows systematic exploration of diverse runtime flags (e.g., --privileged, --cap-add, AppArmor profiles) to evaluate whether the generated Seccomp profile remains effective across different settings. Additionally, Houdini could validate whether the reduced syscall profile indeed blocks known exploits, as done in Lopes' Apache test case, but at scale.

This namespace information is crucial because it allows the system to filter out irrelevant syscalls made by the host or other processes, ensuring that only syscalls from the target container are recorded. These logs are then processed to generate a Seccomp profile that whitelists only the syscalls actually used by the application during testing. One of the key advantages of using eBPF is its runtime-agnostic nature. It works not only with Docker but also with Podman or any other container technology, since the tracing happens at the kernel level. Additionally, eBPF's integration into the CI/CD pipeline enables automatic profile generation whenever code changes are committed, making it easy to keep Seccomp profiles up to date with minimal manual effort. As a proof of concept, the authors applied their system to a vulnerable Apache container and demonstrated that, after tracing and generating a Seccomp profile using eBPF, the container was no longer susceptible to a known RCE vulnerability (CVE-2018-11776).

He et al. [59] found a new type of attack where eBPF can be misused to break container isolation in shared-kernel environments like the cloud. eBPF was designed to safely let programs interact with the Linux kernel for things like monitoring and debugging. But the paper shows that attackers inside a container can use eBPF helper functions, such as ones that read or write other processes’ memory to spy on or interfere with programs running outside the container, including on the host. These attacks can steal sensitive data, crash important services like systemd, or even escape the container by taking over a root-level process on the host.

One key problem is that eBPF tracing programs are not limited by namespaces, so they can see and interact with processes system-wide. The authors tested this in real-world services like Jupyter notebooks and Kubernetes clusters and successfully escaped containers or spread attacks across nodes. Even trusted tools like Cilium and Datadog that use eBPF for monitoring could be at risk if used in containers with the wrong settings.

To fix this, the paper proposes a new system called CapBits. It gives each process fine-grained control over which eBPF features it can use or be targeted by. CapBits is faster and more secure than previous methods and can stop attacks where eBPF is used to hijack sensitive processes. Overall, the paper warns that while eBPF is a powerful tool, its risks in container environments are not well understood and need better protection.

Jiao et al. [56] introduce Seccomp-eBPF, a new way to improve system call filtering on Linux using the extended Berkeley Packet Filter (eBPF). System call filtering is a key technique used to protect the operating system from untrusted applications, such as containers, by controlling which system calls are allowed. The current standard, Seccomp with classic BPF (cBPF), is widely used but has serious limitations. It only allows basic, static checks and cannot store information or respond to complex patterns of behavior, making it hard to implement advanced security policies.

Seccomp-eBPF solves this by allowing developers to write more powerful and flexible filters using eBPF, a newer language already used in many parts of the Linux kernel. With Seccomp-eBPF, filters can track state (such as counting how many times a system call has been used), detect specific sequences of system calls, prevent race-condition attacks by forcing certain system calls to run one at a time, and safely examine data passed from user programs. These features make it possible to block sophisticated attacks that cBPF cannot handle.

The authors implemented this system in the Linux kernel and added support for it in the crun container runtime. They showed that it works well in practice. For example, it reduced the number of allowed system calls during the startup of common server applications by up to 55\%, significantly shrinking the attack surface. Despite its added flexibility, Seccomp-eBPF maintained performance similar to optimized cBPF filters and was much faster than user-space alternatives like Seccomp Notifier. Overall, Seccomp-eBPF offers a safer and more powerful way to secure Linux systems, especially in environments like containers that rely heavily on system call filtering.

Findlay et al. \cite{findlay2021bpfcontain} use eBPF to build a new security system called BPFCONTAIN that improves container security on Linux. Containers often rely on tools like seccomp, AppArmor, and SELinux for isolation, but these tools can be complicated, inconsistent, and not designed specifically for containers. To solve this problem, BPFCONTAIN uses eBPF to monitor and control what containers are allowed to do directly inside the Linux kernel. It checks actions like file access, network use, and system calls, and blocks anything not allowed by the container’s policy. These rules are written in a simple YAML file, making it easy to manage. BPFCONTAIN loads these rules and programs at runtime, without changing the Linux kernel or container tools like Docker. It also adds extra protections to block known container attacks, such as privilege escalation.


\subsection{System Call Filtering}

System call filtering is a security technique used to control which system calls a program is allowed to make to the operating system. Since system calls are the primary way that applications interact with the kernel, restricting them helps reduce the attack surface and prevent malicious behavior. On Linux, this is commonly done using Seccomp, which lets developers create filters to allow or block specific syscalls. Traditional filtering with classic BPF (cBPF) is simple and efficient but limited, it only supports static rules and cannot track complex behavior or context. More advanced techniques, such as those using eBPF, improve flexibility by allowing filters to maintain state, inspect arguments, and respond dynamically to syscall patterns. 

This paper used system call filtering as a key part of its security monitoring approach. Gantikow et al. [63] used two tools named Sysdig and Falco that rely on a kernel module to capture and analyze system calls made by containers. By watching these low-level operations, the system can spot unusual or potentially harmful behavior. Sysdig collects all system calls and lets users filter them by container, process, or syscall type to reduce noise. Falco adds a layer of security by letting users define rules that flag suspicious behavior based on these system calls.

For example, the authors created rules to detect when a container tries to access files outside its expected directories using the open() syscall. They also detected unauthorized programs being run inside containers by monitoring execve calls. Attempts to break out of containers were flagged by watching for the setns syscall, and unexpected network connections were detected by tracking relevant network-related system calls.

While Falco can only detect individual suspicious events, not patterns or sequences of events like those involved in buffer overflows or denial-of-service attacks, the use of system call filtering still proved effective in catching many types of threats with low performance impact.

Ghavamnia et al. [27] present Confine, a system that automatically generates restrictive system call policies for Docker containers. Instead of relying solely on dynamic analysis (which often misses rare or conditional execution paths), Confine uses a hybrid approach: it performs a short dynamic analysis to discover all executables launched during container startup and then uses static analysis on those binaries to extract the complete set of system calls they may invoke. This includes both libc-invoked and directly invoked syscalls.

The goal of this syscall filtering is to allow containers access only to the syscalls they truly need, thereby blocking access to the rest, many of which may contain vulnerabilities or provide attack vectors for privilege escalation or container escape. By creating custom Seccomp BPF profiles that deny all unnecessary syscalls, Confine ensures that even if an attacker gains access to a container, they cannot exploit most of the kernel interface.

The evaluation showed that Confine could disable 145 or more system calls (out of 326) for over half of the tested containers, neutralizing 51 known kernel CVEs. This significantly exceeds Docker’s default Seccomp filter, which only disables 49 syscalls.

Houdini could be used to dynamically test whether Confine’s generated Seccomp profiles are too restrictive or too permissive. For instance, if Houdini can successfully run an attack trick under a Confine policy, it might indicate an over-permissive profile. Conversely, if legitimate workloads fail under Confine’s policy in Houdini’s environment, this suggests over-restriction.

Confine assumes that policies generated statically will remain correct across systems. But Linux syscall implementations and Docker behavior change over time. Houdini could systematically evaluate if the same Confine-generated profile works consistently across kernel versions, and flag new vulnerabilities.

Jiao et al. [56] used system call filtering to improve the security of Linux systems by controlling which system calls a program is allowed to make. Normally, this is done using a tool called Seccomp, which filters system calls based on simple rules written in a limited language called cBPF. However, cBPF is very basic, as it can only check the syscall number and some simple arguments. It cannot remember past behavior, check syscall sequences, or read memory safely. This makes it hard to write strong security rules.

Jiao et al. [56] solve this by creating a new system called Seccomp-eBPF, which uses the more powerful eBPF language instead of cBPF. eBPF allows writing filters that can remember past system calls, count how many times a system call was used, block system calls if they’re too frequent, or only allow them in certain program phases. It can also safely inspect data passed by pointer (like file paths), and prevent known bugs caused by racing system calls.

With these improvements, Seccomp-eBPF can block real-world attacks that cBPF cannot. It also helps reduce the number of system calls allowed in early stages of a program (reducing attack surface) by over 50\% in some cases. The paper shows that this system is both safer and faster than older methods that rely on user-space monitoring, and it works well in environments like containers.


\subsection{Rule-based Systems}

A rule-based system is one that makes decisions or detects events based on a predefined set of rules. These rules are usually written by security experts or administrators and follow simple if-then logic. For example, a rule might state that if a certain system call is made by an unexpected process, the system should flag it as suspicious or block it. This approach allows for clear, predictable behavior because every decision is based on explicitly defined conditions.

In the context of container or system security, rule-based monitoring is often used to detect abnormal behavior. Tools like Falco apply rules to system call traces to identify activities that deviate from what is considered normal or safe. For example, rules can be written to detect unauthorized file access, unusual network activity, or attempts to escalate privileges. These systems are easy to understand and customize, making them widely used in production environments.

However, rule-based systems also have limitations. They can only detect behaviors that have been anticipated and written into the rules. This makes them less effective against new or complex attack patterns that do not match existing rules.

A proposed method by Jian et al. [6] implemented as a shell script that runs on the host and follows a sequence of fixed rules to identify suspicious activity. It first collects metadata about all running containers and their processes, including each process’s PID, name, and namespace tag (Nsid). Then, it compares the namespace tag of each container process against the namespace tag of that container’s init process. According to the authors, if a process inside a container has a different namespace tag than its init process, it likely indicates that the process has escaped its namespace—an early sign of a container escape attempt.

This comparison logic is rule-based because it applies a deterministic rule: if Nsid(process) does not equal Nsid(init), then mark the process as suspicious. Further, the script checks whether the suspicious process resembles a shell (based on the process name). If both conditions are met, the system takes action: it kills the process and tries to trace the attacker (e.g., by retrieving the user ID or IP address).

Houdini could have helped improve the work by Jian et al. [6] by making the testing more thorough, automated, and easier to repeat. In the paper, the authors propose a way to detect Docker escape attacks by checking if a process inside the container has a different namespace tag than the container’s main process. They test this using only two known attacks: one involving the recvmsg system call and another using the Dirty COW vulnerability.

With Houdini, the authors could have gone much further. Houdini can automatically run many different escape tricks, both known and custom-made across a wide range of Docker versions, Linux kernel versions, and settings like user privileges, Seccomp filters, and namespace configurations. This would help find out whether the detection method works well in more situations or if it fails in certain cases.

Gantikow et al. [63] propose a rule-based monitoring system that detects security violations in containerized workloads by analyzing system call activity. This is accomplished using two open-source tools: Sysdig and Falco. Sysdig provides a kernel module that captures all system calls made by containers, while Falco builds upon this by applying predefined rules to flag suspicious behavior. These rules are written in a declarative format and can describe conditions such as unauthorized file access, unexpected application launches, or privilege escalation attempts.

In this rule-based model, each rule defines a pattern of behavior that is considered abnormal or malicious. For example, a rule might detect a container process trying to access files outside its designated working directory (indicating a possible information leakage or path traversal attack), or flag execution of unknown binaries inside a container (which might imply a crypto-miner or reverse shell). Rules can be whitelist-based (defining what is allowed) or blacklist-based (defining what is forbidden), and are matched against real-time system call events.

The paper presents various attack scenarios like container breakout, unauthorized networking, or loading kernel modules, and shows how each can be detected with carefully written Falco rules. While the rule-based approach is effective for many types of misuse, the authors acknowledge limitations. Notably, Falco cannot detect frequency-based or multi-event anomalies (e.g., Denial of Service or buffer overflows), as it only supports detection of single-event anomalies.

the paper by Brady et al. [51] uses a rule-based system as part of its approach to securing Docker containers. The authors incorporate Anchore Engine into their CI/CD pipeline, which applies a set of predefined security rules, also known as policies, to each Docker image. These rules include checks for known security vulnerabilities and for unsafe Dockerfile configurations, such as whether the image exposes port 22. In their implementation, the authors use Anchore's default rules, but they note that developers can create and apply their own custom rules based on specific security needs. This rule-based system allows the pipeline to automatically detect and block images that do not meet the defined security standards. It helps developers identify and fix issues early in the development process, improving the overall security of containerized applications.

The paper by Zhu et al. [9] describes three tools Docker-sec, LiCShield, and the proposed Lic-Sec all of which rely on generating and enforcing rule-based security profiles using AppArmor. These profiles consist of explicit allow/deny rules that define what operations a containerized application can perform, such as file accesses, network operations, and use of Linux capabilities.

Docker-sec uses dynamic monitoring to learn what capabilities and network accesses a container actually uses, then generates an AppArmor profile with rules that only permit those actions. LiCShield, on the other hand, uses SystemTap to trace kernel-level operations and generates rules for more types of actions, such as file mounts and execution paths. Lic-Sec combines both tools to generate a more comprehensive rule set that includes deny rules for unnecessary shell commands and tighter restrictions on mounts and execution behavior.

In all cases, the tools use observed behavior during a training phase to produce explicit, rule-based security profiles that constrain container behavior at runtime. These rules are enforced by the AppArmor Linux Security Module, making this a clear example of a rule-based system in container security.

The paper by Chen et al. [68] uses a rule-based system as part of its SEAF framework to detect security flaws in Docker container images. SEAF defines a set of detection primitives that act as basic operations for writing flexible detection rules. These primitives include content matching, feature matching, data recording, usage frequency analysis, and file extraction. Each type of vulnerability, such as misconfiguration, unauthorized access, sensitive information leakage, malware, and software vulnerabilities, is detected by combining specific primitives into rules. For example, to detect unauthorized access in Redis containers, SEAF extracts configuration files and uses regular expressions to search for insecure settings like missing passwords. These rule combinations allow SEAF to systematically inspect container layers and identify flaws by applying consistent logic across images. This rule-based approach is modular, meaning new rules can be added easily to address emerging threats without changing the underlying system. As a result, SEAF can adapt to various application scenarios and detect a wide range of security issues using well-defined and reusable rule patterns.

\subsection{OS Changes}

Luo Yang et al. [26] investigates how containers can still leak information through covert channels, even when isolation mechanisms are in place. It focuses on Docker and shows that the default security features such as namespaces and cgroups are not enough to prevent secret communication between containers. These covert channels take advantage of shared physical resources, allowing containers to bypass the expected security boundaries.

The authors present five high-capacity covert channel techniques. These include CPU load modulation, cache-based covert channels, disk I/O delay signaling, memory bus contention, and file lock contention. Each method allows a sender container to encode data into patterns of resource usage. The receiver container then decodes this data by observing how these patterns affect performance. For example, a sender might create bursts of CPU activity to represent binary data, while the receiver measures CPU latency to interpret the signal. These attacks are a form of side-channel communication, where indirect changes in system behavior are used to leak information.

The paper describes scenarios where a sender container transfers hidden information to a receiver container, despite there being no authorized communication path between them. This demonstrates that containers can communicate by exploiting shared hardware such as CPU caches or memory bandwidth. Even without network access or shared filesystems, the sender can affect system behavior in ways that the receiver can detect and interpret.

In this paper, Sun et al. [13] introduce the idea of security namespaces, a new feature in the Linux kernel that lets each container have its own security settings using tools like AppArmor and IMA. Normally, these tools are set by the host and apply to all containers. This means containers can’t create or manage their own security rules, which is a problem when you want containers to be more isolated or run different policies. The paper’s solution is to separate these security settings so that each container can have its own, without affecting the host or other containers.

To make this work, the authors made small changes to the Linux kernel, only about 1,000 to 1,500 lines of code. They tested their changes in two ways. First, with IMA, containers were able to set their own policies, like only allowing signed programs to run. The containers correctly blocked unsigned or changed programs, and they couldn’t get around the host’s security rules, which stayed in place. Second, with AppArmor, they tested 20 common programs that already had security profiles. Sixteen of them ran correctly inside containers using both the container’s and the host’s security rules. For the four that didn’t, the system gave warnings ahead of time to avoid crashes.

Even though this new design is useful, it doesn’t work with systems like Houdini. Houdini depends on the way Linux currently handles security, where rules like AppArmor and IMA are shared across the whole system. If Houdini had to work with these new security namespaces, it would need to be redesigned from the ground up. Because of that, this paper’s approach, while creative and effective, isn’t compatible with how Houdini is built today.

The paper by Sun et al. [13] relate to OS changes because it shows that even though microVMs are meant to be isolated, some of their operations are still handled by the host operating system, creating security risks. The paper finds that parts of the system such as virtiofsd and kernel threads like kvm pit and vhost are not fully isolated. They run with too much access or are not limited by cgroups. To fix this, the authors suggest changing how the OS manages these components by placing kernel threads into the correct cgroups and reducing unnecessary permissions.


\subsection{Secure Computing}

Lopes et al. [55] present a method to improve container security by automating the creation and maintenance of Seccomp profiles. Seccomp is a Linux kernel feature that limits the system calls a containerized application can make, significantly reducing the potential attack surface. However, maintaining these profiles is difficult because it requires a detailed understanding of which syscalls are needed and must be updated whenever the application changes. To address this, the authors develop a system that integrates with CI/CD pipelines to automatically trace the syscalls made during unit and integration testing using eBPF. These syscalls are collected, and a custom Seccomp profile is generated that whitelists only those calls, blocking everything else by default. For applications with incomplete test coverage, the system can use fuzzing to stimulate additional syscall paths. The approach ensures that each container has a tailored Seccomp profile, improving security without manual configuration. The authors show that this method can mitigate real-world vulnerabilities, such as CVE-2018-11776, by blocking the syscalls required for exploitation.

Ghavamnia et al. present a static analysis-based system named Confine that generates restrictive system call policies for Docker containers. Unlike previous solutions that rely on dynamic training with realistic workloads, which can miss rarely executed paths, Confine uses static analysis of container binaries and their dependencies to identify the complete superset of system calls required for correct operation. This allows it to generate Seccomp (Secure Computing Mode) profiles that deny all other system calls, significantly reducing the container’s kernel attack surface.

The authors evaluated Confine on 150 Docker images and found that it could disable over 145 system calls out of 326 for more than half the containers, far more than Docker’s default Seccomp policy. This reduction effectively neutralized 51 known kernel CVEs, demonstrating strong security gains without breaking application functionality. The approach also handles direct syscall invocations, language-specific system call mechanisms such as Go and Java, and dynamic library loading.

Confine directly builds on Seccomp as its enforcement mechanism. It generates custom Seccomp BPF profiles that define allow and deny lists for system calls per container. By statically analyzing what syscalls are truly necessary, Confine tailors these Seccomp profiles to the exact needs of each container, minimizing the set of syscalls exposed to potentially malicious applications and enhancing the host’s protection. This use of Seccomp is central to the paper’s method for reducing kernel attack surfaces and mitigating container escape vulnerabilities.

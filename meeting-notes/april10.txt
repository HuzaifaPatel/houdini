--privliedged option  overrides apparmor 
if we have --pid=host + --user=guest --privileged, we can't send signals to a uid that does not match ours. this is more of a linux thing not docker
if we use the apparmor docker-default profile, it will block the ptrace systemcall. even if we are root. It will be denied by the seccomp filter. --security-opt seccomp=unconfined cannot override this because apparmor runs independent of seccomp filters

if you're non-root, CAP_KILL only let's you send a signal to a process with the same uid.
We purposefully make python script.py in the VM have root processes, so that we can test to see if the container can kill a root process
if you're a non-root user, CAP_KILL is useless

Why sending signal does not work when apparmor=docker-default is used:
	AppArmor docker-default limits you from:
	Reading or writing to /proc/<host-pid>/mem, maps, or status

	Sending signals to processes you don't own — even if you have CAP_KILL

	Attaching debuggers via ptrace()


Capabilities grant potential power

AppArmor governs whether that power is actually allowed


CAP_SYS_PTRACE gives all the operations. So, no need to enable --privileged
